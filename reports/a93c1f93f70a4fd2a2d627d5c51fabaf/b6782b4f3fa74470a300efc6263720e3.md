## C. Findings

### F1 - High: rollback deletes a replacement account store owned by another writer

**Change:** NEW-FW3-02.  
**File/symbol:** `src\server\recovery_bundle.rs:399-404`, `import`; ownership bookkeeping in `src\server\users.rs:1265-1266`, `rekey_import`.  
**Status:** Reproduced on the local filesystem with a separate writer thread; not merely a mutant or static suspicion.

The fix correctly avoids recording a file when `persist_noclobber` loses an initial creation race. It does not preserve file identity after successful creation. These are the relevant unchanged production statements (S5-S7):

```rust
file.persist_noclobber(&path).map_err(|e| e.error)?;
created.push(path);
```

```rust
super::tenants::recovery_import(directory, &c.tenants, &mut created)?;
super::users::verify_rekeyed(directory, fresh_admin)?;
```

```rust
Err(error) => {
    for path in &created {
        let _ = std::fs::remove_file(path);
    }
    return Err(error);
}
```

`created` contains pathnames, not a protected namespace or identities. If A creates `users.json`, B replaces that file, and A later fails, A unlinks B's file. There is substantial work between recording and rollback: tenant persistence/load and account verification. The issue is not a tiny authorization/write window.

**Executed reproduction, using a valid replacement store:**

1. In an external test copy, add `server::recovery_bundle::tests::a_concurrent_writer_replacement_survives_failed_import_without_new_failpoints` to the existing test module.
2. Use the existing `sample()` and `sealed()` helpers. First successfully import the sample bundle into a separate temporary directory with a different fresh-admin username. Retain the resulting valid `users.json` and its bytes. This store has passed the normal import verification.
3. Begin import A into another empty directory, using the usual fresh-admin identity. Install only HEAD's existing `users::REKEY_BEFORE_PERSIST` test hook. That hook starts writer B, waits for B's readiness message, and returns so A can continue.
4. B waits until A's `users.json` exists, then uses `std::fs::rename(source, target)` to atomically replace it with B's already-valid account store. No new fault hook is needed; production import, tenant persistence, and cleanup logic remain unchanged.
5. A reaches `verify_rekeyed`, observes a valid store whose fresh admin does not match A's requested admin, and returns `the rekeyed account store failed verification`. Its error cleanup then deletes B's replacement.
6. Join B. Assert that the import failed and that `users.json` still contains B's retained bytes. The preservation assertion fails because the file is absent.

Critical fixture scheduling code actually executed:

```rust
let target = d.join("users.json");
let (ready_tx, ready_rx) = std::sync::mpsc::channel();
let writer = std::thread::spawn(move || {
    ready_tx.send(()).unwrap();
    let deadline = std::time::Instant::now()
        + std::time::Duration::from_secs(5);
    while !target.exists() {
        assert!(std::time::Instant::now() < deadline);
        std::hint::spin_loop();
    }
    std::fs::rename(source, target).unwrap();
});
ready_rx.recv().unwrap();
```

The fixture permitted up to 32 scheduling attempts, but the defect occurred on **attempt 0**. Actual output:

```text
attempt=0; import error=the rekeyed account store failed verification
assertion `left == right` failed:
rollback deleted writer B's atomic replacement using HEAD's existing hook
  left: None
test result: FAILED. 0 passed; 1 failed; 0 ignored
```

The expected right-hand value was the retained valid store; its account/password-hash bytes are intentionally omitted from this report.

For this final reproduction, `git diff --no-index` comparisons confirmed the external copy's entire `users.rs`, `tenants.rs`, and `cloud_backup.rs` were byte-for-byte identical to HEAD. `recovery_bundle.rs` differed only by added tests; there was no production import-body mutation. Another temporary test in `backup_policy.rs` was unrelated to this exact test.

An earlier deterministic fixture also paused immediately after successful user persistence using an added test-only hook, let another thread replace users and create a colliding tenant store, and observed rollback delete the replacement users file while preserving the never-owned tenant file. That instrumented fixture is supporting evidence, not the basis for claiming the final no-new-failpoint reproduction.

**Impact and severity rationale:** irreversible deletion of a different writer's account store, violating the explicit ownership contract. This requires another writer with directory write access during offline recovery; no remote privilege escalation is claimed. Severity is High for data loss under the stated concurrent-writer contract.

**Suggested fix / trade-off:** hold exclusive ownership of the target directory across creation, verification, and rollback, with every supported writer participating in that ownership protocol. If arbitrary namespace writers must be tolerated, pathname-only rollback is insufficient: use an unpublished private staging namespace and atomic no-clobber publication of the completed result, or a platform-specific mechanism that deletes the exact owned file object. Merely checking metadata immediately before `remove_file` introduces another check/unlink race. A namespace redesign may require accepting a new absent destination rather than an already-existing empty directory; that is an explicit UX trade-off, not something this report silently assumes.

**Regression test:** retain the valid-store writer test above, preferably with a dedicated deterministic scheduling barrier after persistence. Assert a failed import preserves B's exact bytes, not just that the path exists. Cover replacement of each owned store and a failure after that replacement.

## E. Static inspection, limitations, and recommendations

### Fenced publication inspection

S1 checks the same `Loaded::fenced` flag set under the state mutex by expired shutdown. S2 creates `let authorize = || self.authorized();`, rechecks after the connector, passes that callback to older-pending settlement, and passes it again to fresh publication.

S3 checks before the initial staging write. S4 checks in the retry loop before each publication CAS:

```rust
let bytes = encode(&next)?;
authorize()?;
match self.meta.put(&key, &bytes, Cond::Match(&etag)) {
    Ok(_) => return Ok(Publication::Published(next)),
    Err(StoreError::Conflict | StoreError::Unknown(_) | StoreError::NotFound) => {}
    Err(e) => return Err(e.into()),
}
```

That loop is shared by fresh publication and `resolve_pending`. Inspection found no alternate commit put in these two publication paths that bypasses it. The added post-connector blocking-read test also exercised it with a genuinely expired shutdown fence and a successor runtime. This supports the limited implementation verdict for NEW-FW3-01; it is not a proof over all interleavings.

### Recovery ownership inspection

Both helpers record their store only after successful no-clobber persistence, and tenant-local removal is absent at HEAD. Existing tests meaningfully cover the initial losing-creator cases and an injected post-user-persist sync failure. However, S5 subsequently removes by pathname without maintaining exclusive namespace ownership. S11 also shows that normal user-store persistence is an atomic pathname replacement, so replacement is not an alien filesystem operation.

Priority recommendation: address F1's ownership model, then retain F2 and F3's focused tests as independent regression guards. Do not equate adding the tests with fixing F1.
