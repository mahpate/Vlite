### 2.3 Environment cores: Consumption versus workload profiles

**Numeric defaults and numeric maximums for either environment type: not documented. Adjustable: yes for the listed Consumption, general-purpose, and memory-optimized core quotas.**

Q, https://learn.microsoft.com/en-us/azure/container-apps/quotas#basic-quotas, gives these exact table rows:

> Managed Environment Consumption Cores | One managed environment | Submit a managed environment quota request | Portal or CLI | The maximum number of consumption cores allocated to the environment. This value is the sum of cores requested by each active replica across all apps in the environment.

> Managed Environment General Purpose Cores | One managed environment | Submit a managed environment quota request | Portal or CLI | The total cores available to all general purpose (D-series) profiles within an environment.

> Managed Environment Memory Optimized Cores | One managed environment | Submit a managed environment quota request | Portal or CLI | The total cores available to all memory optimized (E-series) profiles within an environment.

QR, https://learn.microsoft.com/en-us/azure/container-apps/quota-requests#managed-environment-quota-requests, adds:

> Managed environment memory optimized cores are available only for workload profiles environments, not consumption-only environments.

**Accounting distinction:** Consumption core quota explicitly sums requested cores of active replicas, not configured `maxReplicas` and not observed CPU utilization. A running idle replica still contributes its requested cores. There is no separate exact sentence saying "scale-to-zero replicas do not count"; that conclusion follows from zero running replicas and the active-replica sum, not from billing rules.

R, https://learn.microsoft.com/en-us/azure/container-apps/revisions#running-status, defines:

> Scale to 0 | Zero running replicas, and not provisioning any new replicas. The container app can create new replicas if scale rules are triggered.

Thus a revision actually at zero running replicas contributes zero **replica-requested Consumption cores**. Its app resource still exists; zero replicas do not imply exemption from an unknown app-count limit. Treatment of provisioning/transitional replicas is not detailed by the quoted definition, so reserve rollout headroom.

Do not apply the Consumption active-replica formula to Dedicated profile quotas as if those were identical: Q defines Dedicated core pools by profile family, while W describes per-node allocation and runtime reservations. HA templates select `WorkloadProfileName=Consumption`; they consume the Consumption quota even though the required environment is a workload-profiles environment.

## 3. Tenant-capacity computation

### 3.1 Actual topology and missing inputs

Use the requested architecture: **one shared gateway app**, plus **one writer app and one reader app per dedicated tenant** in the same environment. "One reader" here means one reader **app**, which can have multiple replicas. This is a capacity model, not proof the current per-deployment scaffolding provisions a shared multi-tenant gateway automatically.

The templates require, rather than default, CPU and scale inputs:

| Role | CPU per replica | Configured minimum replicas | Configured maximum replicas |
|---|---|---|---|
| Shared gateway | `g` in {0.25,0.5,0.75,1,1.25,1.5,1.75,2} | `Gmin` in 2..1000 | `Gmax` in Gmin..1000 |
| Writer per tenant | `w` in the same set | 1 | 1 |
| Reader app per tenant | `r` in the same set | `Rmin` in 1..1000 | `Rmax` in Rmin..1000 |

Memory is `2*g`, `2*w`, or `2*r` GiB per replica. These are allowed choices, **not selected production sizes**. `parameters.example.json` does not resolve them.

Let:

- `A` = actual applicable total app-count allowance, **UNVERIFIED / not documented**.
- `C` = actual environment Consumption-core quota, **UNVERIFIED / not documented**.
- `N` = number of identically sized dedicated tenants.

Assume no unrelated apps, jobs, or core consumers; one steady-state active revision per app; no rollout/maintenance overlap; and no other tighter quota/network/storage constraint.

Then:

```text
apps(N)       = 1 + 2*N
cores_min(N)  = g*Gmin + N*(w + r*Rmin)
cores_max(N)  = g*Gmax + N*(w + r*Rmax)

N_apps = floor((A - 1)/2)
N_min  = min(N_apps, floor((C - g*Gmin)/(w + r*Rmin)))
N_max  = min(N_apps, floor((C - g*Gmax)/(w + r*Rmax)))
```

`N_min` is the minimum-replica fit, **not** assurance all tenants can scale to maximum. `N_max` is the simultaneous configured-maximum fit. A negative result means even the gateway configuration cannot fit that core allowance; it must not be clamped to a misleading "successful zero-tenant deployment." A result of zero means no dedicated tenant fits.

For heterogeneous tenants, replace `N*(w+r*R)` with a sum over tenants.

### 3.2 Numeric coefficients established from template bounds

At the **smallest accepted resource sizes and minimum replica choices**, `g=w=r=0.25`, `Gmin=2`, `Rmin=1`:

```text
apps(N)      = 1 + 2*N
replicas(N)  = 2 + 2*N
cores_min(N) = 0.5 + 0.5*N
N_min        = min(floor((A-1)/2), floor(2*C-1))
```

This is the densest permitted **sizing scenario**, not a recommended or configured default. At the same replica counts but the largest accepted role sizes (2 vCPU), demand is `4 + 4*N` cores.

If gateway and reader maxima are each **configured to the permitted ceiling 1000**, while CPU remains at the smallest 0.25-vCPU choice:

```text
cores_max(N) = 250 + 250.25*N
N_max        = min(floor((A-1)/2), floor((C-250)/250.25))
```

At 2-vCPU sizes and those 1000-replica settings, demand becomes `2000 + 2002*N` cores. These illustrate why the per-revision ceiling is not a capacity reservation or a usable default. Configured maxima may instead equal their minima, in which case the corresponding min/max formulas agree.

**Requested maximum tenant count: UNVERIFIED at both minimum and maximum replicas.** No numeric `A` or `C` is published in the allowed current sources, and the repository does not select `g/w/r/Gmin/Gmax/Rmin/Rmax`. Reporting a specific tenant number would invent inputs. The equations above are the computable outcome supported by the evidence.

### 3.3 Headroom and operational trade-offs

R, https://learn.microsoft.com/en-us/azure/container-apps/revisions#zero-downtime-deployment:

> The existing active revision isn't deactivated until the new revision is ready.

S, https://learn.microsoft.com/en-us/azure/container-apps/scale-app#scale-definition:

> During platform upgrades or maintenance, you might temporarily see more replicas than expected.

Therefore the exact-fit formulas are **steady-state upper bounds, not safe production admission limits**. Subtract other consumers and explicit measured rollout/maintenance reserve from `C`. Revisions in Single mode can overlap; configured writer min=max=1 is not fencing. The HA README's explicit writer stop/handoff process remains necessary and is not qualified by quota research. Gateway/reader rollout overlap still needs headroom.

Dedicated tenant isolation trades linear app/core/storage growth for isolation. Shared-pool tenants can reduce per-tenant overhead, but selecting that trade-off or changing sizes is outside this task. A separate environment can distribute load/isolation only if environment-count quota, regional capacity, subnet capacity, and operational constraints allow it.

## 4. Default single-ACA deployment impact

**Static conclusion: no newly identified structural incompatibility for the default singleton; no source or deployment change is needed from this research. An unconditional "no quota impact" against a real subscription is not verified.**

The default template requests one app, one steady-state replica, **1 vCPU / 2 GiB**, and a 60-second termination grace. The init container requests **0.25 vCPU / 0.5 GiB**. Both pairs appear in C's table; even the arithmetic sum, 1.25 vCPU / 2.5 GiB, is a documented pair. This observation does not assert how the service accounts sequential init/main execution against quota.

Its single steady-state replica is well below the documented 1000-replica configurable ceiling. It does not introduce dedicated writer+reader apps per tenant, and the script creates at most one environment if the named environment is absent. HA scaffolding is opt-in and does not change this singleton.

However:

- An exhausted environment-count or Consumption-core quota can still affect a singleton. Actual usage and grants were intentionally not queried.
- No published apps-per-environment number is available to compare against one app; unknown does not mean unlimited.
- Sixty seconds is consistent with the nonnegative template-field contract, but neither a platform maximum nor live acceptance was established.
- Nondefault CPU options and storage durability qualification are not certified by the default-case conclusion.

Thus the task's expected "no" is supported only as **no additional HA-induced limit conflict for the default configuration**, not as a real-subscription capacity guarantee.
