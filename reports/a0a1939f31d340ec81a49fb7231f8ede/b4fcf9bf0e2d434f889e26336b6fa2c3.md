# VLite HA signing-key delivery: ACA and Key Vault evidence

**Status: INCOMPLETE for platform validation; documentation research completed.**

Research date: 2026-11-17 UTC (2026-11-16 Pacific). Only public Microsoft Learn pages were fetched. No Azure account, resource, secret, deployment, runtime measurement, or newer HA implementation was accessed. The supplied architecture is an assumption, not a reviewed implementation: gateways sign principal envelopes; backends verify audience, expiry, tenant, and policy generation; replicas roll independently without sticky sessions. Current injected test keys do not establish platform readiness.

## Conclusion

Use **version-pinned Key Vault secret references, immutable ACA secret names per delivery generation, and startup-loaded, role-specific key bundles containing explicit key IDs**. Put the gateway's active signing-key ID in the same versioned bundle as its signing material. First distribute old/new verification overlap to every backend, then roll gateway bundles to the new active ID, then retire the old key only after old signing has stopped and its maximum envelope acceptance window has elapsed.

Do not use a versionless reference as an atomic fleet-wide active-key switch. Microsoft documents retrieval within 30 minutes and automatic restart of active revisions using the secret in environment variables, not coordinated backend/gateway cutover, a completed-rollout deadline, or application-level key retirement. A real, separately authorized non-production drill remains a release gate.

An app-scoped secret is not an environment-wide secret and is not captured immutably with a revision. |

| Versionless reference | S1 supports the URI without a version and states: "the app automatically retrieves the latest version within 30 minutes." ## 2. Identity, permissions, and network prerequisites

- **Reference identity:** ACA must have a system-assigned or user-assigned managed identity, and the secret reference must select it. S1 shows `identity: "system"` or the user-assigned identity's **resource ID**. An attached identity without Key Vault authorization is insufficient. [S1, Reference secret from Key Vault; S2, Configure a target resource]
- **Recommended authorization:** Use an RBAC-enabled vault and grant the selected identity **Key Vault Secrets User**, scoped to the intended secrets/vault. This reads secret contents; Key Vault Reader cannot read sensitive values, and Key Vault Contributor is control-plane only. The runtime identity does not need permission to set/delete secrets, grant roles, or administer the vault. Separate the rotation publisher/operator from the consuming identity. [S1; S4, built-in roles]
- **Legacy policy alternative:** Key Vault also supports legacy access policies. A secret GET requires `secrets/get`; `list` is a distinct permission, not a substitute. Prefer the RBAC path explicitly recommended for ACA rather than assuming a role assignment authorizes a vault configured for legacy policies. Switching permission models can invalidate existing access-policy permissions and cause outages. [S4; S5; S7, Secret access control]
- **Identity lifecycle:** System-assigned identity is tied to the app; user-assigned identity is independent and can be pre-authorized. S1 notes system-assigned identity cannot be used with the documented app `create` command because it does not exist until the app exists. A pre-authorized user-assigned identity avoids that bootstrap ordering, but sharing one unnecessarily broadens exposure. Prefer separate gateway/backend identities and access boundaries. [S1; S2]
- **Platform-only identity use:** S2 documents identity lifecycle `None` for an identity used only by platform features including Key Vault secrets, without exposing its tokens to container code. Consider this for the reference-resolver identity if the selected API/environment supports it; verify it in the drill. It does not conceal secret material intentionally injected into the container. Direct SDK retrieval, if later chosen, instead needs container identity availability and explicit user-assigned client-ID selection. [S2, Control managed identity availability; Connect to Azure services in app code]
- **Propagation is not instantaneous:** Identity changes do not automatically restart the app or create a revision. S2 warns managed-identity backend services cache per resource URI for around 24 hours, permissions can be outdated until token expiry, and forced refresh is unsupported. This is a warning against assuming instant permission changes, not a measured ACA Key Vault secret revocation SLA. [S2]
- **Network authorization is separate:** Valid identity/RBAC does not establish DNS, routing, firewall, private-endpoint, or network-perimeter reachability. Key Vault's trusted-services exception is not blanket approval for all Azure services or scenarios. S1 specifically calls out allowing `AzureKeyVault` and `login.microsoft.com` when using its UDR/Azure Firewall scenario. Verify the actual chosen network path without weakening the vault to make a test pass. [S1; S6]
- **Operator exposure:** S1 warns ACA `listSecrets` operations return plaintext and some operator/contributor roles include them through wildcards. Restrict who can read secrets or deploy containers/configuration that consumes them. Do not collect secret values in drill evidence, logs, command histories, diagnostics dumps, or Blob control-state snapshots. [S1, Permissions for managing secrets; final constraints are application recommendations]

## 3. Recommended explicit-key-ID scheme

This section is a **suggested application/deployment protocol, not an Azure guarantee**, and does not prescribe a change to the already-selected signing algorithm.

Use a small validated bundle with a schema version, delivery generation, and an allowlisted map from unique `kid` to verification material. The gateway bundle additionally contains the explicit `activeKid` and corresponding signing material. A role-specific backend bundle contains only verification material when the selected algorithm permits that separation. With a symmetric MAC, verification material can also forge signatures; recognize that trust trade-off rather than describing it as public verification. Never distribute asymmetric private keys to backends.

Store bundle bytes only as Key Vault secrets; expose each through an ACA secret definition referencing an exact Key Vault version. Bind one secret-backed environment variable per container role to an immutable ACA name such as `principal-keys-g003`. Startup parses/validates the bundle and publishes only safe metadata (generation, active/accepted IDs, revision/replica identifiers, readiness); never bundle contents. An immutable generation name means the operator does not later retarget that same ACA name to different bytes. This is an operating constraint, not an ACA-enforced immutability feature.

Keep old generation definitions while an allowed rollback revision references them. Deploy a new revision to change the binding and active signing ID together; do not independently update `activeKid` and key bytes through asynchronously refreshed references. This avoids application SDK polling, file watchers, multi-file consistency, and an uncoordinated mutable active-key pointer. Environment delivery trades hot reload for deterministic startup/revision behavior and requires protecting process diagnostics. Volume delivery could avoid an environment variable but still needs a defined load/restart protocol and additional verification; no hot-reload benefit is established by the fetched documentation.

Every envelope must carry a bounded, authenticated `kid` (covered by the signature/MAC), with a fixed allowed algorithm and local allowlist lookup. Reject unknown/retired IDs; never use an envelope-controlled ID as an arbitrary Key Vault URI or fall back to another key, unsigned identity, or local test key. Validate signature, audience, tenant, expiry, issuance-time/lifetime constraints, and current policy generation before authorizing. Key generation and policy generation are distinct.

Missing/malformed material, duplicate IDs, wrong algorithm/key shape, or an active ID absent from signing material must fail startup/readiness explicitly. Existing replicas may continue only with an explicitly approved still-valid generation; a failed refresh must not silently advertise the target generation as installed. Keep all test-key modes explicitly non-production.

## 4. Safe staged rotation and retirement

All steps below are **application protocol recommendations**. ACA does not supply these cross-app barriers.

1. **Define bounds before rollout.** Set maximum envelope lifetime `L`, a conservative combined clock/acceptance uncertainty budget `S`, and any bounded authorization/in-flight allowance `D`. Enforce lifetime at both issuer and verifier, including rejection of unjustifiably future issuance times; expiry checking alone does not prove a maximum lifetime. Establish a rotation timeout/deadline and rollback-compatible generations. Do not choose numeric values without the workstream's requirements.
2. **Prepare the new key.** Assign a never-reused new ID `B` while `A` remains active. Publish pinned old/new verification bundles and the future gateway bundle through the authorized secret-publishing mechanism. No material goes into Blob control-state snapshots or logs.
3. **Expand verification first.** Roll all backend instances that can receive traffic to accept `A` and `B`. Gate on actual startup-loaded generation/accepted-ID evidence and authenticated synthetic checks, not just resource provisioning or elapsed time. Cover every backend app, active revision, direct revision route, region if applicable, and scale-out template. Deactivate or otherwise fence incompatible revisions from traffic/reactivation.
4. **Switch issuance second.** Only after that barrier, roll gateways to a bundle with `activeKid=B`. Old gateways may still issue `A`; both must verify at every reachable backend. No sticky sessions are needed or assumed. Abort/pause if convergence is not established by the deployment deadline; a timer does not make an unobserved replica safe.
5. **Establish the final old-issuance bound.** Stop/drain/fence every `A` signer, including old revisions, queued work/retries capable of fresh signing, and reactivation/scale-out paths. Record conservative `Tstop`, the latest possible `A` issuance time. A last-seen log event is not proof that all old signers stopped. If this cannot be proven, a separately enforced signing cutoff/lease mechanism is needed before retirement; that is extra application work, not an ACA feature assumed here.
6. **Retire verification only after the drain window.** Do not remove `A` before `Tstop + L + S + D`, and only once `B` convergence and rollback restrictions hold. `S` must cover the complete issuer/verifier clock tolerance, not just one clock; `D` applies if authorization/in-flight semantics require it. Retries must not indefinitely renew `A` envelopes. If the bound or clock-health premise is unknown, retirement is blocked.
7. **Remove old consumption, then disable access/material.** Roll verifiers to `B` only, remove old signing material from gateways, and verify rejection of `A`. Before deleting an ACA secret, S1 says deploy revisions that no longer reference it and deactivate referencing revisions. Preserve only explicitly authorized recovery material in Key Vault under retention/access controls; never rely on old app snapshots. Disable the retired version according to the approved recovery plan; do not assume Key Vault expiry removes copies already loaded into processes.

**Convergence trade-off:** S1's 30-minute versionless retrieval statement is not the bound for this protocol and must not be substituted for an acceptance barrier. Pinned revisions converge when observed healthy consumers have the intended generation; stalled convergence blocks rotation. There is no finite safe retirement timer while an unfenced old signer can keep minting envelopes.

**Rollback:** Before retirement, roll back only to a gateway/backend generation compatible with every currently issued key. If a rollback gateway resumes signing `A`, reset `Tstop` and the retirement window. After `A` is retired or compromised, do not reactivate an `A`-only revision; roll forward a compatible configuration instead. Keeping immutable secret generation names helps bind rollback intent but does not restore a disabled Key Vault version or permissions. [Application recommendation informed by S1/S3]

|---|---|---|
| Access revoked, identity removed, RBAC propagation | S1 lists identity/authentication/RBAC errors. S2 documents permission caching and no automatic restart for identity changes. No fetched source promises immediate zeroization of delivered material or a specific running-replica fate/retry cadence. | Block new generation activation when delivery fails; report sanitized errors. Test warm replicas, cold starts, scale-out, and restart independently after access removal, then recovery. Do not assume one version can be individually deleted without checking the supported operation. |

| Stale process environment/key cache | Secret-definition updates alone need not affect existing revisions; documented versionless env consumers restart. | Compromised old signing key | No platform delivery feature makes already-issued forged envelopes distinguishable from legitimate ones. | Emergency ID denial/policy fencing may intentionally reject unexpired legitimate envelopes; do not wait normal overlap if compromise requires immediate application rejection.
