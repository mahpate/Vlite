### 2. MEDIUM - An unconfirmed successful checkpoint is never reconciled into recovery-point status (confidence 10/10)

**Changed evidence:** `src/server/backup_policy.rs:1315-1322` updates checkpoint sequence/time only from a newly returned checkpoint, then clears `last_error`; `:1429-1434` returns `checkpoint: null` when the remotely committed index already covers the live head. `src/server/cloud_backup/archive.rs:381-389` can commit the index but fail to observe that outcome.

**Executed reproduction:** With a matching historical preimage plus the patch, inject an applied-but-unknown index PUT and an unavailable confirmation GET. Reopen the runtime and retry without new writes. The retry succeeds with one indexed checkpoint, but status reports `baseline_checkpoints: 1`, `checkpoints: 0`, `last_checkpoint_sequence: null`, `last_checkpoint_unix_ms: null`, and `last_error: null`. A crash between remote publication and local status persistence has the same reconciliation gap.

**Impact:** The advertised recovery-point monitoring (`docs/DOCKER-OPERATIONS.md:526-528,570-574`) can indefinitely omit the latest recoverable sequence/time if no more writes occur. Stored data remains recoverable; status and success accounting are wrong.

**Remediation:** Reconcile the verified index tip into status on every successful open, including idle retries. Track publication identities if counters/audit events must be recovered exactly once. Add the failed-confirmation-plus-restart case; the existing test only confirms an ambiguous PUT immediately.

### 3. MEDIUM - Saving the snapshot's dashboard policy silently disables archiving (confidence 10/10; already fixed in pinned base)

**Impact:** An ordinary dashboard save unexpectedly changes continuous recovery to snapshot-only.

**Remediation:** Preserve the previous archive object when no archive controls are exposed, and test policy round-tripping. **Keep the pinned base's existing fix at `src/dashboard/admin-tools.js:556-557`; this is a snapshot defect, not an outstanding defect in that base.**

### 4. LOW - The published OpenAPI contract rejects the newly documented policy field (confidence 10/10)

### 5. LOW - The documented hard 64 MiB segment limit is actually a soft cut (confidence 10/10)

**Changed evidence:** `src/server/cloud_backup/archive.rs:297-302` rejects only an export that stops before the live head; `:320-325` checks the cumulative 1 GiB limit, not a per-segment byte limit. `docs/DOCKER-OPERATIONS.md:535-536,580-581` instead promises refusal above 64 MiB and a segment of at most that size.

The exporter appends whole commits before checking its byte threshold (`src/logops.rs:397-403` in the matching historical tree). **Executed reproduction:** Write 64 one-MiB payloads after a baseline. Archiving succeeds and publishes a **67,113,076-byte** segment, exceeding **67,108,864 bytes**.

**Impact:** The documented resource/error boundary is false; the final whole commit and serialization overhead can exceed it. This reproduction did not establish data loss.

**Remediation:** Either enforce the intended byte cap before upload and return `pitr_delta_too_large`, or explicitly document the soft whole-commit bound and memory headroom. Add below/at/above-threshold tests and define whether the limit covers frames or serialized objects.
