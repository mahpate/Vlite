# MEAS-005 remaining clock-calibration and polling prerequisites

**Status: INCOMPLETE for ACA timing validation; research and implementation report delivered.** No live Azure operation, authentication, deployment, mutation, or qualification was performed. The existing local checks listed below do not establish ACA clock precision or MEAS-005 success.

Inspected baseline: `467f54d47b1e4087ebe70bc5431bca379fa1acc4`, initially clean. Scope is MEAS-005 clock collection, calibration, fixed-process coverage, and configurable polling. MEAS-004 image-build fixes and MEAS-006 investigations are deliberately excluded. Only this report is changed.

## Executive finding

There are two independent blockers, not a failed timing measurement:

1. The harness never samples or calibrates clocks. It deliberately omits analyzer clock fields and unconditionally records `ClockCalibrationUnavailable`.
2. The fixture-preparation plan drops polling/revocation settings, while the mutator independently hardcodes 1000 ms and a 30000 ms observation deadline. Consequently, the documented 100 ms / 1000 ms-deadline pilot and fresh-trial polling sweep cannot be generated.

Polling can be fixed without Rust serving changes. Replica clock collection can reuse the existing native clock operation, but **sampling the four observers is insufficient**: offsets must be relative to the actual mutator, currently an ACA job. Public CLI/API evidence supports replica-specific app exec; it does not establish equivalent exec support for the job. Do not substitute the Linux operator's clock for the job's clock.

The smallest dependable end-to-end design using established app-console capabilities is a **MEAS-005-only, fixed single-replica driver app**, with the existing driver identity/projection and exactly one explicitly initiated mutation command. This changes execution topology, not native evidence schemas, serving policy, or retry semantics. It must be documented as a proposal-only contract adjustment, not silently treated as the existing job contract. If the job topology must remain exact, mutator clock access/calibration is a genuine unresolved prerequisite and timing must remain incomplete.

### Effective settings and sweep

Use pilot defaults: poll 100, revocations 1, mutations 3, deadline 1000, observer sampling 50 ms. The existing 1200 s observer duration is permissible: the contract says **at least** 20 s, not exactly 20 s. Do not shorten it to 20 s while ignoring bounded native command execution.

For full mode retain mutations 20, revocations 10, deadline 30000, and the current bounded observer configuration. Accept `GatewayPollMs` from 1..5000, with proposed full default 1000; generate each documented sweep point as a separate explicit invocation with a fresh run ID, resource group, fixture, credentials, and evidence directory. No in-place polling changes, shared sacrificial credentials, automatic interval search, or automatic re-execution after unknown writes.

The native mutator checks `N * (deadline + poll + 138000) <= 3540000` (`benchmarks\ha_meas005.rs:133-150`). At pilot defaults this bound is 417300 ms; at full poll 5000 it is 3460000 ms. Observer clocks/calibration, staggered app starts, setup, and report transport consume additional time. A 3540 s full observer window leaves only 80 s versus that largest driver bound **before setup**. Therefore preflight must refuse a run whose conservative remaining observer/credential lifetime cannot cover the configured driver bound and post-calibration. Do not infer sufficient coverage from the job's 3600 s timeout or `readyAt`.

Keep the 2-hour credential expiry, 120 s margin, and no-retry controls (`measure-gateway.ps1:19-21,776-809`). Record a static insufficient-window reason rather than silently extending credential expiry, observer bounds, or observation deadlines.

## Smallest trustworthy collection and calibration design

### 1. Reuse native output; do not build another clock service

Add `cfg-clock` to **each role's own** configuration-secret projection:

```json
{"operation":"clock","role":"ROLE","work_dir":"/measurement","source_revision":"SOURCE","source_dirty_paths":"DIRTY"}
```

These are public settings, not additional credentials. Retain the role bundle allowlists in `measure-gateway.ps1:12-17` and `measure-gateway-entrypoint.py:120-128`. Writer/reader must never receive signing seeds, driver admin files, sacrificial credentials, or the driver's identity. The clock command needs neither control-state publication nor a control read.

Address each invocation with explicit app, revision, replica, and container. Retain a collector-side companion receipt containing phase (`before`/`after`), invocation ID, bound inventory identity, source, collector UTC and monotonic send/receive times, raw clock-report digest, and validated clock report. Do not add those keys to the native `vlite-meas005-clock/1` object: its top-level allowlist is strict. Keep console tokens, endpoints, subscriptions, private configs, and native diagnostics out of receipts/evidence.

### 2. Bound the console adapter independently

Do not send `exec` through the ordinary `Invoke-VLiteMeasAz` JSON parser (`measure.ps1:371-384`), which expects completed JSON commands and has no process deadline.

Recommended minimal CLI adapter: a small **host-only** Linux Python-standard-library PTY/process wrapper around the installed `az containerapp exec`, called from PowerShell. A real PTY supplies stdin for the CLI's terminal requirement; capture CLI stdout and stderr separately, keep stderr private/discarded, and expose only a verified complete frame plus static outcome. This requires no pip/npm package. Keep this adapter separate from the runtime entrypoint's explicit "no Azure operations" promise.

Use a fixed command invoking `python3 /usr/local/bin/measure-gateway-entrypoint.py --config /measurement/in/cfg-clock`, not an interactive shell conversation or an echoed inline secret. Bracket the **entire** adapter invocation locally, including CLI startup, identity/token retrieval, connection setup, remote execution, and frame reception. A 30 s per-clock hard timeout with one attempt per phase/identity is a reasonable collection budget, not a precision promise. Close/reap only the adapter's own process tree on timeout.

Because CLI output merges remote console channels, clock transport must accept only complete ASCII framing, reject `FAILED`, duplicates, unexpected payloads, invalid JSON and semantic clock errors, and never claim it retained separated native stdout/stderr. For clock samples all remote errors are already static. Do not rely on CLI exit 0 to establish native exit 0. Validate a complete successful clock frame and clean adapter completion. A transport timeout or disconnect invalidates that sample even if a partial frame exists.

Alternative: PowerShell's existing .NET `ClientWebSocket` can separate protocol channels without a PTY or new package. It avoids CLI terminal handling but requires maintaining Azure's console protocol/token/endpoint handling, much of which is demonstrated by CLI source rather than a stable batch-exec contract. Prefer the bounded CLI adapter unless a dedicated, version-tested protocol adapter is intentionally accepted. Never install a WebSocket package to solve this.

### 3. Calibrate the actual mutator, not just observers

**Current job fallback:** implement observer receipts, but leave analyzer clock fields null and retain `ClockCalibrationUnavailable` if the mutator cannot be sampled. A separate clock job, a publish job, ingress RTT, HTTP Date, assumed NTP synchronization, or operator `clock_offset_ms:0` is not evidence for the mutating job's host.

**Recommended complete topology:** introduce a proposal-only MEAS-005 driver app with one fixed replica/container, the same resources, driver-only identity, and projection. No external ingress or clock HTTP listener is required. Its bounded launcher restores files and idles; it must not automatically mutate on startup/restart. Inventory this driver along with the serving set. Then:

1. Confirm all four serving processes and the driver identity are stable and ready as applicable.
2. Collect before clock samples on all five selected containers.
3. Execute exactly one existing `operation:"mutate"` against the selected driver container. Retain the create-only mutation-attempt marker. Persist the validated native mutation report and native status in private driver files before transport; add a bounded, create-new evidence sink to the wrapper rather than changing the native JSON shape.
4. Collect after clock samples on those same containers immediately after the driver finishes, before observer coverage ends. Also collect terminal observer reports and final inventory.
5. Use existing `operation:"transport"` for read-only re-export of persisted evidence if a console disconnect loses delivery. **Never repeat mutate** to recover a report. Any unknown write outcome remains unknown_do_not_retry.

For the new driver app, preserve an outer <=3600 s operation timeout and the native command budgets, one explicitly initiated command, zero retries, and finally cleanup. This adds no external service or credential system: it uses the already selected ACA environment, role-specific ACA secrets, managed identity, and native mutation binary. Nevertheless, it is larger than polling-only wiring. If topology cannot change, request a documented, authorized way to calibrate the existing job clock; do not guess an undocumented jobs exec URL.

### 4. Conservative offset math

Let collector UTC bracket be `[s,t]` and the native remote UTC bracket be `[r0,r1]`. An intentionally conservative interval for remote UTC minus collector UTC is:

```text
remote_minus_collector = [r0 - t - q, r1 - s + q]
```

`q` must include outward timestamp quantization and justified clock motion during the invocation. With integer-ms timestamps from both sides, allow at least 2 ms for independent truncation before adding justified drift/clock error. Record local monotonic duration and reject backward UTC, negative elapsed, excessive wall/monotonic disagreement, or missing finite timestamps. Do not subtract startup/log/exec latency from RTT to manufacture narrow bounds.

For observer interval `[Ol,Ou]` and actual mutator interval `[Ml,Mu]` relative to the same collector/reference window:

```text
observer_minus_mutator = [Ol - Mu, Ou - Ml]
```

Compose **both** remote-command uncertainty intervals and collector reference-clock evolution between them. Before and after observations must bracket the mutation window. Form a conservative enclosing hull of the composed pre/post intervals, then expand for justified motion across the run. Do not average away disagreement or intersect pre/post intervals merely to narrow uncertainty.

Convert only a defensible final `[L,U]` to the existing analyzer inputs:

```text
clock_offset_ms = (L + U) / 2
clock_uncertainty_ms = (U - L) / 2
```

Reject nonfinite values, reversed bounds, or uncertainty above 60000; represent unavailable calibration with **both fields null**. Wide but defensible bounds may still miss the existing deadline and must remain incomplete. Never clamp them to 60000 or shrink the bound until a run passes.

### 5. Drift and stale evidence are real prerequisites

Pre/post agreement alone does not bound a clock excursion that occurs and reverses between samples. The observer already records max UTC-versus-monotonic deviation throughout its polling loop (`benchmarks\ha_meas005.rs:481-506`); analyzer adds this deviation and 10 ms mutator allowance (`:651-655`) and refuses observer jumps above 10 ms. Keep those rules.

The mutator's command-local wall/monotonic agreement checks do not cover clock changes during jitter, envelope preparation, behavior checks, or idle periods. Therefore a trustworthy collector must have a supported run-wide drift/error bound for the reference and mutator clocks, or retain null calibration. Do not treat the analyzer's 10 ms allowance as a discovered ACA guarantee. If adding run-wide monitoring, keep results in validated companion calibration evidence and refuse unsupported gaps; do not change the native measurement schemas or relax the existing jump criteria.

Receipts must be freshly generated within this trial and bracket its actual mutation window. Clock schema/source alone cannot distinguish old samples from another run of the same revision. Bind samples through fresh invocation context and exact platform container identity, require unique pre/post receipts, and reject out-of-order collection or post observations taken before driver completion. A newly executed targeted command is the freshness mechanism; log timestamps or an old clock file are not.

No public documentation checked establishes the necessary ACA clock-motion bound. That remains a genuine external qualification prerequisite, even after all collection plumbing is implemented.

**Analyzer lifetime gap:** the contract requires the observer lifetime to cover the whole command and observation window (`measure-gateway-contract.md:513-515`). Thus an observer ending after a fast first observation but before `command_end + observation_deadline_ms` can currently have a complete timing sample. Correct this to require conservative lifetime end to cover the declared observation-window end as well as the matching observation. Add a regression fixture ending between those two times. This is a prerequisite correction, not a new timing threshold.

The existing executed analyzer test already illustrates this discrepancy: its fixture ends observers at UTC 2000 (`benchmarks\ha_meas005.rs:818`), the last command ends at 1410 with deadline 1000 (`:798-805`), and analysis is asserted complete (`:835-836`). The required full-window end would be 2410, before adding calibration/drift padding. This is existing fixture evidence, not a live process-lifetime experiment.

Preserve exact generation matching, backend minimum_generation >= target, unknown commit outcomes, null latencies for missing clocks, successful-only distributions, and distinct censoring reasons (`benchmarks\ha_meas005.rs:630-738`). Add malformed/stale/chronology fixtures; native identity/source comparison is not run-ID validation.
