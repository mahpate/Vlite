### Why parked and what remains uncertain

The recorded reason is an **owner pause with unfinished qualification**, not a proven failed approach. The E2 contract is only *provisionally ratified*: it explicitly says ratification is not a release go and nothing is public, activated or wired to a route (`F1:docs/projects/roadmap/gap1-e2-resume-contract.md:3-18`). Main's later handover independently records the lane as parked with pending ES decisions (`main:docs/projects/roadmap/handover-0.7.2.md:91-99`).

Important unfinished work:

- **Independent acceptance remains partial.** The oracle omits TTL/high-water races, content nodes, shared edges, record owners, post-chunk barrier matrix, maintenance relabeling, child/sibling isolation, commit-indeterminate faults and many precedence/decoder probes. The golden additionally lists missing literal byte vectors and digest probes. Its source points at machine-local scratch notes that are not supplied by the retained branch; do not assume those notes are recoverable evidence (`F1:tests/memory_erasure_resume_oracle.py:1-29`; `F1:tests/fixtures/agent_memory/erasure_resume_golden.json:3`).
- **Tests written are not mutants replayed.** Commit `603c8cb` reports only 16 of 41 Rust hand mutants replayed locally, no pool replay, and no accepted independent oracle. Commit `7964c9d` reports that E2-M16 initially survived and was then killed after the whole-window test was strengthened. This is a useful concrete warning against treating named tests or ledger entries as completed qualification.
- **Historical local gates are not current verification.** `7964c9d` reports fmt, strict all-target/all-feature clippy, and default/all-feature library tests, with one timing-sensitive test rerun; it explicitly says integration suites and pool replay were not run. I did not reproduce those Rust gates.
- **Bounded does not imply scalable or complete erasure.** E2 can stall on a high-degree memory; hidden expired memories are not candidates and may leave evidence/content residue. Every chunk may scan memory nodes from other scopes until a scope index or equivalent is decided. E4's orphan discovery is explicitly unsolved: unattached evidence may be legitimate preloaded evidence, so it cannot safely be deleted just because it is unattached (`F1:docs/projects/roadmap/gap1-e2-resume-contract.md:27-41,514-529,596-607`; `F1:docs/projects/roadmap/gap1-e4-reconciliation-contract.md:139-196`).
- **Temporal/facts drafts are not ratifiable.** The temporal banner lists unfinished independent review, consistency/citation checks, schema-snippet validation, B1b/B6/B7 owner decisions and disputed rollback wording. The facts/E3/E4 banners list missing decoders, byte vectors, evidence/receipt designs and stale citations (`F1:docs/projects/roadmap/serving-temporal-contract.md:1,1502-1536`; each companion contract's line 1).

Main already explains it (`main:docs/MEMORY.md:293-297`). No new documentation cherry-pick is needed for that clarification.
4. **Main's 0.7.3 hardening must be preserved.** Read-only exact-scope grants, bounded ordinary receipt reclamation and restart-free existing-binding grant reload are shipped (`main:docs/RELEASE-0.7.3.md:13-59`). Receipt reclamation concerns ordinary remember/forget/consolidate receipt groups, **not** E4's erasure receipts, manifests or orphan evidence; it does not finish E4 (`main:src/memory/reclaim.rs:1-10,30-39`; `F1:docs/projects/roadmap/gap1-e4-reconciliation-contract.md:164-174`).

### Why parked and what main makes stale

Parking is explicitly a design/ratification pause. Decisions D1-D19 cover who can enable memory, aggregate-route restrictions, token lifetime/password requirements, tenant audience, shared writes, stable personal labels, text indexing, state storage and sequencing. The four independent reviews and production-shaped migration rehearsal remain unperformed in the retained evidence (`F4:docs/projects/roadmap/f4-self-serve-memory-contract.md:3,292-310,324-380`; `main:docs/projects/roadmap/handover-0.7.2.md:98-99`).

The draft is based on 0.7.1 (`0eb2bd81`), not 0.7.3. In particular:

- **An immutable registry is no longer the starting point.** F4's finding F1 and proposed replacement registry predate main's live `reserved::Served`, request-lifetime `Pin`, installation under the database lock and drain reporting (`F4:docs/projects/roadmap/f4-self-serve-memory-contract.md:28-29,94-104`; `main:src/server/reserved.rs:242-340`; `main:src/server/memory/reload.rs:116-175`). Reuse the current mechanism; do not introduce a parallel generic registry.
- **F4's in-flight semantics are not interchangeable with main's.** F4 proposes loading the registry at each decision and re-authorizing mutations under lock. Main intentionally pins one grants version for the request and fails a superseded write through the durable binding-generation recheck. Replacing the pin model would be a behavior change, not harmless salvage (`F4:docs/projects/roadmap/f4-self-serve-memory-contract.md:101-104`; `main:src/server/reserved.rs:242-258,297-319`; `main:src/server/memory/routes.rs:297-305`; `main:docs/RELEASE-0.7.3.md:48-54`).
- **Part of “no restart” is already shipped, narrowly.** Main reloads principals, scopes, read scopes and raw-access grants. Initial enable, binding additions/removal/retirement and resource/state/window changes remain restart-only. F4 is broader managed lifecycle, not an alternative implementation of the shipped grants reload (`main:src/server/memory/reload.rs:1-8,178-190`; `main:docs/RELEASE-0.7.3.md:39-59`).
- **H1 sign-in sequencing is stale; restrictions are not lifted.** The memory-mode dashboard sign-in fix already shipped in 0.7.2. Global metrics/import/etc. refusals and the server gRPC/automatic-maintenance refusal remain intentional. F4's recommended admin aggregate exception was only an option, not authorization to remove gates (`main:docs/projects/roadmap/handover-0.7.2.md:18-20,57-64`; `F4:docs/projects/roadmap/f4-self-serve-memory-contract.md:312-322,345-348`; `main:docs/MEMORY.md:493-494`).
- **An intervening approved PRD explicitly rejected this expansion.** The live-grants PRD says parked F4 was context only, excludes self-service, and rejects request-body grants or a second `memory.json` source of truth (`main:docs/projects/feature-memory-live-grants/feature-memory-live-grants.prd.md:46,70-79,257-269,536-543`). That is narrower-scope evidence, not permanent rejection of all F4 product ideas.

### Reusable pieces and bounded recommendation

**Defer implementation; retain evidence only.** Reuse the threat-model/test-scenario inventory, pinned-label/tombstone migration risks, S/R/N crash-state table and export/downgrade rehearsal as inputs to a future separately approved design. None are reviewed contracts. In particular, never infer an orphan from “unattached,” widen `vlk_` credentials to tenant membership, or expose a self-service token without settling the identity and route-confinement model first.

The smallest useful F4 follow-on, if explicitly prioritized later, is a **design-only delta against 0.7.3**: identify an actual unmet user journey after existing grants/preflight work, subtract the shipped live-cell/reload and dashboard fixes, choose one identity/lifecycle slice, and ratify only its decisions and test contract. No new status endpoint/UI or registry work now: those would duplicate the approved ongoing planner.

Trade-offs worth deciding before code: one file source of truth versus managed state with a reconciliation/backup/downgrade burden; explicit reviewed shared grants versus every editor writing a tenant-wide scope; stable readable labels versus opaque account identity; dedicated memory-only tokens versus the existing credential model; text-only managed evidence without dense recall versus broader core/index work. F4 usefully makes these costs visible but resolves none by implementation.
