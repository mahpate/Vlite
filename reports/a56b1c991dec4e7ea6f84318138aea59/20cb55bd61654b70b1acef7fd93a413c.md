## Summary

The normal Windows restore publishes a complete rekeyed output, refuses an initially existing empty output, and preserves output while reporting an unreleased pin. Import rejects pre-existing entries and disables imported accounts. Targeted atomic-state, parser-redaction, size-boundary, and established live-pin tests pass.

Adversarial fixtures nevertheless reproduce destination substitution, insufficient staging ownership checks, a live-pin registration race, and policy/reopen divergence after a failed recovery read. These are local/operator or storage-failure correctness issues, **not demonstrated unauthenticated remote exploits**.

## Still open

### CR-01 — Partial; medium; N-01

**Symbols:** `prepare`, `restore_pinned`, `require_absent`.

**Evidence:** `src\server\cloud_recovery.rs:273-321,486-558`. Parent canonicalization, same-parent private staging, database verification, store rereading, and one publication rename are present. The normal Windows fixture and initial empty-directory refusal pass. A pre-publication interruption leaves no output; an interruption after the claim leaves an empty output, intentionally refused on retry.

However, `create_dir(output)` followed by ordinary `std::fs::rename(staged, output)` is not an atomic no-replace/identity-preserving claim. The executed substitution probe replaces a different empty directory despite the comment at `:530-531` claiming that the rename refuses anything that took the claim's place. See N-01.

**Recommendation:** Implement atomic no-replace publication rather than claim-then-replace; document the intentional empty-claim crash state until then. Cross-platform verification remains incomplete.

### CR-04 — Partial; documented platform exception, not an arithmetic defect

**Symbols:** `Runtime::publish`, `Sets::fetch`, `check_database_size`, `restore_space_needed`, `check_restore_space`, `compaction::free_bytes`.

**Evidence:** `src\server\backup_policy.rs:1024-1032` checks the actual database-file length under the database write lock, before snapshot copying. `src\server\cloud_backup.rs:48-80,1397-1405` checks the database entry, caps the bundle separately, and checks capacity before database/bundle payload reads. Coordination records and the manifest are read first; therefore **"before any download" is not literally true for metadata**.

Exactly 1 GiB is accepted; larger databases are refused with `cloud_database_too_large`. The bound is intentionally on the database, not total set size. Saturating multiplication/addition and strict `< needed` avoid overflow and the one-byte boundary mistake. The maximum supported database plus maximum 8 MiB bundle requires `2,222,981,120` bytes including the 64 MiB margin. Drill scratch is deleted before the final restored copy, so the inspected flow does not require three simultaneous full copies (`src\maintenance.rs:633-662`).

`src\server\compaction.rs:1143-1164` returns `None` on measurement errors and always on non-Unix systems; `check_restore_space(None, ...)` allows the operation. Thus Windows does **not** enforce the requested universal pre-download free-space guarantee. This limitation is documented in `docs\DOCKER-OPERATIONS.md:460-466`; it is not a newly hidden Windows regression.

**Tests:** Existing size/arithmetic fixture passed; the added zero-space fixture returned 507 before any payload access. Actual Windows free-space measurement, a real 1 GiB workload, and Linux capacity enforcement were not exercised.

**Recommendation:** Say "before payload download"; implement Windows measurement and define fail-closed handling for an unavailable measurement if the unconditional requirement is retained. A preflight cannot reserve capacity against unrelated concurrent writers.

## New

### N-01 — Medium: a substituted empty output is overwritten

**Symbol/location:** `restore_pinned`, `src\server\cloud_recovery.rs:530-547`.

**Reproduction:** In the temporary-copy test hook placed immediately before the unchanged rename:

```rust
std::fs::remove_dir(&output).unwrap();
std::fs::rename(&unrelated_empty_directory, &output).unwrap();
```

The real restore then succeeds and replaces that substituted directory with its complete output. The parent must be mutable by the racing actor; this is not a remote-only exploit and does not show overwriting a nonempty directory. The failure branch additionally calls `remove_dir(output)` without checking it is still the originally created claim, potentially removing a different empty directory after a failed rename.

**Platform/trade-off:** The successful fixture qualifies this host's Windows filesystem, not all Windows filesystems. Rust documents Unix replacement of empty destination directories and equivalent behavior only on Windows 10 1607+ filesystems supporting `FileRenameInfoEx`; older/unsupported Windows configurations can reject the command's own pre-created claim. Rust also documents failure across mount points. Normal staging/output are siblings under the same canonical parent, so choosing a parent on a different volume from the original CLI working directory is not itself a cross-filesystem bug. Replacing the canonical parent's directory entry/mount still requires a stronger handle-relative design to eliminate races.

**Suggested fix:** Use Linux `renameat2(RENAME_NOREPLACE)` and an appropriately tested Windows non-replacing directory move, or a separately designed handle-relative publication protocol. Do not assume a final existence check or an empty claim makes ordinary rename no-replace. Keep the parent operator-private on every platform; avoid deleting an unverified claim on failure.

**Evidence:** `review_claim_substitution_is_overwritten` passed; normal Windows publication and initially existing empty-output refusal passed. Linux execution and cross-mount substitution were not performed.

### N-02 — Low: stale cleanup treats names and arbitrary bytes as ownership proof

**Symbol/location:** `remove_stale_staging`, `src\server\cloud_recovery.rs:388-425`.

**Reproduction:** An unrelated directory named `.vlite-cloud-restore-my-archive`, containing `owner.lock` with arbitrary nonempty text plus another data file, is recursively removed. The function checks only the prefix, directory/non-symlink shape, and whether the lock is free with at least one byte. It does not validate a generated suffix, marker schema, PID, or expected staging contents. Even without a lock, an old prefixed directory is eligible.

**Impact/trust boundary:** Operator data accidentally stored under the reserved-looking prefix can be lost when another restore starts in that parent. An attacker needs local directory-creation/manipulation access; no lower-privileged remote trigger was established. This is weaker isolation than the function's "directories interrupted restores left" description.

**Suggested fix:** Prefer explicit/manual abandoned-staging cleanup, or a validated ownership marker and strict generated-name/type checks before automatic recursive deletion. Preserve unrecognized entries. Marker checks do not replace trusted-parent permissions or handle-relative race protection.

**Evidence:** `review_cleanup_deletes_unrelated_prefixed_directory` passed, observing actual deletion. `review_cleanup_spares_a_directory_junction` passed, preserving a real junction's target. No arbitrary symlink/junction traversal was demonstrated; do not describe the deletion reproduction as such.

### N-03 — Medium: force can remove a same-process active pin before registration

**Symbol/location:** `Runtime::hold`, `src\server\backup_policy.rs:652-660`; `Runtime::unpin`, `:1267-1290`.

**Interleaving:**

1. Restore publishes its operation pin through `sets.pin`.
2. Before it inserts the ID into `self.live`, a privileged caller lists the new pin and calls removal with `force=true`.
3. `unpin` sees no live entry, removes the pin, and retention can delete that set.
4. The original restore registers the now-missing pin and fails to fetch its source.

The deterministic temporary scheduling hook performs those actual production calls; retention deleted the oldest set and the restore failed. Existing live-pin tests pause later, at manifest fetch, and therefore miss the registration gap.

**Impact:** Violates the API promise that force refuses an operation still running on this server. Requires a privileged force request racing a restore, and a set otherwise eligible for collection. Force on another host's pin remains a documented operator judgment; this finding is specifically the preventable same-process gap.

**Suggested fix:** Serialize publication plus live registration against forced removal. For example, use the same local gate across `sets.pin`/registration and `unpin`'s check/removal, with explicit lock-order analysis and bounded I/O. Alternatively reserve a generated pin ID locally before publishing it. Add a barrier test at this exact interval.

**Evidence:** `review_force_removes_a_live_pin_before_registration` passed. The ordinary post-registration rejection and abandoned-owner force tests also passed.

### N-04 — Medium: a failed recovery read preserves a usable stale policy

**Symbol/location:** `Runtime::configure`, `src\server\backup_policy.rs:752-775`.

**Reproduction:** Begin with target prefix `vlite/prod/`; configure `vlite/new-target/`. Inject a write error after atomic replacement, then a transient I/O error for the immediate `read_document`. Configure returns the documented 500, but GET still reports the old prefix; reopening reads the new prefix. `configured()` continues to return success on the old runtime.

**Impact:** After a storage error, a running process and a restarted process can choose different backup targets and associated retention policy. The 500 correctly indicates uncertainty, but the stated invariant that GET/memory equals reopen is false, and work is not blocked pending reconciliation. The test simulates I/O failure; it is not proof of a physical-device failure.

**Suggested fix:** On reread failure, persistently mark the runtime's policy authority uncertain, surface that explicitly in GET, and reject scheduled/manual policy-dependent operations until reread succeeds. Log a fixed-code read failure without request contents. Adoption after a successful reread should clear the condition.

**Evidence:** `review_failed_policy_reread_diverges_from_reopen` passed. The original atomic-document test passes because its rereads succeed.

### N-05 — Low: first-step post-persistence import failure escapes cleanup

**Symbol/location:** `recovery_bundle::import`, `src\server\recovery_bundle.rs:239-247`; `users::rekey_import`, `src\server\users.rs:1259-1260`.

**Evidence type:** Static inspection only. `persist_noclobber(users.json)` can succeed and the immediately following directory sync can fail. The caller's `?` exits before reaching its cleanup block, leaving the store in the supplied directory. The existing failure test causes a username collision before persistence, so its successful cleanup assertion does not cover this edge.

**Impact/trade-off:** Offline restore's outer private staging normally contains/removes the partial store and prevents its publication. No activation of a partial admin store was demonstrated. This is an importer contract violation and a direct-call retry obstacle, not a proven authentication bypass.

**Suggested fix:** Have the importer own cleanup across both import steps, or make each helper remove its newly published file on post-persistence failure. Preserve the original failure while reporting cleanup failures explicitly. Add Unix directory-sync fault injection; Windows directory sync is a no-op here.

## Other adversarial questions

- **Second enabled account:** Not reproduced. Source-disabled flags are overwritten, and the verification independently checks enabled-account cardinality and authenticates the new administrator. The current recovery example uses `--output`. The runbook's "complete or absent" and "before any download" wording should still acknowledge the empty-claim interruption state and metadata reads.
