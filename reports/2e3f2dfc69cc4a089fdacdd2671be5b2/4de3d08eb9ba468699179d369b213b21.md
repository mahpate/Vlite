# HA ITEM-014 / ITEM-015 / ITEM-016 implementation review

## Findings

### 1. Medium (P2), confidence 10/10: drain timeout does not cancel active requests

**Evidence:** `src\server\gateway_mode.rs:264-277` times out the Axum server task and calls only `server.abort()`. Axum's independently spawned connection/request tasks are not thereby aborted. Shutdown then awaits `stop_feed` outside that timeout (`src\server\gateway_mode.rs:289-301`), which joins an in-progress blocking poll (`src\server\control_state.rs:991-1000`). The store client allows 120 seconds per request and retries unknown outcomes (`src\server\cloud_backup\azure.rs:145-147,334-347,401-411,575-586`).

**Observed impact:** A fixture invoking the actual public `run_gateway` API requested shutdown approximately 400 ms after listening, with zero propagation delay and `drain_timeout_ms=100`. It logged `drain_timeout`, but an already accepted, incomplete upload completed approximately 900 ms after listening and was still forwarded to the synthetic backend, returning 200. A 2.5-second control-state poll delayed shutdown return until 2,676 ms after invocation. Thus writes can first reach a backend *after* the advertised abort deadline, not merely finish an already-dispatched operation. This contradicts `docs\API.md:1175` and the bounded-drain intent in `docs\projects\feature-aca-ha\feature-aca-ha.prd.md:309,480`.

**Remediation:** Propagate cancellation to active request/body/forwarding tasks and track their completion at the drain deadline; aborting the accept-loop task is insufficient. Make poll shutdown interruptible or bounded within the shutdown budget. Add a regression with a stalled upload and delayed poll, asserting no new upstream dispatch after the deadline. Do not retry an already-dispatched write.

### 2. Medium (P2), confidence 10/10: incomplete uploads indefinitely occupy global request capacity

**Evidence:** `src\server\gateway_mode.rs:388-395` takes a global in-flight permit before authentication. An authenticated request then awaits the entire body with only a byte limit and no receive deadline (`src\server\gateway_mode.rs:461-467`). The upstream timeout starts later (`src\server\gateway_mode.rs:484-492`); it cannot release a permit held by a stalled upload.

**Impact:** With `max_in_flight=1`, the fixture kept a two-byte POST incomplete beyond `upstream_timeout_ms=100`; another otherwise valid request received 503. Static inspection shows that withholding the remaining byte can retain that permit indefinitely. Repeating this up to `max_in_flight` blocks all non-probe traffic on that replica, including unrelated tenants, while `/ready` remains healthy.

**Remediation:** Bound request-body reception, preferably with an explicit idle deadline that permits progressing uploads, return a clear timeout error, and release the permit. Cover stalled-body timeout and subsequent successful admission. Deployment timeout measurements remain separate; this is a missing local resource-lifetime bound, not a recommendation for an unmeasured production value.
