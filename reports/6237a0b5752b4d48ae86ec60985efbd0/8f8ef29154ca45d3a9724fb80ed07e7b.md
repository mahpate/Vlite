### F1 reproduction and recommendation

Use the following checksum-valid manifest, with a matching tag commit and a fake, fully qualifying CI run at that commit:

```json
{
  "version": "0.7.4",
  "source_commit": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "assets": [{"name": "vlite_client-0.7.4-py3-none-any.whl"}]
}
```

`SHA256SUMS` contains **only** the correct SHA-256 line for `release-manifest.json`; it contains no wheel line. Set `CI_TAG=v0.7.4`, `CI_MANIFEST_DIR` to those files, and both wait bounds to zero. Observed result from the actual `release_ci` entry point:

```text
exit: 0
verified=true
manifest_sha256=<actual 64-character manifest digest>
```

Repeating with `"sha256": null` in the asset also produced exit 0 and the same output shape. The cause is the missing-membership check, not a forged checksum or unqualified source. For the omitted-hash case, the uploader's `asset["sha256"]` lookup raises `KeyError`; a null hash cannot equal a wheel's computed digest. Thus the current downstream layer remains fail-closed.

**Recommendation:** require `name in sums` before equality, and require a properly typed SHA-256 value. Add both omitted-hash and explicit-null cases with no corresponding checksum entry to TEST-B12. They must fail at the guard, with exit 1, `verified=false`, and no `manifest_sha256`. For F2, use a SHA containing `a-f`, uppercase it, and verify rejection happens before any source-CI lookup.

Primary source: [guard validation at 33aabfe2](https://github.com/mahpate/Vlite/blob/33aabfe2939e79337321780bc5f8241bf9dc21b7/scripts/ci_policy.py#L318-L331), [independent upload defenses](https://github.com/mahpate/Vlite/blob/33aabfe2939e79337321780bc5f8241bf9dc21b7/.github/workflows/pypi.yml#L99-L114), and [TEST-B12 malformed cases](https://github.com/mahpate/Vlite/blob/33aabfe2939e79337321780bc5f8241bf9dc21b7/tests/ci_workflows.py#L1305-L1345).

### Freshness trade-off and multi-source uncertainty

An additional fake run deliberately changed A's latest CI state to failure while source B was being evaluated. Both source checks had initially been green, and the guard returned authorization at fake time 8 without rechecking A. This is a **sequence of per-source observations, not an atomic common-time snapshot** (`scripts/ci_policy.py:384-388`).

I have not reclassified the accepted one-shot freshness limitation as a new publication bypass. However, the wording "at the instant the guard passes" should explicitly explain the multi-source extension: an earlier source can change before the final aggregate output, not merely after it. If the owner instead requires all sources to be refreshed at aggregate pass, add a final attempt-state refresh/re-evaluation phase and a regression; that reduces the stale interval but cannot make GitHub state and registry upload atomic. PyPI's configured zero waits avoid long polling between sources, but sequential bounded API calls still take time.

## Static inspection, not live workflow execution

- `scripts/ci_policy.py:174-202,249-264` applies bounded retries and first-page count validation to both run and job listings. `:334-391` shares the original guard start across source commits. API execution can extend past a wait deadline; the design explicitly permits this and uses the per-subprocess 60-second timeout plus job timeout as outer bounds. Immediate retries at zero remaining time are intentional.
- PyPI guard permissions are only `contents: read` and `actions: read` (`.github/workflows/pypi.yml:34-36`); no `id-token` or write permission exists there. Its download is bounded by `timeout 120` (`:47`). Publisher OIDC remains isolated to `publish` (`:77-79`).
- `publish` directly needs `ci-guard`, checks `verified == 'true'`, and contains no status-check override such as `always()` or `continue-on-error` (`pypi.yml:59-62`). Under Actions' normal implicit success condition, a failed/skipped dependency cannot authorize publishing. This is source/DAG inspection plus static regression coverage, **not an executed Actions skip/failure experiment**.
- Guard output values are a fixed boolean and a locally computed SHA-256 hexdigest (`scripts/ci_policy.py:310,331,398-406`). Raw manifest names, versions and source strings are not copied into `GITHUB_OUTPUT`. Tag values enter the shell through a quoted environment variable, not expression-generated shell code. Asset names in the upload Python are data, not shell commands. No demonstrated output-file/shell injection was found.
- Publisher checks the downloaded manifest against both the guard digest and its checksum, then verifies every downloaded wheel against both its checksum and manifest entry (`pypi.yml:99-114`). Manifest version is checked by the guard; wheel filename version is checked by the publisher. Empty selected projects fail, and embedded wheels retain required manylinux/Windows/macOS presence checks (`:119-123`).
- Publisher `gh release download` has no newly added explicit subprocess timeout (`pypi.yml:80-86`); this was already unbounded in the original job. The new guard download has its own 120-second bound. No claim is made that the publisher's existing download is now bounded to 120 seconds.
- The entire `release.yml` is unchanged between e0a402ff and 33aabfe2. Its `image-build`, `image-publish`, `image-verify`, and `release` jobs retain direct guard needs and verified checks (`release.yml:336-338,445-447,508-510,560-562`). Existing build/test prerequisites and tag-only publication conditions remain intact.
- A source-segment comparison confirmed `trusted_run`, `all_succeeded`, `full_ci_jobs`, `gh_pages`, `image_ci`, and `route` are byte-identical between the original and fixed policy. PyPI event conditions, matrix, environments, version filtering, and publication action remain; intended changes are provenance qualification and stricter manifest-bound uploads.
- `bindings/release_assets.py:27-41` was inspected as supporting prior art for the produced manifest/checksum format and asset overrides; it was not changed. Its normal producer includes hashes, so F1 requires malformed or manually altered metadata rather than its ordinary output.
