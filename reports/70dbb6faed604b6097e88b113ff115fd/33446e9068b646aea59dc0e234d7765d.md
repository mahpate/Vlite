## Findings

### 1. High: the API maintenance recipe must not be used unchanged for an authority-enabled writer

**Instruction.** `docs/API.md:1282-1286` tells operators to issue tenants/credentials by stopping a trusted backend, running the same database standalone with its admin directory, issuing them, stopping it, updating control state and restarting the trusted backend. There is no authority/failover qualification attached to that recipe.

**Actual behavior.**

- `src/bin/vlite-server.rs:404-423` requires authority options to be used with writer mode and persistent REST serving. A plain standalone maintenance invocation is not an authority-enabled writer.
- With no authority options there is no writer fence, as correctly stated in `docs/HA-ACA.md:117-123`; the service starts with a disabled fence in `src/server.rs:365`.
- Authority ownership is not automatically released on shutdown. `src/server/writer_authority.rs:363-370` refuses a subsequent claim when `writer_id` is present, with `writer_authority_claimed` and an explicit-failover requirement.
- Following an actual transfer, `src/server/writer_authority.rs:190-205,234-283` restores the authority's archived base. Standalone changes outside that archive must not be assumed to survive it.

**Operational impact.** The documented simple restart is unusable once the writer has claimed authority. Omitting authority to make maintenance run bypasses the intended fenced lifecycle and can create changes not represented by the authoritative recovery boundary. A subsequent failover/restore is not a guarantee of preserving those changes. The exact persistence of each tenant/credential artifact was not independently exercised here.

**Minimal correction.** Scope the existing recipe explicitly to the non-authority gateway MVP. For authority-enabled writers, mark tenant/credential issuance maintenance unsupported by this recipe until a reviewed maintenance/handoff procedure preserves both authoritative database history and the published control state. Explicitly prohibit dropping authority flags, using a standalone writer as a claim workaround, or assuming a stopped process has released authority. Link the manual transfer and archived-base recovery requirements instead of implying a restart is sufficient.

### 2. High: prescribed status and abandoned-pin operations have no access path on the HA templates' trusted backends

**Instructions.**

- `docs/HA-ACA.md:277-281` uses administrator-only serve-status to verify a recovered writer.
- `docs/HA-ACA.md:343-346` requires reader serve-status/progress inspection after explaining how to run a gateway-trusted reader.
- `docs/HA-ACA.md:367-373` and `deploy/azure-container-apps/ha/README.md:9-12` direct an administrator to remove abandoned reader pins using the forced-unpin procedure.
- The linked procedure is an admin REST `DELETE .../pins/{pin}?force=true`, not an offline pin command: `docs/DOCKER-OPERATIONS.md:430-436`.

**Actual behavior.**

- The writer and reader templates both pass `--gateway-trust-file`; only the writer receives authority/policy files, and no backend receives an admin credential: `deploy/azure-container-apps/ha/templates.ps1:388-420`.
- Trusted-mode authentication returns immediately through trust authentication instead of checking local bearer admin tokens: `src/server.rs:1259-1263`.
- A verified principal envelope produces only `Role::Scoped`: `src/server/gateway_trust.rs:221-254`.
- Serve-status and cloud pin deletion fall through to `Need::Admin`; scoped grants cannot satisfy that need: `src/server.rs:1312-1426,1537-1539`.
- Adding `VLITE_ADMIN_DIR` is not a workaround: it is rejected with trusted mode in `src/bin/vlite-server.rs:628-642`.
- Reader enrollment can release pins with the same replica reason, but that identity comes from `CONTAINER_APP_REPLICA_NAME`, then `HOSTNAME`, then PID: `src/server/reader_apply/follower.rs:141-154,231-235`. A replacement ACA replica is not guaranteed to reuse it.

**Operational impact.** An admin bearer request to a trusted backend does not authenticate via the local token path; an otherwise valid scoped envelope is forbidden from these routes. Going through the gateway does not grant admin access either. Thus neither the mandatory diagnostic step nor arbitrary abandoned-pin cleanup is executable as written for this deployment. Pins are bounded at 16 per set (`src/server/cloud_backup.rs:37,1644-1648`), so pin accumulation can eventually prevent enrollment, restores or other operations.

**Minimal correction.** Separate standalone/admin-directory procedures from trusted-backend procedures. Explicitly state that serve-status and forced-unpin REST are unavailable in the projected trusted mode and remain an operational qualification gap. Existing `authority show`, private startup/archive logs, authorized data reads and reader freshness headers can supply partial evidence, but are not equivalent to the full admin status or pin-management capability. Do not prescribe exposing backends, adding an admin token secret, disabling trust, or editing Blob records as a workaround. Keep the affected qualification/drill blocked until an existing safe management path is reviewed and demonstrated.

### 3. High: the API's reader-routing recipe omits a runtime epoch refusal that rejects real readers

**Instruction.** `docs/API.md:1273-1280` says opting a dedicated tenant into readers routes reads to the reader and falls back to the writer for connection/timeout, 503 or lineage/binding mismatch. It does not disclose that a healthy reader needs an epoch stamp or that an epoch refusal is final.

**Actual behavior.**

- A dedicated target carries the directory's required epoch even when its endpoint is a reader: `src/server/gateway.rs:449-467`.
- The gateway first accepts a reader response if it is not 503 and its lineage and binding generation match: `src/server/gateway_mode.rs:467-506,552-566`.
- It then requires a valid `x-vlite-epoch`, checking against the maximum of the dispatched epoch and the current same-lineage directory epoch before streaming: `src/server/gateway_mode.rs:510-536`. A refusal returns directly; it does not re-enter writer fallback.
- The backend adds `x-vlite-epoch` only when `writer_fence.epoch()` exists: `src/server.rs:1776-1781`. That value comes from a writer claim: `src/server/writer_fence.rs:171-173`.
- Reader authority flags are not permitted (`src/bin/vlite-server.rs:414-418`), and reader progress/header generation supplies lineage, binding and age/sequence, not a writer-fence epoch (`src/server/reader_staleness.rs:48-99`).
- The explicit tests for gateway epoch handling use synthetic stamped upstream responses: `src/server/gateway_mode.rs:1419-1495`. Their existence is not evidence that the actual reader process stamps an epoch.

**Operational impact.** On this trace, a healthy real reader with matching lineage/binding headers passes eligibility, then fails the required dedicated epoch check with 503 `backend_epoch_stale`. It does not fall back. An unavailable/ineligible reader may instead cause a successful writer fallback, potentially concealing that reader-serving itself is unusable. This was not reproduced with a running binary in this review.

**Minimal correction.** Preserve and strengthen `docs/HA-ACA.md:367-369` and `deploy/azure-container-apps/ha/README.md:224-228`: keep routing `writer_only`. In the API, document the enforced epoch check, final refusal, and current actual-reader limitation rather than presenting `readers` as a working end-to-end path. Before any future relaxation, require a real gateway + reader process test, not only mocked upstream headers, followed separately by ACA qualification. Do not fix this operationally by fabricating an epoch header or weakening gateway checking.

### 4. Medium: frozen-base freshness is not preserved across reader re-enrollment

**Claim.** `docs/HA-ACA.md:359-364` says an HA frozen base is not a freshness confirmation, age continues to grow during a prepared transfer, and the reader becomes stale at its bound. The same section recommends restart/re-enrollment for replacement.

**Actual behavior.**

- Enrollment accepts the authority's `head` or `base`, including a prepared transfer's frozen base: `src/server/reader_apply/follower.rs:198-217`.
- After restoring its slots, enrollment unconditionally calls `progress.confirm(sequence, now)`: `src/server/reader_apply/follower.rs:323-328`. This does not distinguish `Recovering`.
- Later poll steps do distinguish it: when authority is `Recovering`, `confirmed_at` retains the previous timestamp rather than advancing to `now`: `src/server/reader_apply/follower.rs:538-548`.
- Staleness compares time since that confirmation to the configured bound: `src/server/reader_staleness.rs:14-20`.

**Operational impact.** The claim holds for an already-enrolled reader that stays running, not an unrestricted new enrollment during recovery. Restarting/replacing it can give the same frozen data a new age window. Repeated restarts must not be represented as proof of freshness. The runbook's definition is also archive-head confirmation age, not writer-commit lag (`docs/HA-ACA.md:349-353`).

**Minimal correction.** Qualify the current claim as applying to continuing followers. During a prepared transfer, keep replacement/re-enrolled readers out of routing and do not treat fresh age/readiness after enrollment as proof that the frozen archive is current. Require a serving current-epoch head and independent recovery verification before admitting reads. A stronger cross-restart freshness contract would need a separate implementation decision and test; this report does not propose a new service or dependency.

### 5. Medium: the API's explicit epoch-null and no-fencing claims are stale

- `docs/API.md:991-996`: the experimental MVP "has no epoch fencing, failover or ACA deployment".
- `docs/API.md:1270-1272`: the directory epoch is stored but not checked against responses.

**Actual behavior.**

- `src/server/serve_mode.rs:162-178` reports `"epoch": service.writer_fence.epoch()`, with null only when no writer fence is installed.
- `src/server/writer_fence.rs:171-173,306-313,335-365` obtains the claimed epoch and verifies authority before commit/ack.
- `src/server.rs:1725-1742,1776-1781` implements the successful-mutation response barrier and epoch header.
- `src/server/gateway_mode.rs:510-536` enforces dedicated response epochs against the dispatched and latest same-lineage directory values; this is a directory view, not a direct authority read by the gateway.
- `src/server/failover.rs:332-443` implements reported, acknowledged authority transfer.
- `docs/HA-ACA.md:277-281` already states the correct conditional epoch behavior.
- `site/api.html:1593` gives a narrower serve-status summary. It does **not** repeat the "currently null" claim; it omits epoch and reader progress rather than contradicting the implementation.

**Operational impact.** Operators can misinterpret a non-null epoch as unexpected, believe directory epochs have no serving consequence, or confuse implemented manual recovery with the unqualified ACA deployment path. Conversely, fixing these sentences must not imply a proven zero zombie window.

**Minimal correction.** Say "claimed writer epoch when authority is enabled, null otherwise"; describe `x-vlite-epoch` and dedicated gateway refusal semantics, including no retry/fallback on epoch refusal and no such requirement for shared-pool targets. Replace the broad no-fencing/no-failover sentence with "opt-in local manual authority/fencing/recovery is implemented; automatic failover and live ACA qualification are not provided." Optionally add the conditional epoch and reader progress to the site's terse summary without claiming the site currently makes the null error.

### 6. Medium: advertised `CreateFormat=3` cannot start the authority-enabled HA writer

**Instruction/acceptance.** `deploy/azure-container-apps/ha/README.md:103` advertises `CreateFormat` 3, 4 or 5. **Actual behavior.** Format 3 creation has no lineage, whereas 4 and 5 create one: `src/lib.rs:1383-1398`. `src/server/writer_authority.rs:353-362` requires the opened database's lineage to match authority and refuses a missing/mismatched lineage. `docs/HA-ACA.md:73-75,151-152` already correctly requires a lineage-bearing v4/v5 database.

**Operational impact.** This accepted configuration is unusable after the future rollout gate is satisfied. It is not a current deployment escape: the unconditional qualification refusal occurs first. Newly generated database lineage/bootstrap provenance also remains part of that unresolved initialization verifier, not something the numeric format range solves.

**Minimal correction.** Document that authority-enabled HA requires 4 or 5; do not recommend format 3. Follow up separately by aligning the HA validators with the mandatory authority constraint. Leave the singleton's general format support unchanged and do not treat this correction as implementing create-only authority/bootstrap qualification.

## Verified aligned sections and important boundaries

The following comparisons are aligned by static inspection unless a fixture result is explicitly mentioned.

### Manual failover, fencing and rollback

- **Usage and inputs match.** The failover usage excerpt in `docs/HA-ACA.md:221-223` matches `FAILOVER_USAGE` in `src/server/failover.rs:15`. Optional observed sequence/time are paired, archive status is bounded at 64 KiB, and exact optional inputs affect the report digest (`failover.rs:83-128,218-227,332-385`). The instruction to preserve identical report/execute inputs is appropriate.
- **Acknowledgment is not fencing evidence.** The zero-replica number is operator-supplied. `failover.rs:397-408` checks the value and digest/epoch/revision; it does not query Azure. The runbook explicitly says so at `docs/HA-ACA.md:252-258`. `failover.rs:409-435` additionally rechecks authority and uses expected-state transfer. Unknown loss remains unknown; local archive status cannot advance the authority boundary (`failover.rs:341-381`).
- **Execute is preparation, not promotion to service.** The runbook correctly separates execute, startup restore, claim, data verification and routing (`docs/HA-ACA.md:260-281`). Full old writer revision deactivation and zero-replica re-enumeration are required, not just single-revision mode or min=max=1. The script's corresponding stop loop is `deploy.ps1:328-375`; its behavior was exercised only through mocks here.
- **Startup fails closed and does not reclaim automatically.** Restore checks the observed base, HA manifest, scope, epoch, lineage, chain and exact sequence; installation preserves an existing database under a no-replace superseded path (`writer_authority.rs:190-333`). Claim uses the prepared authority observation and refuses an existing owner (`writer_authority.rs:343-406`). Configuration restrictions precede restore (`writer_authority.rs:164-176`; `src/bin/vlite-server.rs:954-982`).
- **Rollback warning is correct.** `docs/HA-ACA.md:283-287` forbids decrementing authority or reactivating old revisions after execute/uncertainty. The deployment path also has no automatic writer rollback/reactivation (`deploy.ps1:372,395,654-656`). Failed claim after a successful local restore is not a reason to run the superseded file or repeat CAS blindly.
- **Write safety is not zero-window proof.** The writer performs precommit and preack authority reads, a response barrier, and periodic idle rechecks (`src/server.rs:718-730,749-770,1725-1742`; `writer_fence.rs:306-375`; `writer_authority.rs:456-483`). An authority outage before a commit can recover on a fresh check; postcommit uncertainty latches stop (`writer_fence.rs:393-404`). The runbook correctly warns that polling intervals are not wall-clock zombie bounds (`docs/HA-ACA.md:117-123`).

### Archive policy, restore and retention

- **Existing mechanisms only.** The writer template mounts existing app-secret files and passes both authority and archive-policy arguments (`templates.ps1:388-418`). No Key Vault is introduced. Policy schema, bounds, enabled backup/archive requirements and target matching agree with `docs/HA-ACA.md:138-200` (`src/server/backup_policy.rs:78-196`). The policy is incompatible with `VLITE_ADMIN_DIR` (`src/bin/vlite-server.rs:624-627`).
- **Initial backup is attempted, not guaranteed.** Router construction and the initial archive-base attempt precede serving (`src/bin/vlite-server.rs:1160-1203`); failures are logged rather than converted to a successful qualification (`writer_authority.rs:413-425`). The runbook discloses nonfatal initial snapshot failure (`docs/HA-ACA.md:165-172`). Readiness or a claimed epoch alone does not demonstrate a durable HA head: independently require verified recovery evidence before a drill/handoff.
- **New epoch needs its own archive baseline.** The archive loop takes a fresh snapshot when authority has a transferred base but no head (`backup_policy.rs:1435-1443`), matching the runbook's new-epoch statement. Epoch-aware archive publication is not interchangeable with legacy checkpoints.
- **Retention protection matches.** Head/base set IDs are excluded from condemnation; an unreadable authority prevents new Published-set retention decisions (`src/server/cloud_backup.rs:2030-2078` and the remainder of `collect`). This matches `docs/HA-ACA.md:130-133`; it does not promise that cleanup of already-deleting sets or stale staging stops.
- **Offline restore is not writer promotion.** `cloud-restore` is rekey-only and rejects seed (`src/server/cloud_recovery.rs:301-308`). HA checkpoint restore uses the authority head/base for that set and verifies HA scope (`cloud_recovery.rs:663-689`). No exact checkpoint means no arbitrary rounding; no checkpoint archive may require snapshot restore without `--archive-checkpoint` (`cloud_recovery.rs:682-689`). The runbook appropriately separates this isolated new-lineage procedure from same-lineage startup recovery (`docs/HA-ACA.md:472-508`).
- **Minor usability clarification:** `cloud-sets` lists sets/records, not an archive checkpoint sequence inventory (`cloud_recovery.rs:262-275`; `cloud_backup.rs:1476-1550`). In `docs/HA-ACA.md:487-489`, "exact listed checkpoint sequence" should name a retained checkpoint report/status as the source, not imply the preceding `cloud-sets` command supplies it. Do not try unsupported restore values merely to discover production checkpoints.

### Readers, control state and key rotation

- **Reader constraints align.** Private `reader-a`/`reader-b` slots, whole-set operation pins, mandatory bounded capacity/staleness and fatal reseed requirements match `docs/HA-ACA.md:291-341,355-374` and `src/server/reader_apply/follower.rs:198-328,450-620`. Authorization precedes read-only/staleness admission. Sequence redaction and archive-confirmation age, not commit-lag promises, match `src/server/reader_staleness.rs:14-99` and `src/server/serve_mode.rs:147-178`. The cross-restart freshness exception is finding 4.
- **Control refresh is not key refresh or epoch transfer.** The usage matches `CONTROL_USAGE` (`src/server/gateway_mode.rs:52`); create-only publish, CAS mutations, local admin-directory mutation before remote publication, and reviewed directory/reimport behavior are covered by `gateway_mode.rs:955-1113`. Trust readiness polls the control snapshot and reports its generation (`gateway_trust.rs:269-276`). Repairing an outage need not publish an older snapshot; the runbook's refusal to undo revocation just to recover availability is appropriate.
- **Rotation ordering aligns, but is deliberately not executable deployment automation.** Backend verifiers are created from bounded bundles at startup (`gateway_trust.rs:104-125`), and the parser permits one or two distinct valid keys only (`src/server/principal_envelope.rs:257-277`). Backends accepting old+new first, new signers second, stopping all old signers and waiting envelope lifetime plus skew/drain before dropping verification is the correct sequence (`docs/HA-ACA.md:433-470`; HA README `194-220`). Keep rotations serialized within that two-key limit. Secret-value replacement is not runtime reload. `-Rotate` refusal and immutable generation state are not an overlap rollout implementation.
