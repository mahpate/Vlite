## Scope

A parallel task (T24 / ITEM-038, owning `backup_policy.rs`,
`writer_fence.rs` and `writer_authority.rs`) makes a claimed writer
publish sets with an HA manifest (`publish_ha`) and append HA checkpoints
(`append_checkpoint_ha`), advancing the authority `head`. Those sets have
no legacy `archive.json`, and today `fetch` refuses their manifest. Make
every reader of sets accept them, follow the authority head, and keep HA
sets safe from retention.

1. `fetch`/`fetch_with` accept an HA manifest: when the bytes parse as
   `parse_ha_manifest`, run its `check` and the same inner `Manifest`
   checks, record sha and size envelope, and return the inner manifest
   plus a new `Fetched` field carrying the `HaIdentity` (`None` for legacy
   sets). Keep both function signatures. Legacy behaviour and error codes
   are unchanged. This also makes `cloud-restore` of an HA snapshot and
   `drill_pinned` work.
2. Follower with an authority. Read the authority through
   `AuthorityStore::new(sets.coordination())`:
   - `Missing` → the existing legacy path, byte-for-byte.
   - Present → the followed position is `head.or(base)` (a Recovering
     authority keeps serving the frozen base; staleness then grows and the
     existing bound fails readiness). None of either → the existing
     `reader_apply_no_set` refusal.
   - `enroll_with` pins and fetches the set named by that `HeadRef`
     (refuse if it is not an HA set or its manifest sha differs), then
     applies HA checkpoints up to exactly that head.
   - `step` re-reads the authority each poll: another `set_id` → the
     existing `reader_apply_reseed_required` path; a lower sequence →
     "the archive head moved backwards"; a higher one → apply the HA
     checkpoints after the copy's position (verified through
     `open_archive_ha_at`: hashes, chain, contiguity, lineage, header,
     bundle) into the standby slot and swap; equal → confirm.
   - A store outage while reading the authority is a `Retry` exactly like
     today's `cloud_store_unavailable`; a record that disappears after an
     HA enrolment fails the follower.
3. Add an archive helper (in `archive.rs`) such as
   `follow_archive_ha(record, manifest, database, head) -> Follow` and a
   restore helper that replays an HA set's verified checkpoints onto its
   downloaded baseline up to exactly `head.sequence` (baseline sha and
   lineage verified, never past the head). The restore helper is used by
   item 4 and later by ITEM-040 (startup base restore).
4. `cloud-restore --archive-checkpoint <sequence>` of an HA set replays
   through the HA index of the authority's current `head.or(base)` for
   that set; a sequence that is not an HA checkpoint refuses with the
   existing `pitr_target_unsupported` listing. Legacy sets are unchanged.
5. `collect` retention: when an authority record exists, the sets named by
   `head` and `base` are always protected. Read it through
   `coordination()`; `Missing` → no change; any other read failure skips
   the retention phase (no deletions) and reports the error, while the
   earlier janitor steps still run.
6. Remove `#[cfg_attr(not(test), allow(dead_code))]` only from HA items
   that your non-test code now uses. Leave the attributes on items only
   T24 uses (`publish_ha`, `resolve_ha_baseline`, `open_archive_ha`,
   `append_checkpoint_ha`), or the non-test build fails `-D warnings`.

Existing deployments (no authority record) must be unchanged in
behaviour: the same sets chosen, the same reseed rules, logs, status JSON
and refusal codes.

## Tests (test-first)

Lib unit tests with `cloud::fake::Memory`, publishing HA sets with the
existing `setup_ha`/`prepare_ha`/`publish_ha`/`append_checkpoint_ha`
helpers (no runtime loop needed):
- `fetch` of an HA set verifies and returns `ha: Some(identity)`; a
  tampered HA manifest is refused; a legacy set still returns `None`.
- Enrol on an authority head with two HA checkpoints → applied to the
  head sequence; append a third and advance the head → `step` swaps to it;
  a head on another set → reseed; a lower sequence → reseed; an outage on
  the authority read → `Retry`; no authority → identical legacy result.
- Follow of a frozen `base` (after `prepare_transfer`) serves the base and
  never advances past it.
- The HA restore helper stops at exactly the head sequence and refuses a
  baseline with another sha or lineage.
- `collect` with retention enabled never deletes the head or base set and
  deletes nothing when the authority read fails.
- `cloud-restore --archive-checkpoint` of an HA set restores the exact
  checkpoint; an unknown sequence lists the supported ones.
