# Research: Azure Blob off-host backup and asynchronous warm standby

**Baseline:** `mahpate/Vlite`, pushed release commit `25003dd9dace64f5829a4cf2afad23ab8d78edcc`, package/tag `0.7.5` / `v0.7.5`.

**Validation status: INCOMPLETE for runtime recovery, Azure durability, and fenced failover.** This is completed static research for a later design-first exercise, not a feature PRD, implementation, production qualification, or successful failover review. Only read-only repository checks and JavaScript syntax checks were executed. No database mutations, Rust tests, fixture drills, cloud calls, deployment changes, or live failovers were run.

## 1. Executive findings and evidence boundaries

The release already supplies useful **local** building blocks: owner-locked snapshots, validated copy-out, backup manifests, scheduled verification/drills/retention, whole-commit log export, and a library follower that syncs and fully replays received commits. These are not an Azure backup service or an operational warm-standby system. The inspected server exposes export, not follower apply, membership, remote durable progress, promotion, or fencing.

The most consequential constraints for later design are:

1. **Database recovery is not server recovery.** Database bytes include graph/vector/KV/import state, but exclude tenant policy, credential revocations, accounts, actual memory grants, bootstrap secrets, TLS identities, provider configuration, webhook state, and operational configuration. A database-only standby can be current in sequence and stale in authorization.
2. **The existing production REST export is unavailable for agent-memory databases with bindings/reservations.** Do not assume the dashboard export route can simply be polled by a standby. Raw library export is different from server-authorized export.
3. **Promotion is only `ReplicaFollower::promote(self) -> Database`.** It returns the existing database; it neither closes/reopens nor checks an external owner, epoch, lease, old writer, transport drain, or catch-up target. Local locks and KV CAS cannot fence a different host.
4. **Primary ACK and replica durability are different positions.** File-backed default durability is periodic, 60 seconds; export first calls `sync()`. A follower ACK follows local sync and replay, but async primary ACK does not wait for that follower. No fixed off-host RPO/RTO follows from these primitives.
5. **Maintenance can sever a shipping chain.** Checkpoints preserve lineage/revisions but discard old history; restore/compaction/key rotation change lineage. Follower header equality also matters, not just sequence and lineage.
6. **Important surfaces are only partially integrated.** Encrypted maintenance exists in the engine, but admin snapshot publication, verification, drills, selection, and selection resolution call keyless helpers. Some docs/dashboard permissions contradict server authorization. These are static findings requiring focused reproduction before depending on those workflows.

## 3. Snapshot, scheduled backup, publication, and retention trace

### 3.1 Entry points and consistency boundary

The manual route is `POST /v1/admin/backups` -> `admin::backup` -> `Service::run` -> `ops::snapshot` -> `ops::publish` -> `maintenance::inspect` (`src/server/admin.rs:1172-1188`). `Service::run` acquires an admission permit and the `RwLock` write owner; the permit survives client disconnect (`src/server.rs:564-593`). For manual backup, verification/publication also happen inside this closure, extending owner hold time.

The scheduled path is `Ops::run_loop` -> `scheduled_backup` -> `backup_cycle` -> `with_database(snapshot)` -> `publish` -> optional `drill_into` -> optional `retention` (`src/server/ops.rs:264-310,316-324,566-649`). The scheduled path releases the database owner after snapshot copying, before verification/drill/retention. There is one scheduler thread, but manual schedule-run HTTP calls spawn their own blocking operation; the shared permit limit bounds work, not a global one-backup-at-a-time transaction (`:566-581,1108-1114,1125-1147`). Multiple copies/manifests/retention passes can therefore overlap after serialization at the snapshot boundary. No per-cycle distributed coordinator or comprehensive retention-vs-verify lock was found.

`snapshot(db, directory)` first checks health and calls `db.sync()`, records the current logical file position, copies the stream from zero into a same-directory `NamedTempFile`, syncs the staged file, and restores the source position (`src/server/ops.rs:797-821`). It includes all committed frames reachable through the database stream, not just visible query results. Directory stores are exposed as a logical chain; offline `maintenance::source` also explicitly packs a directory through `LockedFile::chain` (`src/maintenance.rs:72-83`). Enumerating a directory's filenames externally is not equivalent to this locked logical snapshot.

The boundary is **one database**, not database + `VLITE_ADMIN_DIR` + secret/config files. Tenant/user/credential operations may use the owner lock for serialization, but persist separate files without database frames. Credential create captures lineage/collection scopes under `Service::run` and subsequently commits the credential store on a blocking task (`src/server/credentials.rs:739-786`). Holding the owner only around database copy does not make all sidecars a transactional snapshot.

### 3.2 Included and excluded state

Included: database header/version/flags, lineage, committed sequences/history that still exists, live and historical record mutations, payload/metadata, record expiry, collection identities/settings, named/sparse/vector-version state, import markers, graph schemas/nodes/edges/attachments/allocation marks and logged graph mutations. Source decoding and restoration are evidenced by `format::load_inner` dispatch (`src/format.rs:2106-2339`), named-vector `commit_vectors` (`src/vectors.rs:613-632`), and graph replay (`src/property_graph/frame.rs:197-266`).

Excluded: separate credential/account/tenant stores; audit history; webhook configuration/signing secrets/cursors; provider aliases and provider secrets; memory binding file's grants; bootstrap bearer credentials; TLS key/cert files; CLI/environment settings; running jobs, runtime schedule counters, rate-bucket/session occupancy, in-memory HNSW and external ANN sidecars. Inventory and consequences are expanded in section 7. A whole-file backup also contains other tenants and data hidden by logical TTL; it is not a tenant export or secure erasure.

### 3.3 Publication and manifest semantics

Engine offline `backup_inner` validates a complete locked source, performs a byte-identical copy, checks copied length, and delegates to `publish_with` (`src/maintenance.rs:371-387`). `publish_held` reloads the staged output, rejects an incomplete tail, syncs it, takes an exclusive publication lock where supported, and `persist_noclobber`s it. A failure before visibility leaves no final output; after visibility the file is retained, with Unix directory-sync failure exposed as `PublicationIndeterminate` (`:731-788`). Unsupported publication locking is explicitly tolerated there; ordinary source/directory locking has its own error contract (`src/directory.rs:157-170`).

Admin `ops::publish` keylessly verifies and inspects the stage, publishes no-clobber, syncs the directory, builds the JSON manifest, then writes that separately with staged file sync/replacement/directory sync (`src/server/ops.rs:785-795,825-855`). The manifest has schema/name/creation time, bytes/CRC32, format/dimensions/live-record/commit counts, hex lineage, a **collection count**, verification time and drill result. It does not contain Azure object/version identifiers, cryptographic authenticity, graph/KV recovery probes, policy generation, an external leader epoch, or a retained-log coverage map.

The final backup and manifest are **not atomic as a pair**: a crash/error after file publication but before manifest publication can leave a complete unmanifested backup, and the request can fail even though a final file is present. `verify` can create a manifest if none exists, but an existing malformed/unreadable manifest or mismatched derived fields fails; it does not bless edited metadata (`src/server/ops.rs:1149-1205`). `read_manifest` treats missing/symlinked/invalid/oversize JSON as `None`, with a 64 KiB limit (`:761-783`). Listing can show a backup with no manifest.

CRC32 detects accidental damage; an unkeyed SHA-256 segment digest also does not authenticate a publisher. Existing database AEAD authenticates encrypted frame bodies but is not a remote catalog authorization scheme. A later Azure design needs a separate trust/identity analysis rather than calling a local CRC manifest authenticated.

### 3.4 Scheduling and local retention

`BackupConfig` defaults: disabled, 86,400-second interval, retention off, `retain_last=7`, `retain_days=0`, drill every run, drill ceiling 4 GiB (`src/server/ops.rs:77-99`). `schedule_put` merges optional fields, permits 300..604800-second intervals, retain-last 1..100, days <=3650 and drill-every <=100; it updates memory/timers only (`:1035-1106`). `schedule_run` can run a cycle even if periodic scheduling is disabled. Shutdown joins the worker (`:250-262`).

The scheduler advances its next timer before work and skips a cycle if admission is full; `backup_skipped_busy_total` increments (`:264-310,566-578`). It has no durable job journal, persistent missed-run catch-up, remote retry/backoff, or guaranteed deadline. Runs increment after publication, so a failed drill can coexist with a created/verified backup and a counted run (`:597-623`). A ceiling-skipped drill is recorded as skipped, not proof of recoverability.

Local retention ranks generated `backup-*.vlite` by manifest/name time, protects the newest backup, newest marked verified, startup selection and active path, ignores symlinks/non-generated files, applies count **and** age eligibility, sync-audits each deletion first, deletes the backup and best-effort deletes its manifest, then directory-syncs (`src/server/ops.rs:684-745`). Restored copies are outside the generated-backup candidates. Protection uses a stored verification timestamp, not fresh verification of every retained item.

This is suitable prior art for safe local operator cleanup, not remote reference-aware GC. It knows nothing of an upload in progress, an offline follower's required prefix, key-retirement dependencies, Blob versions, immutable retention, or remote generations. Retention and explicit verify/drill work can race after snapshot owner release; platform file-sharing behavior and absence of a common pin need qualification. Do not copy this age/count algorithm into Azure GC unchanged.

## 4. Verification, drills, restore, reopen, and rollback

### 4.1 Integrity is stronger than checksum-only, weaker than service recoverability

`verify_loaded` takes the source lock, fully loads/replays/decrypts the format, requires a complete tail, then scans all bytes for independent CRC32 and confirms length stability (`src/maintenance.rs:157-195`). It is not merely a transport checksum. It still cannot prove external keys/configuration will be available on a different host or that restored authorization is safe.

`maintenance::drill` loads the backup, captures collection names/raw record counts and graph state, restores a new scratch file with fresh lineage, opens it as a database, compares collection names/counts and graph equality, and performs a k=1 exact squared-L2 self-search of the smallest ID in each nonempty collection. It closes the handle and attempts scratch deletion (`src/maintenance.rs:633-710`, `graph_check`, `probe`). No serving listener, provider call, webhook dispatcher, user sign-in, KV CAS write, transport restart, external fencing or host isolation is exercised.

Scratch is under the configured admin/work directory, on the same host/filesystem, not an isolated recovery failure domain. The doc comment says always deleted, but error propagation and failed cleanup/publication remain possible filesystem outcomes; no cleanup success should be inferred after `PublicationIndeterminate`. Probe-time failures attempt removal before returning the probe error (`:651-658`). The probe opens and closes once, not a second-process service boot or a post-promotion restart.

Limits needing focused qualification: no encrypted drill overload; a 4 GiB default schedule ceiling; one vector probe per collection rather than exhaustive application invariants; no explicit KV enumeration/value/CAS probes; no admin-state checks. A collection containing an already-expired smallest record is a potential false-negative self-probe because raw counts and visibility-filtered `get` differ; this is a static test need, not a reproduced failure.

### 4.2 Restore identity and PITR

`restore_inner` validates complete input and creates a new, no-overwrite output; v4+ gets a new lineage, while ordinary frame bytes and record revisions are copied (`src/maintenance.rs:389-446`). Thus restore is intentionally **not** follower bootstrap: bootstrap uses a lineage-preserving backup. Full restore does not imply numeric KV revisions are globally unique; it mainly invalidates lineage-bound callers/credentials/cursors. Compaction can restate/resequence state; distinguish it from byte-copy restore and directory checkpoint.

`restore_to` accepts a complete log and optional earlier same-lineage exact-byte-prefix base; checks sequence beyond-head/below-history-floor; requires timestamps for timestamp selection; copies only complete frames through the cut; rewrites lineage; and fully validates publication (`src/logops.rs:88-187`, `RestoreTarget`, `is_prefix`). The optional base is a proof/bound, not a magical delta-restoration engine. A backup plus arbitrary later segment files is not directly accepted by this API: reconstruction of a complete valid log/chain would need orchestration and coverage verification.

Directory stores do not support commit timestamps (`docs/STORAGE-FEATURES.md:394-398`; converter refusals `src/maintenance.rs:204-247`). Checkpoint history floors invalidate earlier restore/feed/export targets. Retaining a newer compacted image alone cannot provide arbitrary historical PITR. Pre-compaction timestamps/history need their own retained chain (`docs/STORAGE-FEATURES.md:66-74`).

### 4.3 Admin restore selection is restart-only, not failover

`admin::restore` accepts a safe generated backup name and mutually exclusive sequence/timestamp; creates a new `restore-*` copy and does not change the live owner (`src/server/admin.rs:1190-1248`). `select_restore` validates, writes a synced `next-startup` marker, then syncs the directory (`:1256-1277`). `selected_database` checks that marker and the selected generated copy, rejects invalid/torn files, and keeps selection across subsequent restarts (`:1279-1307`). CLI `open` uses this path and only creates a missing positional database if no selection was supplied (`src/bin/vlite-server.rs:522-578`). No silent fallback is the intended behavior.

A failed selection can leave a previous marker intact; a post-marker-replacement directory-sync error can mean visible-but-uncertain new selection. The original source is not overwritten. Reversing selection is an operator procedure, not distributed rollback or promotion; after either side accepts new writes, two files can diverge.

## 5. Log export, follower apply, handoff, retry, and crash recovery

### 5.1 Export path and mutation coverage

REST `GET /v1/admin/replication/export` -> `features::replication_export` -> `Service::run` -> `Database::export_log(after,max)` -> `read_segment` -> `LogSegment::to_bytes` -> base64 JSON (`src/server/features.rs:791-826`). It returns lineage/base/last/head as decimal strings. Budget default is 1 MiB, accepted 1..16 MiB, **soft** because whole commits are retained; one large commit and JSON/base64 overhead can exceed the requested budget. Source log scanning continues to determine/validate the head (`src/logops.rs:326-426`).

`export_log` forces periodic data sync and serializes scans with `log_scan` (`src/lib.rs:2574-2596`). Offline `export_log_segment` opens a closed/copied source under maintenance locking (`src/logops.rs:430-439`). It is not a way to bypass a live primary's exclusive file lock.

Raw frames include committed vector puts/deletes/metadata/TTL, collection create/drop/settings, batches/import marker state, named/sparse/vector-version mutations, graph creation/drop/schema/batches including cross-collection vector mutations, attachments, deadlines/reclamation, and supported logged temporal entries. They use the normal loader, not handler re-execution (`src/format.rs:2106-2339`; `src/vectors.rs:613-632`; `src/property_graph/frame.rs:197-266`). This avoids regenerating revisions/IDs, rerunning CAS conditions, external inference, audit side effects or logical-feed filtering.

Do not reconstruct replication from `/v1/changes`: that route presents event projections and filters reserved data (`src/server/features.rs:64-87,97-130`); full raw replay has more storage semantics. Likewise per-page vector exports are not consistent database snapshots (`src/dashboard/index.html:242`; `proto/vlite/v1/vlite.proto:58-61`).

Crucially, `replication_export` refuses when `memory_bindings` is nonempty **before** work (`src/server/features.rs:801-803`). `docs/SECURITY.md:66-97,117-126` also documents refusals when persisted binding records reserve resources after configuration removal. `metrics_with_memory` does not lift replication refusal (`:101-109`). Library export can carry these graph bytes, but a new operational replication principal/channel must be designed explicitly; widening ordinary tenant/read permissions is not a safe workaround.

### 5.2 Segments, continuity, idempotence

`LogSegment` contains exact file header/encryption descriptor, lineage, base sequence, last included sequence, advertised source head, and raw frames (`src/logops.rs:214-249`). Serialization includes magic, lengths and SHA-256 over metadata/header/frames; `from_bytes` validates lengths/digest (`:256-322`). Encryption preserves ciphertext frames, with actual database key needed for follower replay. Unkeyed SHA-256 is integrity against accidental/tampered-in-transit bytes only when compared to a trusted source; a hostile publisher can recompute it. No transport security is supplied by segments.

`ReplicaFollower::create` only accepts base zero, writes header+frames to a new file, syncs, opens/replays, verifies final sequence/lineage, and best-effort removes failed output (`src/replica.rs:40-82`). Directory/checkpointed primary bootstraps instead need `maintenance::backup` copied at S and `ReplicaFollower::open` retaining lineage. `restore` generates a different lineage and is not interchangeable.

`apply` requires exact lineage, exact `base_sequence == applied_sequence`, and exact header bytes (`src/replica.rs:140-162,202-215`). Gaps, duplicates of already-applied nonempty segments, foreign lineages and header changes are refused. **Not idempotent by replaying the same nonempty request**: retry must first establish the follower's durable current sequence and request the suffix from there (`tests/replica.rs:90-147`). Empty segments are status observations, not new commits.

These checks do **not** prove that two already-diverged, same-lineage logs have an identical prefix: there is no preceding-prefix digest or leadership term in `LogSegment`/`apply`. If two raw clones accept different commits through the same sequence, a later otherwise-valid suffix can pass lineage/header/base checks without detecting every historical difference; replay may catch a particular invariant violation, not arbitrary divergence. This is a static protocol limitation, not an executed corruption scenario. The exact-byte-prefix proof in PITR is stronger in this respect (`src/logops.rs:138-156`) and is not performed by follower apply. Fencing/reseed decisions must prevent this condition rather than assuming sequence parity detects split brain.

`read_segment` errors when cursor is ahead, or before an `OP_ADVANCE` checkpoint floor; complete commits remain unsplit (`src/logops.rs:349-361,394-421`). It offers no server-registered consumer ACK, durable retention pin or old-segment archive. Directory checkpoint install deletes obsolete files when manifest publication is durable (`src/directory.rs:739-783`); a lagging follower must bootstrap if history is lost. For single-file logs, growth persists until maintenance rather than a bounded shipping spool.

**Header-transition investigation:** checkpoint image creation enables `FLAG_HISTORY` and rewrites header context (`src/maintenance.rs:940-985`, `write_v5_image`); follower checks exact header. A follower started before the first checkpoint cannot be assumed to continue merely because its sequence is >= floor and lineage is unchanged. Establish exact supported transitions (initial checkpoint, later checkpoints, encryption/feature flags and compact images) with focused tests. Current inspected directory tests establish revision/lineage/feed-floor behavior, not an operational uninterrupted shipping contract through every transition.

### 5.3 Apply durability and failure behavior

`replica_extend` appends at prior valid end and calls `sync_all`, fully reloads, rejects incomplete tail, wrong last sequence/lineage/flags, and only then installs collections/imports/high-water/commit-times/graph (`src/lib.rs:2602-2654`). Success discards HNSW/rebuild state through `Collection::from_loaded`; apply cost includes full historical replay and index reconstruction.

On failure, it attempts truncate to prior end + sync; if rollback fails it poisons the database (`src/lib.rs:2655-2663`). The returned error may be the original failure; callers must not assume a rollback I/O failure left a healthy handle. Data state is installed atomically only after successful validation. `apply` updates its advertised primary head before calling `replica_extend`, so a failed segment can affect lag telemetry without advancing applied data (`src/replica.rs:154-160`).

`ReplicaFollower::open` uses internal Full-durability open, detects/discards an incomplete tail, then reopens, requires supported lineage/resident data, and initializes `primary_head` to local sequence (`src/replica.rs:84-111`; `src/lib.rs:1180-1188`). Applied position is reconstructable from the file rather than an independent cursor. The latest known source head is **not persisted** and is forgotten on restart. Newly reopened status can show zero lag with no contact to the primary.

A process dying mid-segment can leave a complete commit prefix followed by an incomplete frame. Reopen keeps valid complete commits, discards the incomplete tail, and reports the reconstructed sequence; that may be ahead of the last network response. A lost ACK is therefore not safe reason to blindly replay the old request. Corrupt complete frames are not equivalent to an incomplete tail and are not generally auto-truncated.

`LogSegment::save` uses a fixed `<path>.part`, syncs and renames but does not sync the parent directory (`src/logops.rs:256-269`). This is useful local shipping serialization, not a concurrent durable archive protocol: unique ownership, concurrent writers, Windows replacement semantics and directory-entry durability remain caller concerns.

### 5.4 What is not replicated

Not replicated by `LogSegment`/`ReplicaFollower`: membership; network credentials; bootstrap/admin/read-only bearer tokens and revocation generation; scoped credential JSON/revocations; tenant JSON/tombstones/suspension/limits; users/password hashes/versions; sessions/login throttles; webhook signing secrets/subscriptions/delivery checkpoints; audit logs; actual memory binding grants/config file; provider aliases/secret references/loaded secrets; TLS identities; scheduler policy/counters; server role/listener config; metric history; read snapshots; in-memory index readiness/background jobs; external ANN/disk-ANN files; external source systems; ownership/leader epoch; a remote backup catalog.

Canonical memory nodes/provenance/receipts and binding identity/digest records **are** graph data when committed. That is not replication of the corresponding external authorization or upstream source. See section 7 for restoration fidelity and permissions.

### 5.5 Server integration is missing

`Service::try_new` and its database owner hold `Database`, not `ReplicaFollower` (`src/server.rs:181-198,245-263`; normal `run` accesses that database). CLI `open` opens/creates an ordinary database and has no follower role (`src/bin/vlite-server.rs:522-578`). `src/replica.rs` methods are library entry points; the inspected server/bin call graph contains export only. A read-only ordinary `Database` can be served but cannot simultaneously be an externally extended live file under the same exclusive ownership model without new coordination.

The proto defines `ReplicaInfo` and `is_replica`, but gRPC `Info` hardcodes `is_replica:false`, `replica:None` (`proto/vlite/v1/vlite.proto:585-595`; `src/server/grpc.rs:2248-2275`). The service declaration has Changes/WatchChanges/vector export but no apply/promotion RPC (`proto/vlite/v1/vlite.proto:22-67`). Field presence is not standby support.

## 6. Durability, crash windows, export retention, and supported RPO/RTO statements

### 6.1 Local ACK contract

`Durability::Periodic` writes the full frame to OS cache before ACK, with background sync; default interval 60 seconds, accepted 1 ms..60 s. Full syncs each commit before ACK; None is in-memory only (`src/durability.rs:11-43,47-72`). Public opens reset mode to default; durability selection is not persisted (`src/lib.rs:1736-1757`).

`commit_frame` skips per-frame sync when grouped or periodic and marks the flusher written; otherwise it syncs (`src/lib.rs:2396-2419`). `commit_frame_with_sync` serializes optional time anchor/encryption, calls `append_and_sync`, then advances sequence/end (`:2474-2522`; append helper `:4295-4304`). Successful server mutations await their owner-locked operation (`src/server.rs:541-593`). Full durability is local storage durability only, not quorum or Azure durability.

The flusher tracks written/synced counters, stores sync failures, and exits on failure (`src/durability.rs:90-119,138-190`). Health checks reject poisoned/failed-flusher handles (`src/lib.rs:1695-1705`). `sync` forces pending acknowledged writes or reports `CommitIndeterminate` (`:1808-1829`). Writes can be complete and replayable after an unacknowledged I/O failure: report indeterminate, reconcile state, do not equate an error with rollback.

Group commit batches fsync opportunities but is not one atomic multi-request transaction. In periodic mode it still follows periodic durability rather than silently making every group Full (`src/lib.rs:2420-2472`). Exact atomicity belongs to individual batch/graph frames.

### 6.2 Shutdown and reopen

`Database::close` stops/joins rebuild, attempts checkpoint completion, syncs/stops periodic flusher with explicit failure reporting, then unlocks; Drop cannot report a sync error (`src/lib.rs:3918-3947`; `src/durability.rs:214-249`). `Service::close` shuts down group commit/webhooks/ops, waits for owner, takes the database and closes it (`src/server.rs:637-660`). A clean service shutdown is useful prior art, not proof that an external fencing lease remains valid throughout shutdown.

Tests distinguish abrupt process exit from storage/power failure. `periodic_commits_survive_a_process_crash` uses child `process::exit` while OS cache remains; it asserts 99 records/delete/payload after reopen (`tests/durability.rs:35-89`). `unsynced_suffix_loss_shapes_fail_closed_or_need_explicit_repair` writes truncated/zeroed fixtures: clean missing suffix opens, torn tail requires explicit repair, zero-filled suffix is Corrupt (`:130-181`). Neither demonstrates actual power-loss durability of Azure Files, a VM disk, Blob, or a storage controller.

Directory manifests are staged/synced/renamed; `publish_manifest` returns `Ok(false)` on post-publication directory-sync uncertainty, retaining old files rather than equating visibility with durable cleanup (`src/directory.rs:595-601,739-783,795-820`). Windows directory sync is a no-op (`:148-154`; also `admin::sync_directory`, `src/server/admin.rs:1248-1255`). Qualification must name platform/filesystem and failure model.

### 6.3 RPO/RTO that can and cannot be claimed

- **Can state:** Full local ACK follows local sync; periodic acknowledged suffix can be lost on OS/power crash (documented as about one interval under its assumptions). Export/snapshot force a synced source boundary. Follower successful apply syncs and validates locally before returning.
- **Cannot state:** a 60-second off-host RPO, a 5-minute maximum loss merely from minimum backup interval, zero-loss failover, or a bounded restore time. Busy skips, outage duration, backlog, checkpoint floors, disk/key loss and missing admin state can dominate.
- **Async data loss accounting:** within the same valid lineage/epoch/history, compare the primary's latest actually durable committed position with the chosen follower's validated durable applied position. The missing suffix is potential database loss; the last known primary head may be stale/unknown after failure. Control-plane loss needs separate accounting because it does not share database sequence.
- **RTO drivers:** discovering and authorizing the correct remote generation; credentials/key access; download size/throughput; full validation/replay memory; suffix scan/apply frequency; index warming; policy reconciliation; external fencing confirmation; routing/draining; process start and application probes. None was benchmarked here.

The baseline roadmap already separates visible/local-durable/replica-durable/object-published positions and warns against reading durability into `ReplicaStatus.primary_head` (`docs/projects/roadmap/scale-out.md:100-113`). Its async/fenced recommendation is prospective, not existing guarantee (`:274-304`).

### 7.2 Tenant lifecycle and authorization callers

Tenant create uses random immutable 32-hex ID and audit-before-commit (`src/server/tenants.rs:237-273`). Settings/suspend/resume go through shared owner-locked `mutate` and persist separately (`:341-367,410-468`). Delete refuses configured memory bindings, nonempty collections or graphs; removes tenant accounts first, tombstones tenant, audits and commits (`:275-337`). A crash between account deletion and tenant tombstone can leave partial cross-store progress, intentionally retryable, not one database transaction.

Authentication entry points: bearer `authenticate` handles bootstrap tokens or `Store::authenticate`, then tenant admission through `Store::get` (`src/server.rs:1048-1075`). Cookie sign-in checks origin, live session, enabled matching account version and tenant (`src/server/users.rs:1108-1175`). Transport-neutral `authorize_need` checks role/lineage/operation/reach and is shared with gRPC; route mapping is deny-unmapped (`src/server.rs:1095-1115,1230-1310`). `RequestScope::guard_collection` checks qualified name scope, reservation visibility, actual resolution, and lineage+ID/name coverage; graph guard checks tenant-qualified graph grant/reservation (`src/server/guard.rs:259-365`).

Tenant names are `t<id>__<local-name>`; isolation is policy over one file, not independent encryption/process/storage (`docs/SECURITY.md:521-549`). KV namespaces are application partitions, not authorization boundaries (`:442-451`). A raw backup/log segment therefore requires whole-database operator-level trust, especially for reserved memory data. Normal tenant read credentials must not become backup/replication authorities.

`Grant::covers` binds collections to lineage and ID/name; a dropped/recreated collection does not inherit access. Graph grants are names, so recreating a graph name is covered again (`src/server/credentials.rs:161-190`). This distinction matters for restore/rebootstrap testing, not just API compatibility.

### 7.3 What "source" means here

No first-class admin `/sources` CRUD/revoke registry was found in the inspected route modules/capability registry. Do not invent a persistent source-credential lifecycle. There are several different existing meanings:

- Memory `source_id/source_kind/uri/transformation_id` maps directly into `Provenance` (`src/server/memory/routes.rs:490-511`); it is data supplied with remember/consolidation, not an upstream access grant.
- Provider secret **sources** are config references to environment/private files (`src/server/providers.rs:129-133,305-350`), not runtime tenant source resources.
- Bootstrap token **sources** are CLI/environment/files and explicit reload/revoke-read-only handlers (`src/server/admin.rs:451-465,694-721`).

Memory source/provenance saved as graph content participates in raw graph replay; upstream connectors, source deletion/revocation and external data-retention requirements are not supplied by that metadata. Source-specific deletion/revocation expectations must be clarified before scope/effort can be estimated. A source revoked in another system is not automatically removed from old local/Blob backups.

## 8. Graph, KV, conditional writes, indexes, and recovery invariants

### 8.1 Canonical versus derived

Canonical database state is the validated file/chain plus its interpreted record/collection/vector/graph state. `Collection::from_loaded` retains records/revisions/expiries/settings/vector data, rebuilds metadata/text/sparse indexes, and resets HNSW/named HNSW/background policy (`src/collection.rs:132-182`). Index configuration can be canonical while a ready index is derived. Replication deliberately rebuilds rather than copying in-memory mutation buffers/jobs.

ANN sidecars are separate, identity/content-bound and may contain vectors; encrypted files refuse ANN/disk-ANN plaintext sidecars (`docs/STORAGE-FEATURES.md:49-53`; `src/lib.rs:3951-3965`). A follower with all data applied can still lack latency/recall readiness. Calling it warm requires measured exact/ANN serving behavior, not just `lag=0`.

Compact code present in this baseline must not be confused with unpublished production compaction work. Precision/source modules have explicit test/preactivation gates; release `precision_supported()` is false (`src/compact/mod.rs:36-68`). Existing compact reader fixtures and test-only writers are evidence of compatibility/failure checking, not deployment of a new source-codec architecture. No conclusions are imported from `c61aae9`.

### 8.2 Graph atomicity and replay

`commit_graph` allocates next sequence, validates graph body, encodes one graph frame, commits it, applies graph state then dependent vector mutations, poisoning on an impossible post-validation failure (`src/property_graph/mod.rs:808-830`). `commit_planned` operates on a planner, performs due-entity reclamation, orders graph/vector operations, refuses deletion of attached records, requires attachments to live nonexpiring records, and commits only after planning completes (`:1041-1169`).

Replay decodes all vector entries, validates collections/dimensions, atomically applies graph state, replays vector mutations, and confirms touched attachments refer to live records without expiry (`src/property_graph/frame.rs:197-266`). Graph checkpoint snapshots validate equivalent attachment invariants and carry graph IDs/schema/node/edge/attachment/high-water data (`:268-342`). This is concrete reusable data integrity, not a cross-host write fence.

Deletes and TTL reclamation are logged mutations where committed. Visibility expiry alone is not a new delete commit; followers preserve deadlines and apply their query clock. Equal sequence at different wall clocks need not yield identical TTL-visible results (`docs/STORAGE-FEATURES.md:195-209`; `src/collection.rs:146-149`). Preserve clock-aware comparisons, edge/node cascade, attachment ownership, graph schema and node/edge allocator high-water marks; never reconstruct from only live traversal output.

### 8.3 KV and CAS

KV uses ordinary one-dimension collection records with `[0.0]` vector and encoded namespace/key/value, a stable hash/probe window of 16 IDs, full-key equality and no persistent collision tombstones (`src/kv.rs:1-24,36-58`). It is therefore included in database backup and frame replication, not a separate store needing an independent copier. Delete frames are historical tombstones in the append log, while the live map removes revisions/expiry; checkpoint/compaction may eliminate old deletion history.

`KvStore::put_at` probes current state, checks requested version, uses the occupied/free slot's underlying revision to avoid overwriting a competing/colliding record, then writes an ordinary conditional record. `delete_at` uses matching revision; expired/missing behavior is deliberate (`src/kv.rs:419-489`). KV batches plan before one frame; supported limits/atomicity/no-expiry-in-batch are documented and coded in `KvStore::commit`/batch planner (`src/kv.rs:493-575`; `src/kv/batch.rs:95-176`).

Engine `Expected::{Any,Absent,Revision}` checks current revision (`src/lib.rs:866-886`); put/delete check before frame write, then commit/apply (`:2098-2230`). REST `precondition` validates one strong ETag under the same owner lock and turns it into `Expected::Revision` (`src/server.rs:2290-2340`). These stop concurrent writes to the same **local** state, not two hosts starting from the same prefix.

Important nuance: docs broadly say maintenance rewrites KV revisions, but full `restore_inner` copies frames and changes lineage, so numeric revisions may survive a restore (`src/maintenance.rs:411-446`). Header-bound/ETag/grant identity checks and application re-read requirements still matter. Raw numeric CAS is not a globally never-reused leadership token; two divergent copies can both satisfy it. Directory checkpoints specifically preserve revisions (`tests/directory_store.rs:84-160`).

### 8.4 Replay side effects and recovery trade-offs

Raw log replay invokes format/graph state application, not REST handler code. It does not call provider inference or recreate request audit. On the other hand, starting a **server** on recovered data may provision memory binding records/scopes on writable startup (`src/server/memory.rs:65-75,98-150`) and starts a webhook worker when configured (`src/server/webhooks.rs:58-98`). A recovery validation harness must isolate/disable external effects and treat read-only startup differently from writable activation.

Logical forget/TTL does not erase retained historical copies. Backup/log retention, external caches and key retirement determine whether old bytes still exist. The baseline dashboard says this explicitly (`src/dashboard/index.html:396`), and scale-out recommendations warn about retained-copy erasure (`docs/projects/roadmap/scale-out.md:123-129`). Do not claim deletion propagation to Blob merely because a delete reached the follower's current map.

Dependency distinctions: Blob backup and standalone async shipping can each start from existing locked backups; neither requires implementing unrelated local branching first. A remote publication catalog and a fencing authority are related operationally but not the same mechanism. Performance optimization, lazy remote reads and synchronous ACK replication are not prerequisites implied by this research and should not be smuggled into scope.

Important trade-offs to bring into design review:

- Packed full snapshot is simpler to validate/transport but consumes full-copy space/time; reusing immutable directory segments reduces repeated transfer but increases catalog/pinning/history/GC complexity.
- Database-only backup with separately reprovisioned policy is simpler than atomic all-state recovery, but cannot claim transparent identity/credential continuity. Copying sidecars verbatim instead risks stale revocations, webhook replay and secret exposure.
- Keeping current Full follower apply durability is reusable, but full replay after every segment trades catch-up latency/memory/index readiness against large batches and stale reads.
- Infrastructure/manual fencing is a narrower initial safety boundary than automatic failover; an application lease without enforceable stale-writer rejection is not an equivalent substitute.
- Azure Blob backup durability, Azure Files shared filesystem behavior and native local disk durability are three different qualification problems. `deploy/azure-container-apps/README.md:16-32` explicitly says its Files probe does not establish cross-host locking/power-loss performance; it recommends VM/AKS managed disk if the probe fails.

## 13. Prioritized open design questions

1. **P0 - Fencing authority and fault model:** Which independent durable authority or infrastructure action proves the old host cannot write? What happens on authority partition, lost response, long GC pause, process resume, credential/config mutation and background side effects? Where is stale epoch enforced, not merely observed?
2. **P0 - Recovery scope and authorization freshness:** Is the deliverable database recovery with mandatory reprovisioning, or complete serving recovery? How are tenant tombstones/suspension, credential revoke/rotate, user disable/password resets, actual memory grants, secrets and webhook effects brought to a safe common boundary before serving?
3. **P0 - Memory replication permissions:** The current server refuses whole-log export with memory bindings/reservations. What privileged internal mechanism is acceptable without weakening reserved-resource/tenant protections or treating ordinary read access as backup authority?
4. **P0 - Promotion and loss accounting:** What exact source/follower/policy positions are proven for planned handoff? What can be disclosed when the failed primary's final head is unknown? Who authorizes choosing a potentially stale prefix, and how is the losing suffix preserved for investigation?
5. **P1 - Identity and checkpoint handoff:** Which lineage/header/capability/floor transitions require reseeding? Can a pre-first-checkpoint follower continue after header/history changes? What is the accepted bootstrap snapshot-to-log coverage proof?
6. **P1 - Azure provider contract:** Which Blob API/client/auth identity is approved, and which conditional publication, immutable version, digest, listing, retry and ambiguous-write semantics will be tested? Does remote-head ownership need an epoch distinct from storage ETag CAS?
7. **P1 - Retention/backpressure/privacy:** How long may a disconnected follower pin history? What are local backlog bounds on cloud outage, and when is rebootstrap required? How do remote GC, active uploads/readers, PITR chains, deletion requests and old-key retirement interact?
8. **P1 - Encrypted recovery end-to-end:** How will key-aware admin verify/drill/selection/startup be qualified, and how are keys made independently recoverable without exposing them in report/log/config backups?
9. **P1 - Failback/rejoin:** How is the old primary isolated and reseeded, with no silent merge or reuse of stale ownership? Which canonical owner/epoch is authoritative after restore or rollback?
10. **P2 - Read and readiness contract:** Are standby reads stale-by-sequence, bounded-by-age, or minimum-position gated? How is TTL clock skew handled, and what separate exact/ANN readiness gates determine "warm"?
11. **P2 - Operational evidence:** Which measurable data sizes, write rates, outage lengths, recovery hosts/filesystems and key-access scenarios will support RPO/RTO targets? Who runs/owns periodic isolated service-level recovery and external-fence qualification?
12. **P2 - Ambiguous source requirements and baseline cleanup:** Does "source" mean provenance, external connectors, provider secret sources or a new resource lifecycle? Which documented permission/format/drill mismatches must be resolved before operator workflows are relied upon?
