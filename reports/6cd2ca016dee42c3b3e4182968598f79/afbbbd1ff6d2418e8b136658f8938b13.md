## Findings, severity ordered

### HIGH H1 — Successful collection can write an unreadable startup state

**Location/symbol:** `src/server/backup_policy.rs:33,243-256` (`MAX_FILE`, `read_limited`), `430-434` (`Runtime::update`), `809-830` (`Runtime::collect_with`); startup propagation at `src/server/admin.rs:412`.

**Impact:** A valid operational result can make the entire configured server fail startup, not merely disable cloud backups. The reader limits `state.json` to 65,536 bytes, while the writer persists the complete unbounded collection report, including each deleted set ID.

**Executed evidence:** `review_repro_large_collection_prevents_restart` configured retention with `keep_sets=1`, `keep_days=0`, published one real fake-store set, then inserted 2,000 older valid-shaped published coordination records using the existing `Memory::set_raw` fixture. `Runtime::collect` returned success with 2,000 deleted IDs and wrote a **90,707-byte** `state.json`. `Runtime::open_with` then failed with `state.json is too large`. This is a metadata-only scale fixture, not a real Blob storage or production-volume test. The protocol permits 10,000 active sets (`src/server/cloud_backup.rs:36`).

**Concrete fix:** Persist bounded summaries/counts and a bounded sample of set IDs; keep full reports separately if needed. Enforce the reader's size limit before replacing any durable file, and ensure the maximum permitted collection remains restartable. Merely returning an error after replacing the state is insufficient.

### MEDIUM M1 — New request parsers reflect arbitrary input in error responses

**Location/symbol:** `src/server/backup_policy.rs:988-993` (`configure`), `1042-1048` (`restore`); `src/server.rs:2081-2085,2114-2126` (`body`, `optional`).

**Impact:** The requested no-input-echo/sanitized-error property is false. Mistakenly submitted secret text can be reflected in JSON errors. This is administrator-visible reflection, not a demonstrated tenant authorization bypass or theft of a process-held credential.

**Executed evidence:** `review_repro_error_echo` submitted a policy with an unknown field named `FAKE_SECRET_REVIEW_MARKER`, and a restore body `{"mode":"FAKE_SECRET_REVIEW_MARKER"}`. Both JSON error bodies contained that exact synthetic marker. The generic helpers forward `JsonRejection::body_text()` and serde errors, which include unknown field/enum values.

**Concrete fix:** Give these routes fixed public parse-error messages/codes; discard parser text containing input. Cover policy, nested target/auth, restore mode, unknown fields and wrong types. Do not copy raw parse diagnostics into status, audits or logs.

### MEDIUM M2 — Public unpin can remove a live restore's protection

**Location/symbol:** `src/server/backup_policy.rs:882-891,904-928,1090-1106` (`Runtime::unpin`, `Runtime::restore`, `unpin` handler); `src/server/cloud_backup.rs:364-368,1113-1157` (`Pin`, `Sets::pin`, `Sets::unpin`).

**Impact:** Restore/drill operation pins are indistinguishable from manually removable holds. Listing exposes their IDs and DELETE can remove them while the consumer is live; collection can then delete the source during download. The caller must be super-admin: this is a destructive concurrent-operator/API correctness issue, not tenant escalation.

**Executed evidence:** `review_repro_active_restore_pin_can_be_deleted` published two sets and enabled `keep_sets=1,keep_days=0`. A fake-store hook paused the old set's restore at manifest GET, after `fetch` checked its pin. The hook listed the active pin, called the same `Runtime::unpin` used by DELETE, then collected. Collection deleted the restore's source, and restore returned `cloud_set_corrupt`. No stale-janitor race was needed.

**Concrete fix:** Distinguish operator holds from consumer-owned pins. Refuse ordinary DELETE of a live operation pin; release it only with its operation ownership token. Provide an explicit, audited crashed-owner recovery/override path rather than allowing every visible pin to be silently removed.

### MEDIUM M3 — Policy and scheduling/pending state are not one atomic generation

**Location/symbol:** `src/server/backup_policy.rs:464-495` (`Runtime::configure`), especially the separate replacements at `489-490`; `353-368` (`Runtime::open_with`).

**Impact:** Individual files are atomically replaced, but the configuration transaction is not. A crash or second-write failure leaves a new policy with old pending/schedule state. A failed PUT can leave the old in-memory policy active while restart activates the new durable policy, including its enabled/retention settings.

**Executed fixture evidence:** `review_repro_crash_between_policy_and_state` created an unknown publication on prefix A, saved its state, configured prefix B, then restored the saved state file to construct exactly the durable image between the two renames. Reopen accepted policy B plus A's pending handle. The next run looked up that handle in B and reported it `lost`. This reconstructs a crash boundary; it is **not** an actual process-kill or filesystem fault-injection test.

**Concrete fix:** Store policy and operational state in one versioned atomic document, or use generation files plus one durable selection pointer. Bind pending handles to the target generation. Define recovery for an uncertain PUT rather than allowing disk and memory to diverge without reconciliation.

### MEDIUM M4 — Persisted wall-clock timestamps can suppress backups after rollback

**Location/symbol:** `src/server/backup_policy.rs:327-338` (`next_run`), `513-528` (`claim_due_at`).

**Impact:** A forward clock error followed by correction, including across restart, can postpone all scheduled backups for the duration of the error. The due time is the persisted wall-clock attempt/policy timestamp plus interval, with no future-timestamp reconciliation.

**Executed fixture evidence:** `review_repro_clock_rollback_defers_runs` persisted a last-attempt timestamp one year ahead, reopened, and invoked `claim_due_at` with the corrected clock. Claims remained false until the future timestamp plus the 300-second interval. No machine clock was changed.

**Concrete fix:** Use monotonic elapsed scheduling within a process and explicitly reconcile future persisted timestamps on startup/clock rollback. Bound the delay to an interval or enter an explicit unhealthy-clock state with operator-visible failure; do not silently suppress backups for an arbitrary period.

### MEDIUM M5 — No durable job lifecycle; panic/shutdown outcomes are untracked

**Location/symbol:** `src/server/backup_policy.rs:116-135` (`Status`), `526-543` (`claim_due_at`, `start_claimed`), `565-573` (`cycle`); `src/server/ops.rs:283-296` (`Ops::shutdown`).

**Impact:** ITEM-006 calls for persisted jobs and crashed-owner reconciliation. Here `busy` is process-local, attempts are initially changed only in memory, and there is no durable running/interrupted job identity. A worker panic releases the busy guard but records no failure. Shutdown joins the scheduler, not its detached cloud-operation thread; an operation may continue after shutdown returns.

**Executed evidence:** `review_repro_panicked_run_has_no_durable_job` injected a synthetic connector panic and caught it at the test boundary. `running` became false, but `failures` remained zero; reopening showed zero runs and no last attempt. The shutdown observation is static inspection, **not** a shutdown-under-upload runtime test.

**Concrete fix:** Durably admit a job ID/phase before remote work, mark interrupted owners on reopen, and finalize failures through a panic-aware boundary/guard. Track scheduled operation handles and define bounded join/cancellation behavior at generation shutdown. Keep this on the existing scheduler rather than adding another scheduler.

## Confirmed-good behavior and design trade-offs

- **Authorization:** Every explicit method/path above falls through to `Need::Admin`; scoped grants cannot satisfy it, and read-only tokens cannot call `/v1/admin/*` (`src/server.rs:1287,1332-1367`). Authentication/authorization occurs before handlers (`1459-1521`). An isolated **full configured router** test exercised all nine operations with a global scoped backup credential, a tenant scoped credential and a read-only token: **27/27 returned 403**; super-admin GET status returned 200. This is stronger than the committed cloud route test, which mounts only `routes().with_state(...)` and bypasses auth (`backup_policy.rs:1652-1664`). No tenant data exposure was observed.
- **Capabilities:** All eight distinct templates match the registered routes. The added capability is a Boolean; no target, key or token is included (`admin.rs:638,690-697`). A configured admin directory advertises the feature even for an unsupported source; execution separately refuses unsupported sources. This is presence, not a successful-backup/readiness signal.
- **Credential handling:** Policy/Target use unknown-field rejection, expose no key/SAS/token field, and reject URL query/fragment/userinfo. Managed identity is restricted to the exact account public Blob endpoint (`cloud_backup.rs:169-249`); redirects are disabled (`cloud_backup/azure.rs:140-149`). The emulator key is read from the process key-file environment setting, not serialized in Policy (`backup_policy.rs:296-304`). Static inspection found no new normal-path serialization/logging of the actual credential. M1 prevents a blanket no-secret-in-errors claim.
- **Bounds/defaults:** Interval 300..604800 seconds, keep sets 1..1000, days 0..3650, orphan grace 1..720 hours, drill cadence 0..100. Defaults are 3600 seconds, three sets, 30 days, 24-hour grace and every 24th publication (`backup_policy.rs:37-105`). Nonzero keep-set validation exists; retention also protects the newest successful drill (`cloud_backup.rs:1523-1538`). This review does not certify the separately excluded cross-janitor last-survivor issue.
- **Startup/files:** Invalid JSON, invalid policy bounds, missing/invalid installation identity and structurally invalid state fail open/startup; stale staging is cleared (`backup_policy.rs:348-387`). `write_atomic` writes a temporary file, syncs it, replaces the named file and syncs the directory (`275-282`); that protects each file, not M3's multi-file transaction.
- **Permissions:** Persistence uses `NamedTempFile`; no explicit private-directory permission creation/check is added. Directories use `create_dir[_all]`, so privacy depends on the protected admin-directory ancestor and platform defaults. That precondition is documented at `docs/SECURITY.md:3-6`. Unix mode/umask and Windows ACL enforcement were not measured. `sync_directory` is Unix-only and a no-op on Windows (`admin.rs:1322-1330`); Windows test success is not Unix crash-durability evidence.
- **Overlap/pins:** `busy.swap` plus RAII guards serialize run/collection/policy changes and release on unwinding (`backup_policy.rs:146-159,395-404,505-562`). Drills/restores intentionally run concurrently using remote pins; pins do not expire (`cloud_backup.rs:1111-1113`), avoiding unsafe timer-based deletion. Pin-vs-delete is per-record CAS. Crash-left pins can block retention indefinitely; operator reconciliation is needed and must preserve M2's live-owner distinction.
- **Restore isolation/path handling:** Set and pin IDs are checked before use (`backup_policy.rs:969-975,1094-1097`; `cloud_backup.rs:282-295`). Restore uses a generated admin-directory filename, not a caller path, and does not select or replace the live database (`backup_policy.rs:904-936`). `maintenance::restore` changes lineage and publishes without clobbering (`src/maintenance.rs:391-446,718-765`). Existing tests confirm new lineage, contents, released pin, seed-mode refusal and malformed IDs. Drill uses temporary download/scratch directories.
- **Run-now semantics:** Simultaneous runs are excluded, but a completed POST retry is not idempotent and creates another set; there is no request idempotency key or job-lookup endpoint (`backup_policy.rs:559-562,709-711,1001-1006`). This should be documented or replaced by durable keyed submission if callers must retry uncertain HTTP outcomes without creating another backup. Pending-publication resolution alone does not provide POST idempotency.

### Reproducer reconstruction

The review probes were appended only to the existing `backup_policy.rs` unit-test module in a disposable copy, reusing its `setup`, `policy`, `target`, `connector`, `status`, `set`, `call`, `reopen`, `BASE` helpers and existing `Memory`/`Op` fixtures. The key H1 scale loop was:

```rust
let env = setup();
let h = Handle::new(&env.service);
env.runtime.configure(policy(json!({
    "drill_every": 0, "retention_enabled": true,
    "keep_sets": 1, "keep_days": 0
})), &h, BASE).unwrap();
let id = env.runtime.run_now(&h).unwrap()["set_id"]
    .as_str().unwrap().to_owned();
let template = env.meta.raw(
    &format!("vlite/prod/sets/{id}/record.json")).unwrap();
for i in 0..2000u64 {
    let old = cloud::new_set_id(BASE + i).unwrap();
    let mut record: cloud::Record =
        serde_json::from_slice(&template).unwrap();
    record.set_id = old.clone();
    record.created_unix_ms = BASE + i;
    record.updated_unix_ms = BASE + i;
    env.meta.set_raw(&format!("vlite/prod/sets/{old}/record.json"),
        &serde_json::to_vec(&record).unwrap());
}
assert_eq!(env.runtime.collect(&h).unwrap()["result"]["deleted"]
    .as_array().unwrap().len(), 2000);
assert!(std::fs::metadata(env.root.join("cloud-backup").join(STATE))
    .unwrap().len() > MAX_FILE);
assert!(Runtime::open_with(env.root.join("cloud-backup"),
    connector(&env.meta, &env.data)).is_err());
```

For M2, use two ordinary `run_now` publications before enabling one-set/zero-day retention. Register `env.data.hook(Op::Get, "/manifest.json", ...)`; inside the hook list the older record's first pin, call `Runtime::unpin`, then `Runtime::collect`. Invoke `Runtime::restore` for that older ID. The hook executes after the initial pin check and before manifest retrieval; assert the ID is deleted and restore errors with `cloud_set_corrupt`.

For M4, use `Runtime::update` to persist `last_attempt_unix_ms = Some(BASE + 365 * 86_400_000)` under an enabled 300-second policy, reopen, and assert `claim_due_at(BASE + 300_000)` is false and `next_run_unix_ms` equals the future timestamp plus 300,000. For M5, inject `Box::new(|_| panic!("synthetic connector panic"))` into `open_with`, catch the `run_now` unwind in the test, reopen, and assert no durable attempt/failure was recorded. M1 and M3 request/fixture sequences are specified in their findings above. None of these probes requires network access to Azure.
