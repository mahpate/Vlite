# ACA secret materialization without reading an existing token

**Status: INCOMPLETE for backend qualification; public-source research complete.**

**Decision:** No inspected first-party source establishes that a direct Container Apps PUT or PATCH can add five new `configuration.secrets` entries while preserving an existing inline token secret whose value the writer never reads. Direct REST permits constructing a request without calling `listSecrets`; that is a client property, not a preservation guarantee. Do not implement or qualify a production actuator on the strength of the OpenAPI shape, a name-only token entry, or the CLI's advertised "add secrets" behavior.

Research date: 2026-11-28. This report is independent of the repository implementation and any dirty HA work. No repository source, workspace snapshot, Azure account configuration, credential, or live secret was inspected. Five immutable reader file secrets and a separate existing token reference are assignment requirements, not an observed current deployment.

## 1. Documented contract versus the missing guarantee

For API **2025-07-01**, the documented resource endpoint is:

```text
https://management.azure.com/subscriptions/{subscriptionId}/resourceGroups/{resourceGroupName}/providers/Microsoft.App/containerApps/{containerAppName}?api-version=2025-07-01
```

PUT is `ContainerApps_CreateOrUpdate`; PATCH is `ContainerApps_Update`, described expressly as "Patches a Container App using JSON Merge Patch." Both accept a ContainerApp body, including `properties.configuration`; the inherited model requires `location`. The spec declares `application/json` as its consumed content type. None of these declarations explains preservation of omitted existing secrets or omitted secret values. [D3-D4; S1 lines 1-16, 148-223, 281-343; S3 lines 494-528]

`configuration.secrets` is an **array** of Secret objects. `Secret.value` is a string with `x-ms-mutability: ["create", "update"]` and `x-ms-secret: true`. The Secret definition has no `required` list and also exposes `name`, `identity`, and `keyVaultUrl`. This establishes a schema that can represent an entry with only a name; it does **not** establish that submitting such an entry retains a previously stored value. Nor does the schema document a name-keyed merge operation. [S1 lines 613-623; S2 lines 610-636]

The JSON Merge Patch description is meaningful but is not an ACA-specific exception for secrets. Microsoft's general guidelines distinguish PATCH from whole-resource PUT, warn that JSON Merge Patch array operations require the entire array to be read, and describe null in PATCH as a deletion instruction. Those guidelines provide reason **not** to assume append-by-name semantics for `secrets`; they do not prove how ACA's secret storage handles omitted or name-only entries. Do not infer either successful preservation or inevitable deletion from these general rules alone. [D4; S1 lines 281-343; G1 lines 152-158, 286-288, 408, 428]

The **2026-07-01** Learn PATCH page also describes JSON Merge Patch. Its listed URI parameters do not include a conditional header; its responses include `200` and `202`, with `Location` and `Retry-After` for `202`. This corroborates an available update operation, not secret-preservation behavior. The complete public 2026 OpenAPI contract was not retrieved at the pinned spec revision, so the detailed schema assessment above is deliberately limited to **2025-07-01**. [D5, operation/URI parameters/responses]

## 2. Client serialization is not server preservation

At CLI pin `c2569c88758233b17033f943b21ae5b70e8d992e`, `set_secrets` obtains the app, invokes `_get_existing_secrets`, merges supplied entries, and calls `create_or_update`. In the helper's existing-secrets branch, `ContainerAppClient.list_secrets` is called and the returned `secrets["value"]` replaces the in-memory secret collection. The merge helper updates matching names or appends new entries. [C1 lines 3171-3185; C2 lines 792-805, 819-833]

The corresponding low-level client sends a POST to `/listSecrets`; PUT and PATCH methods serialize the supplied envelope with `json.dumps`. Their visible method bodies do not call `list_secrets` before sending the supplied envelope. The pinned client selects API **2026-07-01**. Thus a hand-constructed direct request can avoid a client-side secret read, but reusing `set_secrets` cannot satisfy this assignment's no-token-read constraint for an app with existing secrets. A lower-level method's lack of a read does not confer backend preservation. [C3 line 19, lines 125-178, 274-287]

Learn says `listSecrets` returns plaintext values. The CLI reference's `secret list --show-values` default of false describes output behavior, not evidence that the mutation path avoids reading values. Similarly, "Add secrets" in CLI examples is not documentation of REST omission semantics. [D1, **Permissions for managing secrets**; D2, **az containerapp secret list**, **az containerapp secret set**; C1-C3]

No SDK was executed, and no SDK-specific serializer was qualified. The concrete serialization finding here is for the pinned CLI low-level client, not every SDK, shell, or HTTP library.

## 3. Endpoint, ETag, and concurrency assessment

The entire `paths` collection of pinned S1 was enumerated. In that file, secret materialization is exposed through resource PUT/PATCH; `/listSecrets` is a read action. There is no separately declared per-secret create/update endpoint, append-secret action, or JSON Patch-by-secret-name operation. This is a bounded absence finding for **that file/version**, not a claim about every Microsoft.App child resource or future version. [S1, complete `paths` collection, lines 17-611]

Neither the inspected GET/PUT/PATCH parameter and response declarations nor the inherited Resource/TrackedResource definitions document `ETag`, `If-Match`, `If-None-Match`, a secret generation precondition, or a lock/lease for these updates. A complete lexical scan of S1 and S2 found no actual ETag or conditional-write declaration; unrelated resource-tag text is not an ETag. The inspected Learn request/response sections likewise did not supply a conditional-write contract. [S1 lines 99-223, 281-343; S2; S3 lines 366-394, 494-528; D3-D5]

Microsoft's general guidelines recommend conditional headers and explain their role in avoiding concurrent-update data loss. This is **not** proof that ACA honors an arbitrary `If-Match` header, returns a usable ETag, or advances a token covering secret mutations. `systemData` metadata is also not documented as a compare-and-swap token. [G1 lines 174, 1193-1195; S3 lines 387-390]

Asynchronous completion mechanisms do not provide concurrency control: S1 marks PUT and PATCH as long-running, PUT specifies `azure-async-operation` as its final-state mechanism, and PATCH declares a `202 Location`. The pinned CLI polls operation responses. These can acknowledge operation progress/completion; they do not establish the landed secret bytes or preservation of a concurrently rotated token. [S1 lines 219-222, 322-342; C3 lines 140-145, 164-176]

**Result:** No inspected documented mechanism jointly guarantees new-secret materialization, no existing-token read, token preservation, and concurrency-safe updates. ETag support and its secret-mutation coverage remain UNKNOWN, not proven absent in the backend.

## 4. Revision and file-secret consequences

App secrets are outside revisions, and adding/removing/changing them does not generate a revision. Updated/deleted secrets do not automatically affect existing revisions; the conceptual docs prescribe deploying a new revision or restarting an existing one. Template changes, in contrast, define immutable revision state and produce a new revision. Old revisions therefore cannot be assumed to provide rollback isolation for changes to app-scoped secrets. [D1, introduction; S1 lines 822-829; S2 lines 637-695]

Secret volumes can select specific secrets and paths. In the pinned schema, omitting the volume's selected-secret list projects all secrets in the collection. For the assigned five reader files, the design should explicitly select those five `secretRef` entries and paths, keeping the token's existing reference separate and excluding it from the reader-file volume. This is a proposed boundary, not an inspected implementation. A secret reference or volume projection does not itself create an app-level secret. [D1, **Mounting secrets in a volume**; S2 lines 696-751, 19-36]

For a Key Vault-backed alternative, versioned URLs provide version selection; versionless references retrieve newer versions within 30 minutes and automatically restart active revisions referencing the secret in environment variables. These documented rotation behaviors are distinct from inline-secret PUT/PATCH semantics and cannot be silently substituted into the current prerequisite. [D1, **Key Vault secret URI and secret rotation**]

## 6. Conditions before a real actuator

Obtain an ACA-specific preservation and concurrency contract for the exact API/version and token storage mode, or explicitly acknowledge those unknowns and arrange separately authorized controlled qualification before any production decision. Pin the method, media type, serializer, body shape, environment, and qualification evidence. The no-read identity boundary must exclude plaintext-secret read paths; restrictive permissions do not by themselves prove a write preserves existing secrets. [D1, **Permissions for managing secrets**; S1-S3; C1-C3]

If no conditional-write guarantee can be established, a cooperative single-writer/fencing design must include **every** app configuration writer and token rotator for the entire asynchronous update and reconciliation interval. A local lock among reader-materialization workers alone cannot protect against an external rotator. This is a design recommendation, not an ACA lock feature or a waiver for production gates.

Prefer minimal-field PATCH as a candidate to reduce unrelated stale-body replay, but do not mistake that smaller scope for proven array merge or secret preservation. Consider a separately owned reader app or an explicitly approved Key Vault-reference architecture if token isolation cannot be met. Those alternatives trade shared-token mutation risk for additional identity, deployment, reference, and lifecycle responsibilities; neither is an automatic replacement for this prerequisite.

## 7. Minimal future controlled qualification matrix

**Proposal only: not execution instructions, authorization, or approval.** Use a disposable, explicitly authorized nonproduction app and synthetic token managed by an independent fixture owner. The prospective actuator must never obtain the token value. A trusted consumer may consume its normal secret reference to demonstrate successful token use without returning the value, a value hash, or logs containing it to the actuator/researcher. Qualify file payloads inside the consumer with an exact-byte comparison against non-sensitive fixture manifests and return only per-file pass/fail. This is consumer qualification, not a control-plane secret read.

| Case | Proposed controlled variation | Required evidence and decision boundary |
| --- | --- | --- |
| 1. Preservation/materialization | Separately assess PUT and PATCH, each with (a) five new entries and token omitted, (b) five new entries plus a name-only token entry. Start from equivalent disposable states. | Independently prove the token remains usable and all five files have the exact intended landed bytes, correct paths, and no accidental token projection. Record rejection/clearing/removal explicitly. No outcome is presumed. |
| 2. Replay and ambiguity | Repeat the selected candidate with identical immutable file names/payloads; include a lost/unknown acknowledgement outcome. | Distinguish accepted, pending, terminal, and unknown outcomes. Reconcile through authorized operation metadata and consumer attestations, never `listSecrets`; do not treat timeout as failure or acknowledgement as content proof. Hold unknown outcomes rather than advancing a production gate. |
| 3. Revision boundary | Assess secret-only materialization independently from the template change selecting the five files; observe an existing revision and a newly deployed or restarted controlled consumer. | Establish secret-only revision behavior, consumer freshness, exact mounted bytes, old-reference usability, and whether any propagation/restart is required. Do not infer preservation solely from an already-running consumer caching an old token. |
| 4. Rotation race | Independent fixture owner rotates the token before, during, and after file materialization; include stale-body replay. Test any proposed conditional mechanism only after its contract is identified. | A freshly started/restarted trusted consumer must use the intended final token generation; verify no lost rotation, stale value/reference restoration, or partial file set. If ETags are claimed, prove stale writes are rejected and secret-only rotations invalidate the precondition. Otherwise require verified fencing across all writers. |

Record exact API/version, method, request-field presence (without secret values), media type, serializer, operation identifiers/status, revision identities, and consumer pass/fail evidence. A result qualifies only its tested combination, not all PUT/PATCH variants or future API versions. Unresolved preservation, landed-content, acknowledgement, revision, or rotation-race behavior keeps the prerequisite **INCOMPLETE** and blocks a production actuator.
