VLite baseline measurements

VLite 0.3.0 baseline, not current-source performance. Embedded and REST measurements describe different execution paths and must be interpreted separately.

Shared WSL2 host, 16 vCPU Intel Xeon Platinum 8370C. Medians of three trials at 20k × 128 and two at 100k × 768. Seeded float32 Gaussian clusters (64 clusters, sigma=0.35, seed 42), squared L2, 200 top-10 queries and a tie-aware float64 oracle. HNSW M=16, ef_construction=100, ef_search=100; ten warmups and one sequential client. Server containers used 4 CPUs and 4 GiB. QPS is sequential queries/second, not maximum sustainable throughput.

HNSW traversal optimization (unreleased source)

A bounded visited-node bitmap replaces per-node hashing during graph construction and search on graphs up to 8,388,608 nodes. Each traversal owns one bit per node, rounded up to 64-bit words (at most 1 MiB); larger graphs retain a sparse hash set. This is not a bound on total traversal memory. On 5,000 synthetic 128-dimensional vectors, median rebuild time fell from 5.552 s to 5.080 s (8.5%), and the mean duration of two 100-query batches fell from 76.392 ms to 60.795 ms (20.4%).

Native Windows release build; squared L2, M=16, ef_construction=100, ef_search=100, k=10. One before/after campaign (three rebuilds and two query batches per version) on a shared host with warm caches, not per-query p50 or other latency percentiles, a universal gain. No 100k × 768, other-OS or sparse-fallback measurements were collected. Distance precision, graph-selection rules, filtering and durability are unchanged. Performance and operating model

VLite supports exact scans, rebuildable HNSW, optional scalar-u8 traversal, ANN restart snapshots, metadata indexes, shared-lock read-only opens and concurrent server reads. The live dataset resides in memory. HNSW build cost, high-dimensional search, binding overhead and mixed-write tail latency remain important optimization targets.

See VLite capabilities and the technical reference for contracts and limitations.

Reproduce and interpret results

The benchmark guide documents native campaigns, exact/ANN recall checks, filters, mixed updates, real embeddings and restart measurements. Published measurements retain workload-specific results and limitations.

cargo run --locked --release --bin vlite-bench -- 10000 32 100 100 10 42
cargo run --locked --release --bin vlite-bench -- --ann 16 100 100 10000 32 100 100 10 42

Record source revision, hardware, dataset provenance, dimensions, metric, recall, concurrency, latency percentiles, build/reopen cost and durability settings. Before/after campaigns must use the same workload and preserve raw samples; no single run establishes a universal speed claim.
