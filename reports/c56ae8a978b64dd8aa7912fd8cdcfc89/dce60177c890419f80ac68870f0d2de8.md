## Decision and first slice

Implement a **create-only seed-input/composition slice**, then integrate the independently developed validator/projection and readiness work. Keep a new tenant reserved, provisioning and publicly unrouted until its dedicated writer, seed identity, authority, archive, policy, credential delivery and freshness checks are verified. Do not add a shared writer route, migration, automatic reseed/rekey, automatic takeover, or qualification bypass.

The first patch owns `seed.rs`, the production portion of `worker.rs`, and the runtime threading in `tenant_provisioning/admin.rs`, with focused tests in `seed_tests.rs` and the existing inline worker tests. It adds explicit seed-source configuration, operation-bound staging/key resolution, and a caller of the existing `seed_create`. With no configured source or approved deployment evidence, it refuses **before claim and before any file/ARM side effect**. With all existing gates satisfied, it seeds using the claimed attempt, verifies the receipt and journals it before enabling the writer. It does **not** claim to activate tenants or make today's production preflight pass.

The smallest safe initial delivery can be limited to **explicitly unencrypted seeds on an already verified, durable dedicated staging mount**. An encrypted retained profile must refuse until its exact-version resolver is supplied; never reinterpret it as unencrypted. The source seam and its fail-closed tests can be implemented now without supplying qualification proofs. A usable deployed source, durable artifact handoff, and activation remain externally gated.

## Exact reusable ACA, administration and Blob inputs

### Administration and durable control state

The standalone ACA template has secret **`admin-token`**, exposed as **`VLITE_AUTH_TOKEN`**, and **`VLITE_ADMIN_DIR=/data/admin`** on its `/data` AzureFile mount ([`deploy/azure-container-apps/deploy.ps1:50-85`](../../deploy/azure-container-apps/deploy.ps1)). `server/admin.rs::load_control` loads audit, `credentials::Store`, tenant store and accounts from the private canonical admin directory; credentials/tenants require an admin token ([`server/admin.rs:286-310`](../../src/server/admin.rs)).

Reuse this **control-plane administration input contract**, not the old deployment's singleton app/share or existing database lineage. Managed deployments can attach to an authenticated administration service with `--tenant-deployments-file`, whose JSON is the existing `Source {target_file, object, shared_key_file?}`; `TenantDeploymentsConfig::open` retains the directory lock ([`tenant_provisioning/admin.rs:77-129`](../../src/server/tenant_provisioning/admin.rs)). No tenant database key, operation staging mapping, private validation transport or ACA resource-isolation proof is encoded in `VLITE_ADMIN_DIR`.

`credentials::Store::load` reads bounded regular `credentials.json` with `{schema: 1, credentials: ...}` and validates entries; missing file starts empty. `Store::snapshot` supplies the existing serializable, hash-only `credentials::Snapshot` ([`credentials.rs:500-525`](../../src/server/credentials.rs), [`:1070-1200`](../../src/server/credentials.rs)). **Do not copy/reload an admin directory into a trusted dedicated backend**: the binary expressly refuses `VLITE_ADMIN_DIR` with `--gateway-trust-file` ([`vlite-server.rs:632-650`](../../src/bin/vlite-server.rs)). The standalone template creates format 4 if missing; it is not this V5 seed pipeline.

### Blob contracts and permissions

Existing target JSON fields are **`account`, `container`, `coordination_container`, `prefix`, `auth`, `client_id`**; Rust additionally accepts emulator-only optional `endpoint` ([`cloud_backup.rs:185-214`](../../src/server/cloud_backup.rs), [`ha/templates.ps1:20-23`](../../deploy/azure-container-apps/ha/templates.ps1)). Production uses `auth=managed_identity`, no shared account key. Worker projection uses the same control storage fields but the worker's distinct client ID ([`ha/templates.ps1:769-803`](../../deploy/azure-container-apps/ha/templates.ps1)).

`Source::coordination()` returns existing `(Arc<dyn ObjectStore>, prefix)` via `cloud_recovery::connect`; `Deployments::connect` places control state at `{prefix}{object}` and journals at `{prefix}tenant-operations` ([`control_state.rs:1997-2030`](../../src/server/control_state.rs), [`tenant_provisioning/admin.rs:43-54`](../../src/server/tenant_provisioning/admin.rs)). The dedicated writer's archive target gives its authority/guard coordination namespace; do not substitute the global control prefix for the tenant archive prefix.

Reuse **hash-only candidate publication to Blob**, followed by fresh gateway control reads: `Snapshot::authenticate` authenticates/admits the tenant; the gateway requires a directory record and authorizes against its lineage ([`control_state.rs:710-725`](../../src/server/control_state.rs), [`gateway_mode.rs:629-656`](../../src/server/gateway_mode.rs)). A published candidate alone cannot route an unrouted tenant. Backend projections carry **no credential hashes or secrets**.

Existing `ObjectStore::{put_file, download, get, put}` and `Cond::Create` provide mechanics for an immutable artifact transport ([`cloud_backup.rs:153-179`](../../src/server/cloud_backup.rs)), but **no seed-artifact naming, manifest, ACL, retention, or install protocol exists**. A separate bounded `seed-artifacts/<operation>/...` namespace under an explicitly authorized target is proposed. Do not stuff database bytes into the 1-MiB operation/control record or use cloud restore: public restore's identity-preserving seed mode is deferred/refused; its rekey mode changes lineage.

## Minimum missing interfaces and their ownership

These are a small set of required seams, not implemented APIs or new proof constructors:

1. **`SeedInputs` resolver, worker/seed owner.** Accept verified `Loaded` plus operation identity; return a pre-existing operation-owned staging directory, optional key and an immutable dedicated-target binding. Binding must include tenant/operation/config digest, writer resource ID, intended writer database path, archive installation/scope, and durable staging/artifact identity. Missing, aliased, traversal, symlink/reparse, mutable-generation or foreign-tenant resolution refuses. A new narrow `SeedConfig::encryption()` accessor is needed because its field is private; dimensions need not be duplicated. Validate retained references/configuration before claim. Filesystem canonicalization alone proves neither mount isolation nor AzureFile durability.
2. **Exact-version key adapter and artifact installer, seed/storage owner.** Resolve **only** the retained `Encryption::SecretReference`, verify resolved version equals it, and keep bytes out of operation/config/status/logs. Existing server key readers (`--encryption-key-file`, 32 raw bytes or passphrase; environment alternatives) are decoding primitives, not reference-to-version provenance ([`vlite-server.rs:594-624`](../../src/bin/vlite-server.rs)). Prefer a private raw-32-byte file projection whose immutable secret version is attested by the resolver; ACA does not currently project one. Do not generate/rotate a key on retry. A durable create-only copy/download must verify receipt, config, exact hash and reopened lineage at the destination before writer enable; unknown publication/install outcome is reconciled from exact bytes, never overwritten. First slice may refuse all encrypted/remote-install cases rather than add speculative providers.
3. **Private validator/projection channel, credential/projection owner.** Keep the operational read-only validator separate from the administrator-delivered customer candidate. Supply operation/tenant/seed-lineage-bound validator ID, grant, expiry, delivery identity and an authenticated private envelope-signing/transport endpoint. Reuse `credentials::candidate` to mint an appropriately scoped grant and existing signer/verifier formats; add a private operation-bound hash-only validator record and protected one-time delivery. Do not call customer `issue_candidate`/acknowledge APIs for operational validation, leak the token through CLI output, or distribute `gw-seed` to the worker. No currently deployed endpoint provides this channel. Its retry policy must explicitly reuse a durably delivered identity or refuse/replace with revocation; never silently mint another validator.
4. **Readiness observation adapter, activation owner.** Return authenticated observations bound to operation, dedicated writer resource/revision/image, seed lineage, current authority epoch/head, archive manifest, required/applied policy generation, backend audience/endpoint, binding generation and observation freshness. Feed existing private `Readiness`/`prove` inside the parent tenant-provisioning module; expose a narrow internal composition function, not a public `Proof` constructor. Keep real clock/qualification/quota/budget evidence outside this patch; absent evidence refuses. Add runtime threading of the approved clock source to projection startup only when that source actually exists.

The pending-validation mechanism already exists: `projection::Pending {operation_id, audience, lineage, validator}`, `Publisher::new/publish`, and a tenant-only projection derived from a fresh shared snapshot. Only an uncancelled reserved create without a route/receipt may be pending; it admits an API credential with exact validator ID/lineage and only `read`, `search`, `graph_read` ([`projection.rs:47-68`](../../src/server/tenant_provisioning/projection.rs), [`:167-238`](../../src/server/tenant_provisioning/projection.rs), [`:271-348`](../../src/server/tenant_provisioning/projection.rs)).

**Two integration gaps cannot be bypassed:** current HA trust templates emit `control_state`, not `control_projection`; and production `GatewayTrust::start` passes no clock proof to projection startup ([`gateway_trust.rs:55-94`](../../src/server/gateway_trust.rs), [`:208-227`](../../src/server/gateway_trust.rs)). Full-feed backends require a published route, while the public gateway also refuses a missing route. Therefore neither a bare customer bearer token nor an early route can serve as the private readiness channel. Switching to tenant-only projection requires explicit template/source mapping and actual clock evidence, with no full-feed fallback.

## Concrete Rust composition and ordering

The following call order preserves existing types; steps labeled proposed require new integration code:

1. Existing REST/CLI acceptance retains request/profile/manifest/secret-version references, reserves the new tenant and returns provisioning status. No route exists.
2. Existing worker selection/journal/reservation/profile/resource-inventory/preflight gates run. **Proposed:** derive `SeedConfig::from_loaded`, resolve and validate the seed source, key version and target binding without mutation. Preserve absent-evidence refusals before claim, ARM calls, staging writes or validator minting.
3. Existing `Driver::new` claims the operation. **Proposed integration contract with the ACA owner:** execute only non-serving bootstrap resources first if needed; do not start a writer before the target guard and verified artifact are in place. For an already verified durable mount, no bootstrap resource step is needed.
4. Existing `seed::seed_create` uses that same operation ID and claimed attempt. It creates `<operation>.vlite` and `<operation>.seed-receipt.json`; `seed::verify` rechecks them and `record_seed` settles the bound seed. Never calculate lineage from a caller assertion or a different live database. Report uncertain journal writes as unknown; do not report provisioned.
5. **Proposed:** hold `Guards::of(&authority)` before writer startup and complete immutable artifact installation. The writer can use the operation-named file on its dedicated mount, or a create-only verified installation at `/data/vectors.vlite`; the retained desired body must bind that choice. Never rename/copy over an existing unmatched file. Preserve the sealed empty source/receipt after the writer starts: its writable database will diverge, so future seed verification must not run on live mutated bytes.
6. Existing `establish_authority` validates/creates the recorded seed's installation/scope/lineage and enables the guarded writer claim. **Proposed:** provision/deliver the read-only operational validator and publish the pending tenant-only projection from a fresh source read **before starting the projection-configured backend**; its startup requires an initial accepted projection and a real clock source. No customer acknowledgment is consumed by this step.
7. **Proposed:** start only the pinned dedicated writer with the already verified database/key/policy/trust configuration, using journaled ACA steps and exact readback. No `--create-if-missing`, no route, no reader. Execute authenticated private validation, never use the public gateway's data route. Keep projection witnesses fresh; a one-shot worker that exits cannot keep pending/active projections alive indefinitely. A bounded supervised publisher or explicitly scheduled publisher is an external runtime dependency, not a reason to lengthen stale witnesses.
8. Observe writer lineage/epoch and first archive checkpoint, authority serving/head, resource/revision ownership and applied policy. **Proposed:** validate the endpoint/audience against the exact accepted writer resource and pinned image before constructing `Readiness`. Visible `prove` binds the supplied route and checks owner/succeeded/active count; it must not be fed an arbitrary successful app or caller-chosen URL.
9. Existing admin HTTPS `issue-credentials` publishes the customer candidate from recorded seed lineage. Return its token once through `Minted::deliver`; administrator acknowledges the exact delivery generation and ID. This can run in parallel with resource validation after seeding, but activation waits for both.
10. Existing `prove(..., Some(real_clock_proof))`, `ops.delivered(...)`, then `activate_create(...)` publish **only** the proven `Dedicated`, `WriterOnly`, reader-absent, authority-enabled route. Use fresh clock reads on CAS retries. Revoke/expire operational validation admission, publish the active projection from a new source read, and preserve activation-receipt recovery. Never “successfully activate” on `/health`, one ARM PUT result, credential delivery alone, or a fixture clock.

### Minimal typed sketch

This sketch belongs in the parent `tenant_provisioning` module. Every type/function used already exists and its visibility/signature was inspected. The wrapper itself is **proposed**, not a runnable patch, a source resolver or deployment proof:

```rust
fn seed_claimed_create(
    ops: &Operations,
    intent: &Intent,
    attempt: &str,
    staging: &std::path::Path,
    key: Option<&crate::EncryptionKey>,
) -> Result<seed::SeedReceipt, ApiError> {
    let receipt = seed::seed_create(
        ops, &intent.operation_id, attempt, staging, key,
    )?;
    let config = seed::SeedConfig::from_loaded(&ops.load(&intent.operation_id)?)?;
    seed::verify(staging, &intent.operation_id, &config, key)?;
    Ok(receipt)
}
```

Only call this after the proposed resolver has checked immutable source/target binding and existing gates/claim have succeeded. The real source must retain ownership/exclusion through the filesystem operation; a prior path check followed by an unprotected shared directory is insufficient. Do not add `record_seed` separately: `seed_create` already performs it.
