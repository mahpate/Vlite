## 2. Existing primitives to reuse, and the gaps between them

### Authority and failover APIs

The existing internal entry points are `build_report(&AuthorityStore, Option<&ArchiveStatus>, Option<WriterObservation>) -> LossReport` and `execute(&AuthorityStore, &LossReport, &FailoverAck) -> Observed`. The CLI returns `{report, text}` and, after execute, `result: {record, etag}` ([failover.rs:171-179](../../src/server/failover.rs#L171-L179), [344-456](../../src/server/failover.rs#L344-L456)).

Do not expose the CLI parser as a web handler or accept its filesystem flags over HTTP. Its optional diagnostics must remain identical between report and execute because they affect the digest. The future controller should retain those exact inputs server-side. `AuthorityStore::read`, `objects`, and `prefix` provide the store/binding substrate; `prepare_transfer` provides the existing transition invariants, but not the needed prepare/persist/dispatch split ([authority.rs:189-254](../../src/server/authority.rs#L189-L254), [378-412](../../src/server/authority.rs#L378-L412)).

**Recovery distinction:** the existing CLI considers an unknown transfer followed by readable nonmatching bytes a conflict, and unreadable readback indeterminate ([failover.rs:1342-1375](../../src/server/failover.rs#L1342-L1375)). The harness is deliberately more conservative: after possible dispatch, exact old authority is still indeterminate, exact candidate is attributed to this operation, and a competitor is not ([failover_harness.rs:539-564](../../src/server/failover_harness.rs#L539-L564)). Implement a separate controller recovery path rather than quietly changing the established CLI contract.

### Durable operations and lifecycle

Reuse the existing `ObjectStore` conditional-write patterns rather than adding a queue/database dependency:

* `Operations::accept` stores immutable intent/content, verifies digests, and reconciles create races for principal/key reuse ([tenant_provisioning.rs:481-637](../../src/server/tenant_provisioning.rs#L481-L637)).
* `update_journal`, `claim`, `record`, `observe`, and `settle` use journal CAS; an action is recorded uncertain before dispatch, repeats reconcile instead of blindly sending, and another attempt needs `ActuatorStopped` ([tenant_provisioning.rs:715-895](../../src/server/tenant_provisioning.rs#L715-L895)).
* `Objects::update` rereads/reapplies bounded control-state CAS conflicts but reports unknown writes explicitly ([control_state.rs:1331-1390](../../src/server/control_state.rs#L1331-L1390)).
* `Snapshot::reserve`/`reserve_after` bind a tenant slot to operation, request, route, and generation; concurrent operations and stale anchors refuse ([control_state.rs:862-960](../../src/server/control_state.rs#L862-L960)).
* Terminal sealing closes the journal before lifecycle release; release accepts a trusted sealed outcome, not browser JSON ([tenant_provisioning.rs:303-389](../../src/server/tenant_provisioning.rs#L303-L389), [916-1019](../../src/server/tenant_provisioning.rs#L916-L1019), [control_state.rs:1240-1277](../../src/server/control_state.rs#L1240-L1277)).

These are **reusable patterns, not a drop-in failover implementation**:

1. `control_state::OperationKind` has `Create`, `SetReaders`, `Migrate`, and `Retire`, but no failover; existing terminal outcomes are provisioning-specific and `release_lifecycle` accepts provisioning's sealed type ([control_state.rs:68-79](../../src/server/control_state.rs#L68-L79), [tenant_provisioning.rs:345-389](../../src/server/tenant_provisioning.rs#L345-L389)).
2. The offline failover intent emits a full 64-hex operation hash, while existing provisioning operation IDs and control-state slot validation use 32 hex. Select an explicit versioned identity/mapping contract before integrating; do not silently truncate or pretend the current types compose ([failover.rs:555-579](../../src/server/failover.rs#L555-L579), [tenant_provisioning.rs:531-533](../../src/server/tenant_provisioning.rs#L531-L533), [control_state.rs:780-789](../../src/server/control_state.rs#L780-L789)).
3. The failover HTTP target DTO lacks the app incarnation (`createdAt`) and revision mode that the proof binding requires. Resolve and retain them from trusted configuration/observations; a browser target object cannot become the binding authority ([failover.rs:500-512](../../src/server/failover.rs#L500-L512), [failover_proof.rs:26-39](../../src/server/failover_proof.rs#L26-L39)).
4. A tenant slot serializes only a writer proven dedicated to exactly that tenant. The harness rejects both unknown/empty bindings and two tenants sharing a target. Broader shared-target failover needs target-wide serialization, not one arbitrary tenant lock ([failover_harness.rs:211-217](../../src/server/failover_harness.rs#L211-L217), [821-837](../../src/server/failover_harness.rs#L821-L837)).

The target guard is a separate interlock: `Held` and `WriteEnabled` both forbid transfer; absence or `Released` allows it. Failover must not acquire it, release somebody else's guard, or create an owner exception just to get its CAS through ([guard.rs:124-139](../../src/server/tenant_provisioning/guard.rs#L124-L139), [failover_harness.rs:790-819](../../src/server/failover_harness.rs#L790-L819)). A later hold does not stop an already-serving writer, and the check and authority CAS are separate objects. The holder's post-hold authority reread remains part of the race defense, not atomic multi-object serialization ([guard.rs:15-19](../../src/server/tenant_provisioning/guard.rs#L15-L19), [failover.rs:435-443](../../src/server/failover.rs#L435-L443)).

### ARM integration

`worker::production_arm` now constructs `ArmClient` behind existing gates; it is no longer merely an unavailable adapter seam. However, production preflight proofs still have test-only constructors, and create-worker execution remains blocked before adapter construction/claim/network calls ([worker.rs:178-235](../../src/server/tenant_provisioning/worker.rs#L178-L235), [aca.rs:554-605](../../src/server/tenant_provisioning/aca.rs#L554-L605), [tenant PRD:1288-1292](../../docs/projects/feature-aca-ha/design-tenant-provisioning/design-tenant-provisioning.prd.md#L1288-L1292)).

The generic ARM revision inventory is not `WriterFenceProof`: its ID/type can be omitted, integral floating replica values are accepted, and it reduces a revision to name/activity/configuration digest. The proof parser instead requires explicit integer zero plus stopped state and direct/repeated reads ([arm.rs:1030-1093](../../src/server/tenant_provisioning/arm.rs#L1030-L1093), [failover_proof.rs:208-245](../../src/server/failover_proof.rs#L208-L245)). Reuse transport/authentication and bounded resource handling, but do not reinterpret `Revisions::Complete` or retirement/reader stop checks as a qualified writer fence.

## 3. Prioritized implementation sequence

The sequence below is a recommendation, not implementation authorization. Offline persistence/API work can be developed against fake ports while live qualification remains blocked. Do not make unqualified ports callable by a real dashboard.

### P0 - Resolve host, scope, actor ownership, and credential boundaries

**Deliverable:** a short agreed control-host and trust contract before production-capable wiring.

Choose an independently available admin/control host and a distinct failover operation worker/state machine. The UI/API/auth must survive the old writer being at zero replicas. The existing gateway is DB-free and can remain a data/auth-routing role, but must not receive authority-write credentials or expose this admin operation. Existing tenant dashboard gateway sessions do not make it a super-admin control host ([HA PRD:952-966](../../docs/projects/feature-aca-ha/feature-aca-ha.prd.md#L952-L966), [gateway.md:65](../../docs/projects/feature-aca-ha/gateway.md#L65)).

For the smallest useful first scope, recommend a trusted, one-tenant/one-dedicated-writer binding, unchanged target/route during transfer, and operator-owned stop followed by server verification. Explicitly decide whether later iterations let the controller issue Stop; doing so introduces another uncertain side effect and requires its own journal/actuator ownership. Current `AuthenticatedFenceReads` is read-only, not a stop actuator.

Specify separate permissions for authenticated ARM reads, optional stop/deactivate actions, authority write, journal/control-state write, and archive verification. Resolve trusted target IDs to fixed resources/store prefixes server-side. Establish who can deploy/reactivate/claim and how those actors are excluded during the operation. Include current automatic supervisor and out-of-band CLI operators in the exclusion story; a manual tenant slot does not currently interlock them.

**Exit condition:** host availability and target scope are selected; permission/actor boundaries have an explicit qualification plan. A no-reactivation mechanism is identified, not assumed from a lease, replica count, or dashboard confirmation.

### P1 - Persist the operation and lifecycle reservation

**Deliverable:** a failover-specific versioned intent, journal, report, acknowledgement, terminal, and reservation/release contract over the existing store.

Persist principal/key/request-digest acceptance before returning an operation ID. Add supported failover slot/terminal semantics deliberately; preserve old snapshots and fail-closed handling by old consumers. Bind the slot to tenant, exact target, route receipt/digest, lifecycle generation, authority installation/scope/lineage, and the selected operation-ID contract.

Persist the report's exact authority record **and ETag**, original loss inputs, text/digest, generation, evidence references, and server-observed timestamps. Every regenerated report or authority/target/route change clears acknowledgement. Derive the actor from authenticated server context; do not trust the `actor` field of submitted acknowledgement JSON.

Adopt inspectable states corresponding to the DTOs: accepted/reserved/awaiting stop/verifying fence/report ready/acknowledged/transfer pending/reconciling/transfer prepared/cancelled/refused. Represent indeterminate outcomes explicitly. A terminal release must be sealed against the same reservation generation, and survive failure between sealing and release. Never let a sealed operation reserve again.

**Exit condition:** real object-store fault tests and fresh-instance reloads prove these invariants, replacing `Model::restart()`'s memory clone.

### P1 - Build a production-capable fence verifier behind a fail-closed qualification boundary

**Deliverable:** authenticated, bounded, auditable reads producing retained fence observations, plus a separately qualified no-reactivation capability.

Use the parser's exact app/environment/incarnation/authority/route/lifecycle binding and ordered-read algorithm. It requires every revision inactive, explicit integer zero replicas, `Stopped`, no contradictory traffic/provisioning state, latest revisions included, safe complete pagination, and consistent repeated reads ([failover_proof.rs:193-399](../../src/server/failover_proof.rs#L193-L399)).

Do not simply remove `#[cfg(test)]` and claim the constructor is now production proof. Define authenticated transport provenance, clock failure/rollback handling, evidence lifetime across human acknowledgement and restart, parser/body/page bounds, cancellation, and permission-denied/timeout/incomplete outcomes. Recollect evidence immediately before possible dispatch and invalidate stale acknowledgement rather than silently updating its basis.

Repeated GETs detect observed drift; they cannot exclude a reactivation after the last GET. Require an independently enforced exclusion mechanism or keep actuation refused. Also distinguish **writer stopped** from **previous controller cannot dispatch**: the latter needs a separate `ActuatorStopped`-like capability for takeover.

**Exit condition:** offline adapter/parser tests pass, but production actuation stays disabled until the platform evidence in section 5 exists.

### P1 - Split candidate preparation from one-shot dispatch and reconcile durably

**Deliverable:** a controller transfer adapter that preserves existing authority transition invariants without recreating a candidate on retry.

Construct a checked candidate once: epoch +1, archived head/base frozen, no writer/claim time, `Recovering`, operation-specific retained revision. Serialize and persist its exact bytes, digest, expected complete authority/ETag, acknowledgement, and owning attempt. Reject malformed/tampered retained candidates.

Immediately before dispatch, reread reservation/route/authority/guard and obtain fresh qualified fence evidence. Persist a **may-have-dispatched** marker through journal CAS **before** sending the authority CAS. Only a newly authorized live attempt may send; replay of the uncertain marker goes to readback, not another mutation. A crash between marker persistence and actual send is intentionally conservative.

Reconciliation:

| Readback | Controller action |
|---|---|
| Exact retained candidate bytes | Persist observed record/ETag as `transfer_prepared`; then seal terminal and release the exact slot generation. |
| Authority unavailable/unreadable | Stay indeterminate; retain reservation and no-reactivation exclusion. |
| Exact predecessor still current after possible dispatch | Stay indeterminate; do not assume the delayed CAS cannot still arrive. |
| Another successor/current record | Do not attribute it to this operation. Retain sufficient state for conflict/operator reconciliation; do not release an uncertain operation solely on this observation. |

A superseded predecessor ETag may establish that the old conditional request can no longer land, but that still requires a specified settlement/ownership policy. The harness's `Conflict` is not currently sealable, so model behavior is not a complete production conflict-recovery workflow ([failover_harness.rs:495-518](../../src/server/failover_harness.rs#L495-L518), [539-564](../../src/server/failover_harness.rs#L539-L564)).

Allow cancellation only before the possible-dispatch cutoff unless a separately proven recovery procedure establishes settlement. Never decrement epoch or reactivate the old revision as rollback. Do not start any replacement before terminal transfer attribution is durable: a new claim changes the record/revision and can erase the exact candidate readback needed to reconcile a lost response.

**Exit condition:** crash/late-response/replay tests over the actual journal and authority store prove one operation cannot blindly dispatch again, start a writer, or prematurely release its interlocks.

### P2 - Add the safe control-host API, initially testable on fake ports

**Deliverable:** asynchronous administrative operation API, with no HTTP request directly waiting through stop/verification/transfer.

Suggested routes are **new design**, not current endpoints:

| Proposed route | Contract |
|---|---|
| `POST /v1/admin/failover-operations` | Bounded validated intent and idempotency key; server-resolved target; return accepted durable operation/status locator, not transfer success. |
| `GET /v1/admin/failover-operations/{operation}` | Retained server report/text, exact generations, interlock/fence status, uncertainty, refusal, and terminal record/ETag; reads never dispatch. |
| `POST /v1/admin/failover-operations/{operation}/acknowledge` | Quote report ID, epoch/revision, report/operation/lifecycle generations; bind authenticated actor and persist an idempotent action receipt. |
| `POST /v1/admin/failover-operations/{operation}/cancel` | Generation-bound cancellation before cutoff; return inspectable refusal/uncertainty after possible dispatch. |
| Optional list/reconciliation route | Paginated authorized inspection; reconciliation schedules/readbacks the retained attempt, never silently redispatches. Specify exact semantics before adding it. |

Existing precedents are `/v1/admin/tenant-deployments` and `/v1/admin/tenant-deployment-operations/{operation}/{action}` ([tenant_provisioning.rs:1818-1844](../../src/server/tenant_provisioning.rs#L1818-L1844)); their handlers use configured-admin checks, bounded JSON handling, generation tokens, idempotent action records, auditing, and blocking store work off the async runtime ([admin.rs:600-679](../../src/server/tenant_provisioning/admin.rs#L600-L679), [748-801](../../src/server/tenant_provisioning/admin.rs#L748-L801)).

Require super-admin authorization, reject open development administration, deny tenant editor/viewer/data tokens and gateway/trusted-backend access, preserve CSRF for cookie actions, and avoid target-existence disclosure to unauthorized callers. Use decimal strings for all new u64 fields; reject JSON numbers, exponents, signs, leading zeroes, and overflow. Use trusted target lookup, not arbitrary management URLs, store prefixes, filesystem paths, commands, credential uploads, browser-supplied proofs, or self-declared actors.

Specify stable status/error mapping: 409 for stale reports/generations, replay mismatch, held lifecycle, terminal or concurrency conflicts; 503 for unavailable or unresolved authority/store/fence observations; appropriate existing 401/403 and malformed-input conventions. Distinguish unavailable evidence from confirmed unsafe evidence and indeterminate mutation from a clean refusal. Return a durable operation ID whenever acceptance is known, and require exact-key replay to reconcile uncertain acceptance.

Apply the PRD's route inventory, API docs/OpenAPI/site parity, admin coverage, applicable name/memory isolation, audit, and review requirements before enabling a real trigger ([HA PRD:982-984](../../docs/projects/feature-aca-ha/feature-aca-ha.prd.md#L982-L984)). Gateway classification updates, if required by inventory conventions, must preserve denial; they must not grant a gateway admin surface.

### P2 - Implement the independently available dashboard flow

**Deliverable:** a real manual trigger backed by the durable API, not terminal-command generation or the automatic switch.

Flow: select trusted target and planned/unplanned mode -> create durable operation -> inspect stop/interlock/evidence status -> read server-retained loss report and authoritative text -> explicitly acknowledge its exact version -> poll operation -> show `transfer prepared`, refusal, or indeterminate outcome. Label **transfer prepared, replacement not yet verified** rather than "HA recovered."

Clear acknowledgement when report/target/generations change. Handle double clicks, lost HTTP responses, reload, session expiry, and another administrator through server-side operation state and exact action replay. Never store admin tokens, reports, evidence bodies, target paths, or commands in URLs, telemetry, browser storage, or HTML; render text safely. If any non-secret operation locator is retained for resume, define its authenticated/account/server-scoped storage and sign-out cleanup explicitly.

Cancellation UI must reflect the server cutoff, not promise undo after dispatch. Unknown results keep the old writer stopped and expose inspection/recovery instructions. Preserve the existing CLI fallback and existing automatic-switch warnings. Assets require coverage, mocked browser checks, connected exercise, and tour recapture; current CI/release already run dashboard Node/coverage checks ([ci.yml:293-300](../../.github/workflows/ci.yml#L293-L300), [dashboard-ui.yml:79-94](../../.github/workflows/dashboard-ui.yml#L79-L94)).

### P3 - Qualify the control host/fence, then exercise replacement recovery end to end

**Deliverable:** permission/availability/no-reactivation evidence and one authorized isolated full manual drill, distinct from mocks and local Blob emulation.

First qualify the exact host, identity, resource binding, grants, exclusion mechanism, complete revision evidence, and controller takeover safety. Then run an isolated drill: acknowledged writes/archive boundary -> stop/exclude all old revisions -> retained fresh report -> human acknowledgement -> final proof -> one CAS -> durable readback/terminal -> new writer startup restore/claim -> sole-owner verification -> archive advancement -> reader/gateway checks -> controlled traffic admission.

Include crash, partition, paused/zombie, delayed CAS, reactivation attempts, authority head races, stale UI acknowledgement, and release-recovery scenarios. Capture loss against actual restored records and recorded acknowledgement positions, not merely report JSON. Verification must include data/sequence/lineage, authority epoch/owner, actual replica/revision ownership, readiness, trusted-backend behavior, and tenant read/write routing. `serve-status` or `authority show` alone is insufficient ([HA-ACA.md:299-335](../../docs/HA-ACA.md#L299-L335)).

Do not run these cloud steps under this report assignment. Do not infer new timing thresholds or an RPO/RTO from historical fixtures.

### P4 - Release only the verified delivery slice; do not conflate release with rollout

**Deliverable:** reviewed release candidate with accurate experimental/qualification labels and recovery docs.

After the controller/API/dashboard exist, complete the planned three-agent deep review, existing formatting/clippy/API/isolation/dashboard/parity checks, applicable local process drills, release feature matrix, and current release workflow ([HA PRD:982](../../docs/projects/feature-aca-ha/feature-aca-ha.prd.md#L982), [release.yml:118-120](../../.github/workflows/release.yml#L118-L120), [228](../../.github/workflows/release.yml#L228)). Verify the embedded dashboard and binary correspond to the same candidate; document supported host setup, permissions, refusals, restart recovery, CLI fallback, replacement-start separation, and rollback cutoff.

An explicitly authorized experimental artifact may document platform actuation as unavailable until qualified; it must not be represented as delivered production HA. Production/manual qualification and automated promotion remain governed by their existing obligations. No gate waiver, production rollout, or release action is performed here.

### Required new implementation tests

1. **Real persistence, not clone recovery:** recreate controller/store clients after process/object-store failure at intent create, reservation CAS, report publish, acknowledgement CAS, candidate retention, dispatch-marker CAS, before send, after send/before response, terminal seal, and release. ## 5. Missing platform evidence: no-reactivation and verification

**The largest blocker is not proving zero at one instant; it is excluding the old revision and stale actuators throughout transfer and replacement.**

* `WriterFenceProof` records observations, not a platform lock. Its latest read finishes before authority mutation, and its test constructor never interacts with a real deployer, autoscaler, restart mechanism, or permission boundary. The PRD explicitly says a zero-replica read is not fencing if reactivation is possible ([HA PRD:966](../../docs/projects/feature-aca-ha/feature-aca-ha.prd.md#L966)).
* Epoch fencing rejects an already-claimed old writer, but current startup reads prepared authority and claims it based on database lineage/base verification and the guard. It is not bound to an approved ACA revision/image identity. **Inference from code:** an old revision with the same credentials/configuration that is restarted in the writerless prepared epoch is not intrinsically excluded by startup identity checks. A qualified platform/startup authorization boundary must keep it stopped; do not claim this was reproduced ([writer_authority.rs:343-403](../../src/server/writer_authority.rs#L343-L403)).
* A lifecycle guard blocks transfer while held and cannot be held by failover as a shortcut. The unqualified auto supervisor checks the target guard but not the new model's tenant reservation; it trusts its configured fence command's zero output and invokes `execute` ([auto_failover.rs:461-509](../../src/server/auto_failover.rs#L461-L509)). Qualify a common actor exclusion arrangement or explicitly require/prove that this supervisor and other operators are inactive for the manual operation.
* The recorded `arm19a` Single-mode probe is useful limited evidence: a no-ingress test app's latest revision deactivation returned 200, then both revisions were inactive/stopped/zero in 12 samples; the app itself still said running. It also saw approximately 69 seconds of two-active-revision overlap during update, and no pagination link. This is **a repository-recorded probe, not executed or independently verified here**, and the PRD explicitly denies writer-fence qualification ([tenant PRD:1147-1158](../../docs/projects/feature-aca-ha/design-tenant-provisioning/design-tenant-provisioning.prd.md#L1147-L1158)).
* That probe used a quickstart image, no ingress/storage/secrets, and did not exercise the actual Rust adapter/worker or Job identity. Full retained records live outside the repository and were not available under this assignment. It does not show old VLite writers cannot restart, pending ARM mutations cannot arrive, traffic-triggered scaling cannot reactivate, or all authorized actors are excluded. It also found `If-None-Match: *` on app PUT was not honored; a pre-read alone does not serialize deployments ([tenant PRD:1149-1150](../../docs/projects/feature-aca-ha/design-tenant-provisioning/design-tenant-provisioning.prd.md#L1149-L1150), [1157-1158](../../docs/projects/feature-aca-ha/design-tenant-provisioning/design-tenant-provisioning.prd.md#L1157-L1158)).
* Complete live paging, consistent direct/list semantics, missing/recased fields, clock behavior, and freshness across human acknowledgement remain unqualified. The proof's 20-page and 4 MiB limits and strict equality are safety refusals, not demonstrated availability limits for real fleets ([failover_proof.rs:13-16](../../src/server/failover_proof.rs#L13-L16), [305-399](../../src/server/failover_proof.rs#L305-L399), [tenant PRD:1287](../../docs/projects/feature-aca-ha/design-tenant-provisioning/design-tenant-provisioning.prd.md#L1287)).

## 7. Recommended decision

Approve a narrowly scoped **offline durable-controller implementation** after selecting the independent host and dedicated target binding; implement persistence and one-shot recovery before API/dashboard actuation. Develop the API/UI against fake ports while keeping real actuation fail-closed. Separately obtain qualified platform exclusion/identity/read evidence and run the full isolated recovery drill. Only then describe the manual dashboard trigger as delivered and prepare the authorized release slice, with production and automation qualification still explicitly separate.

The least-complex safe choice reuses current Blob CAS/journal/auth/dashboard patterns but adds a distinct failover state machine. A thin synchronous wrapper is smaller in code and inadequate in crash/uncertainty recovery; expanding the create worker conflates unrelated permissions and terminal semantics; a gateway controller violates the intended trust boundary. Availability, no-reactivation, and verified replacement recovery are acceptance requirements, not optional polish after the button ships.
