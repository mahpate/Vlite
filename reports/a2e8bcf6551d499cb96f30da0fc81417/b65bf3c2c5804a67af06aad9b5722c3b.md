## Still open

### OPEN-F004-LEGACY: previously published recovery sets become unreadable without migration

**Severity:** HIGH availability / recovery regression. **Confidence:** 10/10.

**Symbols / evidence:** `Manifest::policy`, `Sets::fetch`, `Sets::collect`; `src\server\cloud_backup.rs:31,541-553,1417-1422,1645-1651,1719-1725,1744-1763`. RB-01 similarly adds required bundle fields at `src\server\recovery_bundle.rs:81-96` while retaining schema `/1` at line 20.

F-004 makes `policy` mandatory without a legacy representation or schema migration. A manifest produced before the change has the same `/1` schema but no such field. It is rejected during deserialization before any database or bundle download. Even if that obstacle were bypassed, pre-RB-01 bundles lack the now-required database digest and policy. This is not corrupt historical data: it is the old supported format.

**Executed evidence:** the baseline new test explicitly asserts that missing `policy` cannot deserialize. Supplemental `audit_legacy_manifest_refused_but_still_retention_eligible`, using the command above, passed assertions that:

```text
pin(old_set) -> success
fetch(old_set) -> cloud_set_corrupt, missing field `policy`
download directory entry count -> 0
unpin(old_set), publish two newer sets, collect(enabled, keep_sets=2, keep_days=0)
old record.state -> Tombstoned
```

The matching manifest hash was updated in the fixture, so the error was not an incidental hash mismatch. Removing the newly mandatory field reproduces the old manifest shape; an old executable was not run to generate a complete historical archive.

**Restore/fetch/collect/retention consequences:** supported offline restore enters `Sets::fetch` before import (`src\server\cloud_recovery.rs:500-513`), so it fails too. Listing/pinning and collection use records rather than parsing the manifest; old sets therefore remain selectable and retention-eligible. Collection uses its current `Retention` argument, not historical manifest terms. The fixture establishes eligibility, not loss of the last verified set: ordinary pin/newest/verified protections still apply.

**Suggested fix / trade-off:** explicitly version the format and define legacy handling. Either support an explicitly marked, rekey-only legacy read path that does not fabricate a current admitted policy, or supply an isolated old-format migration/verification procedure before upgrade. Surface compatibility in list/restore diagnostics and require an explicit policy for retention of incompatible sets until a replacement is verified. Merely defaulting missing policy fields to current policy would invent provenance.

### OPEN-RB01-CAPTURE: database/policy binding is not unique recovery-capture binding

**Severity:** LOW integrity limitation. **Confidence:** 10/10 for acceptance; intended rejection policy requires clarification.

**Symbols / evidence:** `Bundle`, `bundle`, `Sets::fetch`; `src\server\recovery_bundle.rs:81-96,311-329`; `src\server\cloud_backup.rs:1482-1489`; set ID generation occurs after bundle construction at `src\server\backup_policy.rs:1079-1097`.

The bundle carries no set ID or capture nonce. Fetch compares installation, lineage, database hash and policy, but not creation time or any unique shared capture identity. Two backups can have identical database bytes and admitted policy while admin configuration changes independently.

**Executed evidence:** `audit_another_set_bundle_with_same_db_and_policy_is_accepted` passed after publishing two such distinct sets with different tenant names and timestamps, replacing the newer set's bundle reference with the older bundle, copying the old bytes under the newer set, and consistently recomputing the manifest/record hash chain. Fetch returned the old configuration and old timestamp. The different-database and different-policy cases were separately rejected by the existing tests.

**Threat boundary / uncertainty:** this does not defeat SHA-256 or let a payload-only writer bypass the record hash. The replay needs a producer mix-up or permission to republish matching metadata. A malicious writer of all containers can already forge the unsigned chain, as the documented trust model acknowledges. The issue is the stronger “another set's copy” wording versus the implemented database/policy equivalence class.

**Suggested fix / trade-off:** if distinct captures must be distinguishable, generate a random capture ID/set ID before constructing either document, carry it in both, and compare at fetch. Equality of timestamps is a useful diagnostic but a weaker substitute for a nonce. Otherwise narrow the claim to database/policy binding and explicitly document same-database/same-policy cross-set equivalence.

### OPEN-F004-VALIDATE: policy-capture semantic validity and publication-time enforcement are incomplete

**Severity:** LOW defense-in-depth / contract gap. **Confidence:** 10/10.

**Symbols / evidence:** `Manifest::check`, `Sets::publish`, `recovery_bundle::parse`; `src\server\cloud_backup.rs:599-630,984-995`; `Policy::validate` at `src\server\backup_policy.rs:91-109`; `src\server\recovery_bundle.rs:333-351`.

`Manifest::check` only checks policy digest syntax. Captures with `keep_sets=0` and `keep_days=0` pass, although no admitted `Policy` can pass those values. `Sets::publish` does not call `Manifest::check`; it can publish even the malformed digest that `check` refuses. Bundle parse does not validate its policy capture independently.

**Executed evidence:** `audit_manifest_accepts_impossible_retention_and_publish_bypasses_check` passed assertions that a zero-term capture, paired consistently in both documents, passed `check`, publication and real pinned fetch. A separate malformed-digest manifest failed direct `check` but still returned `Publication::Published`. `audit_invalid_policy_hash_not_checked_by_parse_alone` confirmed the parser limitation.

**Boundary:** the normal producer starts from validated `Policy`, and fetch checks manifest digest syntax and bundle/manifest equality. No route admitting a malformed live `Policy`, nor an ordinary fetch bypass of malformed digest syntax, was demonstrated. A digest alone also cannot prove that the copied retention terms match the original policy document.

**Suggested fix / trade-off:** centralize structural `PolicyCapture` validation, reuse the policy retention ranges, invoke it from both parsing boundaries, and call manifest validation before publication. Keep the lack of embedded-policy semantic recomputation explicit rather than presenting a well-shaped hash as full provenance verification.

## New

### NEW-RB03-QUOTAS: strict credential projection drops existing reissue limits

**Severity:** MEDIUM recovery metadata regression. **Confidence:** 10/10.

**Symbols / evidence:** `Entry::recovery`, `Entry::view_base`, `RecoveryCredential`, `Store::recovery_inventory`, `recovery_bundle::import`; `src\server\credentials.rs:253-267,279-288,317-329,512-515`; `src\server\recovery_bundle.rs:389-395`.

Before RB-03, recovery inventory used `Entry::view(now)`, which included `requests_per_second`, `max_vectors` and `max_vectors_per_collection`. The new recovery projection and DTO omit all three. They are non-secret limits, not excluded material, and are no longer available to the operator reissuing credentials after a disaster.

**Executed evidence:** `audit_recovery_drops_live_credential_quota_terms` created a live entry with limits 7/11/3, verified that its old public view contained them, projected the new inventory, then serialized, parsed and imported a real bundle. Assertions confirmed all three fields were absent from the returned `credentials_to_reissue`.

**Impact / boundary:** reissuing from the only recovery inventory can accidentally remove rate or resource limits. Import itself does not activate any credential, so this is not an immediate authorization bypass; deliberate regrant is still required. The reduced projection also cannot distinguish quota-only changes during the before/after configuration comparison; that latter consequence is static analysis, not a separate concurrent mutation execution.

**Suggested fix:** add typed optional quota fields to `RecoveryCredential`, project their existing values, apply the same validation rules used by the live store, and retain them in the reissue report. Add a round-trip regression with non-default limits.

### NEW-RB02-TEMP: arbitrary `.tmp`-prefixed files escape the unknown-entry refusal

**Severity:** LOW completeness limitation. **Confidence:** 10/10.

**Symbols / evidence:** `recognized`, `check_directory`; `src\server\recovery_bundle.rs:108-135,141-152`.

`name.starts_with(".tmp")` recognizes any regular file with that prefix, not merely an actual server-generated temporary filename. Thus an unrelated token/TLS/policy file with such a name is silently outside the bundle while passing this guard. This contradicts the unqualified “any other entry” claim for that namespace.

**Executed evidence:** `audit_directory_extra_files_links_and_temp_namespace` wrote the synthetic ordinary file `.tmp-synthetic-secret.key` and asserted `check_directory(...).is_ok()`. In the same test, ordinary unknown files and recognized-name symbolic links correctly failed. The rekey-only import requirement for a new empty directory remains intact.

**Boundary:** a source filesystem writer is required to place the file; this is not remote code execution or an import path traversal. A filename allowlist cannot prove actual writer provenance even when more tightly constrained.

**Suggested fix / trade-off:** reserve a narrowly defined temporary-file namespace matching the actual helper-generated shape, or make temporary-file handling explicit and fail/retry capture on unexplained leftovers. If broad temporary namespaces are intentionally excluded, document the exception rather than claiming that every non-server-written entry is refused.

### Recommendations, in order

1. Define and test old-format recovery and retention behavior before claiming upgrade-safe backup recovery.
2. Preserve credential limit metadata in the strict DTO and reissue report.
3. Decide whether binding means exact capture identity or database/policy equivalence, then align implementation and claims.
4. Tighten semantic policy-capture validation and publication preflight; constrain or document the `.tmp` exception.
5. Persist focused negative tests corresponding to M01/M08/M11 and the new regressions. Preserve the existing rekey-only, fixed-error and object-hash protections rather than weakening them for compatibility.

Only this report is delivered in the checkout. The temporary test/mutation sources, isolated runtime data and generated outputs are not repository changes.
