# Dedicated reader provisioning: implementation-ready input contract

**Research outcome:** Put the reader endpoint in a versioned, immutable, approved reader-profile document retained by the existing intent. Do not add an endpoint to `Fleet::Present` in the first slice. Build a pure reader-input resolver and its focused tests independently of seed/freshness changes; compose a production worker only after approved profiles, effective pin-scope evidence, and an authenticated live fleet source exist.

**Validation status: INCOMPLETE for runtime/production qualification.** This is a source-grounded design report, not a passed reader deployment review. No Rust build, runtime tests, Azure access, provisioning, qualification exercise, or effective-access measurement was performed. Proposed interfaces below do not exist yet. Missing producers and approvals must continue to block production.

Snapshot: commit `cc6ddbd6c52f7d801f4ce66a940ac13fefa48fbb`, initially clean checkout. The supplied snapshot excludes ongoing `aca.rs`, `tests.rs`, and PRD edits. References to base `aca.rs` identify historical interfaces only, not the current implementation status of another peer's changes. Reader retry/preclaim behavior and actuator-stop logic were not reviewed.

## 1. Scope and non-negotiable boundaries

This work supplies inputs for **dedicated** writers/readers. It does not introduce a shared-first tenant, migration, shared fallback, reader retry redesign, stop-proof redesign, seed production, or a routing qualification shortcut. A new tenant may stay unavailable while its dedicated resources, baseline, and required evidence are prepared.

Keep `read_routing: writer_only` throughout this work. Accepting an input, resolving an approved profile, creating a reader, and qualifying reader routing are different events. A stored reader endpoint must not enable reader traffic. Do not fabricate an ACA hostname from an app name or resource ID, manufacture `PinScope`/`FleetObservation`, or reinterpret an offline grant template as effective permission evidence.

Parallelize **implementation ownership and preparatory work**, not the per-tenant lifecycle CAS or unqualified cloud effects. The current schema has `Create` and `SetReaders` as separate operation kinds and no initial reader field on `Create`; the minimal path is dedicated create, properly succeeded writer activation, then an independently accepted reader operation anchored to that writer receipt. This serial lifecycle dependency does not prevent concurrent implementation of input parsing, seed production, and freshness production. If a product policy requires withholding client availability until readers finish, retain that policy outside this input slice; do not publish a shared route. A combined create-and-readers transaction would be a separate schema/lifecycle change.

## 3. Endpoint decision and request compatibility

### Recommendation: endpoint belongs to the approved reader-profile bytes

Define a new reader-profile document version containing an **explicit, already assigned private origin** plus the reader app resource ID. `Fleet::Present.reader_profile` already commits the exact bytes of that document into the request. The resolver retrieves those bytes from `Loaded.contents`, checks authorization against a controller-owned approval catalog, and extracts the endpoint. This avoids a second source of truth and avoids modifying the tenant-operation schema or UI just to introduce an endpoint.

The approved endpoint must come from an actual assigned ingress/DNS origin established by the approved infrastructure inventory or operator-controlled preconfiguration. For a brand-new app whose platform-assigned origin is unknown, the resolver must return a missing-input refusal. Wait for an approved known origin or define an explicit later discovery-and-sealing contract; do not fill in a guessed hostname, mutable profile alias, empty string, or cloud-readback URL that was not part of the accepted endpoint contract.

Validation has two levels:

* **Shape:** nonempty ASCII HTTPS origin, at most 2,048 bytes, host present, no whitespace/control characters, credentials, query, fragment, wildcard, or path other than `/`. Require the canonical origin spelling in the document; reject noncanonical spellings rather than rewriting accepted bytes. Local HTTP can be tested only in explicit fixture policy, never enabled by a production request flag.
* **Binding:** controller approval authorizes exactly that origin for exactly that app/environment/tenant. A future read-only ingress observation must confirm the authorized origin maps to the planned app and correct gateway audience. HTTPS syntax or a DNS suffix alone does not establish ownership, privacy, reachability, or TLS identity. No redirects or connection to arbitrary caller-selected URLs during admission.

An existing published reader origin may not silently move. Compare to the current anchored route and refuse a change pending the separately defined removal/re-add operation. This preserves the documented `reader_endpoint_changed` behavior [E9], without studying or modifying the existing actuator implementation.

### Digest and backward-compatibility consequences

| Choice | Consequence |
|---|---|
| **Profile-contained endpoint, recommended** | `Payload`, `Fleet`, `SCHEMA`, and operation-ID computation stay unchanged. Old typed payload serialization stays byte-identical. A different endpoint changes retained profile bytes, therefore `reader_profile` and `request_digest`; changing it under the same principal/key must conflict. Approval catalogs may authorize a digest but never replace its bytes. |
| Required endpoint added to `Fleet::Present` | Old intent deserialization breaks unless a versioned reader is supplied. A global `SCHEMA` bump also changes operation IDs, creating a new idempotency namespace; merely bumping it is not a safe migration. Avoid this for the first slice. |
| Optional endpoint added to accepted intent | `default` plus omission on serialization can preserve old payload hashes only if field ordering and legacy round trips are tested. Old missing endpoint still needs an explicit refusal, never a generated/default origin. This duplicates profile/app binding and adds migration/UI/API work for little benefit. |

The reader **profile** receives its own version tag; it does not become the historical writer `{resources}` document with extra tolerated fields. Legacy retained reader documents remain loadable as intents but unexecutable with `profile_unsupported`; do not retroactively attach an endpoint or reserialize retained content. An identical retry of an already accepted legacy request must still return the same operation, even if new admission rejects new unapproved legacy content. Run new semantic admission after duplicate reconciliation, before retaining a new intent. Execution/reload must always re-check approval and version so historical acceptance is not a permission bypass.

Do not change existing `min_replicas == 0` payload validity incidentally. A particular approved profile may restrict the range. A zero-minimum fleet is not proof of reader availability; `writer_only` remains the serving policy.

## 4. Proposed reader-profile and approval-loading contracts

Everything in this section is a **proposed interface/schema**, not an existing API.

### Strict retained document

Use `schema: "vlite.reader-profile/1"` and deny unknown fields. Required fields:

| Field | Contract |
|---|---|
| `tenant_id` | Existing 32-lowercase-hex reader-operation tenant; must match accepted intent. This is not a new create-time tenant allocator. |
| `reader_app_id`, `environment_id`, `endpoint`, `audience` | Explicit identities/origin; app distinct from authoritative writer and live singleton under ASCII-case-insensitive ARM comparison. Bind to approved infrastructure scope and anchored route audience. |
| `resources` | Ordered explicit `{id, ownership, body}` entries. Exactly one owned reader Container App in this first version. Supporting environments/storage are verified-only. Strict supported IDs, no case-fold duplicate, no owned singleton. Resource order is deterministic. Reuse `resource_id` and config-digest helpers, not a copied permissive ARM parser. |
| `files` | Exact nonsecret UTF-8 projected file documents with explicit `{path, kind, content_utf8}` entries for archive target, reader apply config, and gateway verification trust. These bytes are embedded inside the retained profile, not unretained external file references. Reject duplicate paths/kinds. |
| `secret_versions` | Explicit immutable secret reference IDs/versions and their approved mounted paths, never values, signing seeds, admin tokens, storage keys, or connection strings. This is a proposed reader-profile field; current `Fleet` has no secret-version list. |
| `runtime_image_digest` | Immutable approved image identity. No mutable tags in a reader execution profile. |

The separate retained `scaling_rule` gets `schema: "vlite.reader-scaling/1"` and a strict first-version `{reader_app_id, min_replicas, max_replicas}` contract for manual scaling only. Automatic scalers are deliberately unsupported initially, not silently ignored. These numbers must equal the fleet payload and ARM template scale values. Future scaler kinds require their own reviewed schema/evidence, not arbitrary JSON passthrough.

Reader-role and mount validation must be structural:

1. Container command is reader mode with the approved reader-apply and gateway-trust files; prohibit create/durability/group-commit/gRPC/admin-directory/archive-writer options. No admin or writer credentials are projected.
2. All reader storage is private per replica, with capacity for two generations and staging. Reject writer file-share/storage references; compare normalized backing-resource identity, not just volume names or mount-path strings.
3. Embedded reader config meets [E7] bounds; `isolated_pins` is explicitly true for provisioned readers. Target is the approved managed-identity tenant archive/coordination namespace. Target account/container/prefix/endpoint identities match the authoritative archive contract, while the reader uses its approved reader identity.
4. Pointer paths in apply/trust/target config resolve to exactly the retained projected documents or explicitly versioned approved secret mounts. Apply runtime limits on the corresponding document size, including the 64-KiB reader config limit, within the existing 1-MiB retained-content limit. Reject unexpected files, plaintext-sensitive fields, ambiguous path aliases, and unresolved references.
5. Validate paths for the **target container OS**, not by opening files with the Windows worker's `ReaderApplyConfig::load`. That existing loader performs filesystem reads and served-path checks at reader startup; it is not a pure controller-side parser. A Linux ACA projection must not be judged as a Windows absolute path.
6. Derive peak CPU/memory/app demand with checked arithmetic from explicit approved resource values and maximum replica count, including qualified revision overlap. Missing resource sizing or overlap evidence remains unproven, not a zero/default demand.

Do not treat the old secret-key-name heuristic as sufficient validation. A closed allowed configuration model, constrained environment values, exact immutable references, and explicit rejection of unknown command/env/mount surfaces are needed for this version.

### Concrete local approval loading

Propose a controller-side `ReaderApprovalCatalog` loaded once per worker invocation from an explicit read-only file in operator-controlled worker configuration, with its expected SHA-256 pinned by that trusted configuration. No environment-variable fallback, remote URL, mutable `latest`, or request-provided approval file. The request supplies desired content, not the power to approve itself.

Catalog document `vlite.reader-approvals/1` entries bind:

* Exact `(reader_profile_sha256, scaling_rule_sha256)` pair and supported document versions.
* Tenant, subscription/resource group/environment/app, endpoint/audience, archive-target identity, runtime image, secret-reference versions, and allowed replica/demand envelope.
* Approval ID, approver provenance reference, issued/expiry times, and exact qualification-artifact digest references.
* Evidence policy version, allowed observation producer identities, and approved maximum evidence-age/skew/collection-duration limits. These are qualification inputs, not guessed defaults.

Loading sequence:

1. `Operations::load(operation_id)` supplies verified retained bytes [E2].
2. Read the configured catalog with bounded strict UTF-8/JSON parsing; hash its exact bytes and compare with the trusted expected digest.
3. Select the exact authorized digest pair; refuse absent, expired, revoked, wrong-scope, or unsupported entries.
4. Parse the two retained documents without fetching/substituting content. Cross-check their declarations against payload, catalog, and route/authority context.
5. Return a proposed `ResolvedReaderInputs` containing endpoint/app/resources/projected bytes, derived demand, original content digests, catalog digest/approval ID, and evidence-policy identity. It is data, **not** `Preflighted`, `PinScope`, or routing permission.

A hash pin is an integrity binding, not independent proof of approval provenance. The deployment mechanism and authorization of whoever installs that pin must be trusted and reviewed. No approved production catalog or artifacts were supplied here; production must fail closed with `reader_approval_unavailable` rather than ship a sample allow-all catalog.

Qualification, live quota, and budget remain separate inputs covering the exact resolved plan and target. A catalog's authorization to use a profile cannot mint the historical proof types. The eventual verifier/bridge belongs to the corresponding proof owners and must consume real approved evidence.

## 5. Evidence-bound pin scope and live fleet source

The input resolver defines the **subjects to prove**. It must not claim to produce the proof.

### Common subject binding

Propose `ReaderEvidenceBinding` containing operation ID/request digest, tenant, reader/scaling profile digests, approval-catalog digest/ID, normalized app/environment/archive identities, endpoint/audience, planned resource-config digests, anchored predecessor receipt/route digests, lifecycle generation, and route lineage/binding/epoch.

Keep three hashes distinct: retained content hash, normalized ARM configuration hash, and domain-separated evidence hash. Evidence uses a versioned domain and deterministic serialization with sorted replica/resource sets, while preserving meaningful field values. It never changes the accepted `request_digest`. A later observed revision/head may advance only according to the evidence policy; the subject's tenant/profile/route anchors cannot be substituted.

### Proposed pin-scope input/verification port

`PinScopeEvidenceSource::load(binding, now)` is a proposed read-only evidence source, followed by a separate verifier. Its raw record must identify:

* Principal object ID and client-ID mapping, installed grant/role IDs, immutable grant definition hashes and effective configuration versions, tenant namespace, and account/container/reader-pin prefix.
* The approved reader/writer/janitor image/config versions showing every participant honors isolated pins; private per-replica mount inventory and backing resources.
* Qualified effective-access/mount test artifacts, exact tested environment/identity/grant versions, observed time/expiry, trusted producer, and approval provenance.
* Evidence that allowed tenant data reads/pin writes work, sibling access and record/authority/data writes are denied, and writer storage is not exposed. Evidence must include other effective assignments; an intended narrow assignment does not cancel an inherited broad grant.

Raw JSON booleans such as `qualified: true`, isolated-pin enablement, offline template generation, or operator inventory completeness alone do not satisfy this port. Reject missing/stale scope evidence or mismatched subjects. Proposed verification may ultimately enable a restricted production proof-construction boundary, but no such constructor is assumed or introduced by this report/first slice. Until that boundary and its real qualification exist, use the existing `pin_scope_unproven` refusal [E3/E9].

### Proposed live observation source

Use a **controller-owned collector** with explicit read-only ports:

* `PlatformInventorySource`: complete paginated app/revision/replica inventory and approved ingress mapping for the exact bound app; returns completeness, config digest, resource version/ETag where available, enumeration time window, and each revision/replica identity.
* `ReplicaFollowerSource`: authenticated, challenge-bound per-replica follower reports delivered through a qualified private diagnostic transport. It must prove which platform replica was sampled, not just sample the app's load-balanced URL repeatedly.
* Existing authority read interface [E12], wrapped with observed version and collection timestamps.

These ports and the diagnostic transport are **new work**. The base `Arm` interface has no replica-status API, and existing HTTP headers/admin status do not implement `ReplicaFollowerSource` [E6/E8]. Do not assume ACA provides a stable directly addressable per-replica HTTP endpoint. Before implementing the transport, its owner must qualify a supported platform-correlated mechanism or leave `fleet_observation_unavailable`. The collector contract is implementable independently; no fictitious fleet constructor or fake production observation is a substitute.

Propose strict `vlite.reader-live-observation/1` with:

| Section | Required evidence |
|---|---|
| Envelope | Common binding, collector identity/key reference, request nonce, collection start/end/expiry, evidence-policy version, authenticated provenance/integrity evidence. Keys/credentials never appear in the record. |
| Platform | Exact owned reader app, desired config digest, complete active/inactive revisions, exactly one active revision, complete replica identities and their revision membership, ingress binding. Partial pagination or omitted/unresponsive replicas is not an empty healthy fleet. |
| Authority | Validated serving authority with head, installation/scope/lineage/epoch/revision, head set and manifest/index/chain/sequence references, observed version and observation times. |
| Per replica | Platform-correlated app/revision/replica plus process-instance/boot identity; nonce; reader mode/read-only status; actual served set and verified manifest/checkpoint identity; lineage/binding/epoch; applied sequence; configured bound; confirmation age/time; permanent failure status; applied runtime/profile identity; collection times. |

The first producer must provide a coherent follower snapshot tied to the **actually served generation**. Joining independent atomics, environment strings, and a manifest downloaded earlier can create an internally inconsistent success record. Snapshot publication belongs to the freshness/runtime owner, not this reader-input owner.

Collection/verification algorithm:

1. Read current anchored route/receipt and authority observation A. Refuse missing authority, non-serving phase, absent head, or subject mismatch.
2. Enumerate the complete app/revision/replica inventory A. Verify ownership and desired config. Fan out authenticated per-replica reports using a bounded configured concurrency and overall deadline; do not add unbounded parallel network calls.
3. Require exactly one response per enumerated process instance. Match the trusted transport's identity to the platform membership; reject duplicates, missing responses, replayed nonce/boot, and extra/misattributed replicas.
4. Re-read authority B and re-enumerate platform inventory B. Require stable relevant authority/head and inventory/config identities across the collection window. If changed, return an explicit unstable/unavailable observation, not merged evidence. ETags alone are insufficient where membership is not versioned; compare complete membership too.
5. Check every report against current head/set/manifest, route lineage/binding/epoch, configured staleness bound, and failed flag. Age plus bounded transport/collection uncertainty must stay within the configured bound. Unknown clock skew, future timestamps, stale nonce, or unverifiable age fails closed. Existing saturating age behavior is not a clock qualification [E8].
6. Apply accepted min/max and approved demand limits. No-response is never zero replicas; a zero-minimum request does not prove a serving reader. Revalidate the route/receipt and evidence expiry at the publication boundary, including after CAS contention, rather than trusting an earlier collection indefinitely.

No new privileged admin route, admin-secret projection, gateway-trust disablement, anonymous headers, or public backend exposure may supply the missing fields. An approved private collector can sign an envelope using existing crypto dependencies, but a valid signature proves producer provenance, not ACA membership or data correctness; its transport and correlation must themselves be qualified.

Prefer a live collector over reader-written Blob status in the first design. Blob publication would need a new status namespace/grant and freshness/replay semantics; shared tenant reader identities can impersonate another replica unless additional identity binding is qualified. The current offline pin grant is not authorization for arbitrary observation objects. A later Blob transport could implement the same source port only after addressing these additional proof obligations.

## 6. Admission and execution refusal contract

Preserve separation between durable intent acceptance, pure input validation, live evidence, and effects. New semantic admission should reject malformed new reader documents before persisting a new intent, but must not consume a lifecycle reservation or call ARM. Identical already-recorded submissions reconcile first. Runtime re-resolution applies current approval policy without editing the accepted request.

| Failure | Response/status and persistence |
|---|---|
| Wrong kind/tenant, bad digest, min/max invalid, missing/extra/duplicate content | Existing 422 `operation_request_invalid`; no new intent or cloud call. |
| Missing endpoint, invalid reader/scaling schema, unsafe configuration/mount, inconsistent profile/scale/file declarations | Proposed 422 `reader_profile_invalid` / `reader_endpoint_invalid` / `reader_scaling_invalid`; sanitized messages, no content or credentials echoed. Legacy unsupported versions instead remain blocked with `profile_unsupported`. |
| Same principal/key, changed endpoint/profile bytes/payload | Existing 409 `operation_request_conflict`; return no new operation. |
| Missing/corrupt retained content or invalid operation record | Existing 503 `operation_input_unavailable` / `operation_state_invalid`; no default or fallback. |
| Catalog absent/unreadable/untrusted/expired/revoked | Proposed 503 `reader_approval_unavailable` for unavailable artifact; 409 `reader_profile_unapproved` for an authoritative denial. Accepted intent remains intact; no effect. |
| Profile approval subject differs from accepted tenant/app/environment/endpoint | Proposed 409 `reader_input_binding_mismatch`; no reservation/claim/effect from input resolution. |
| Unanchored dedicated route/receipt or changed reader endpoint | Existing documented `readers_unanchored` / `reader_endpoint_changed`; do not repair the directory implicitly. |
| Desired reader routing | Existing/documented 409 `reader_routing_unqualified`; `writer_only` required regardless of profile approval. |
| Pin proof, qualification, quota, or budget absent | Preserve `pin_scope_unproven`, `qualification_missing`, `quota_unproven`/`quota_exceeded`, `budget_unapproved`. Catalog loading does not skip these gates. |
| Unsupported diagnostic transport, partial fleet, missing/stale/replayed/unstable observations | `fleet_observation_unavailable`; use `replica_identity_conflict` for duplicate identities and `replica_ineligible` for concrete subject/freshness failures. Do not treat these as healthy observations. |
| Head/base transition, revision mismatch, below min or above max | Preserve documented `reader_base_transition`, `reader_revision_unproven`, `reader_fleet_below_min`, `reader_fleet_not_reduced`. |

The detailed new error names are proposed; reconcile them with the integrating peer's current API/error conventions before implementation. Input validation, source availability, and genuine qualification denial must remain distinguishable in sanitized status. There is no production bypass flag.
