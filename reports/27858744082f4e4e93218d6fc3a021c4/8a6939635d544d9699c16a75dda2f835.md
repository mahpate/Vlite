## New

### NEW-FW3-01 - Medium - a fenced runtime can resume an older pending publication

**Symbols/locations:** `Runtime::publish` invokes `Runtime::settle` at `src\server\backup_policy.rs:1247`, before the fence at `:1300`; `Runtime::settle` calls `sets.resolve_pending` at `:1329`. The remote commit is in `Sets::finish`, `src\server\cloud_backup.rs:1112-1144` (conditional write at `:1132`).

**Defect:** the new fence applies to fresh `sets.publish`, not the earlier pending-publication resolution. A thread blocked in its connector can outlive shutdown, become fenced, and then start the pending publication CAS after a successor runtime is already open. Local state writes remain correctly fenced, but the remote set changes from `staging` to `published`. This contradicts the new shutdown publication guarantee; it is **not** a claim about deferred HA fencing.

**Executed evidence:** added a temporary test named `server::backup_policy::tests::review_pending_publication_must_not_resume_after_shutdown_fence`, using only the existing `Memory`, fault, gated-runtime and runtime-status helpers. No production condition was weakened for this reproduction.

1. Configure normal no-drill policy. Inject `env.meta.fault(Op::Put, "record.json", Fault::Before, 1, 1)` and `env.meta.fault(Op::Get, "record.json", Fault::Before, 0, 1)`. A first run returns `cloud_publication_unknown`; save its pending set ID.
2. Open a gated runtime on the same local policy directory, start its next scheduled run, and wait for both durable job admission and connector entry.
3. Keep the connector blocked; call `shutdown(50 ms)` and assert false. Open the successor runtime. Its listing shows the pending remote record still `staging`; save its state-file bytes.
4. Open the connector gate and join the old run through a second shutdown call.
5. Assert successor state-file bytes are unchanged, then assert remote pending-record state is unchanged.

Command: `cargo test --locked --features server --lib review_ -- --nocapture`.

The file assertion passed. The remote-state assertion failed:

```text
review_pending_publication_must_not_resume_after_shutdown_fence ... FAILED
assertion `left == right` failed: the fenced runtime changed the remote record
  left: String("published")
 right: String("staging")
```

**Suggested fix:** apply the same publication authorization/fence boundary to pending resolution, including a recheck after a potentially blocking connector returns. Keep that authorization centralized so fresh and resumed publication cannot diverge. Define the boundary for already-issued remote requests honestly; do not hold the state mutex across unbounded network I/O merely to make a bounded shutdown appear atomic. Preserve this reproduction as a persistent test.

**Uncertainty/impact:** demonstrated with the in-memory store, not Azure. This proves an omitted code path, not physical request cancellation or data corruption. The successor can eventually reconcile the still-persisted pending handle, so severity is Medium rather than a claimed loss of the local state fence.

### NEW-FW3-02 - Medium, local/concurrency prerequisite - cleanup deletes another writer's file after losing a no-clobber race

**Symbols/locations:** `recovery_bundle::import`, `src\server\recovery_bundle.rs:376-389`; `users::rekey_import`, `src\server\users.rs:1259`.

**Defect introduced by N-05:** account import now enters the unconditional cleanup branch even when it fails **before creating its own `users.json`**. If another writer creates a store after the initial empty-directory/existing-file checks, `persist_noclobber` correctly returns `AlreadyExists`, but the caller then deletes that other writer's `users.json`. It also unconditionally attempts to delete `tenants.json`, whether this import created it or not. Refusing replacement is defeated by ownership-blind cleanup.

**Executed evidence:** added a temporary test named `server::recovery_bundle::tests::review_account_noclobber_collision_preserves_the_other_writers_files`. Its only added scheduling seam was a test-only one-shot hook immediately before `users::rekey_import` calls `file.persist_noclobber(&path)`. The hook writes synthetic, unrelated `users.json` and `tenants.json` sentinel files into the previously empty directory. Account persistence then returns `AlreadyExists`.

With the production cleanup logic intact, the test failed while checking preservation of the unrelated users file:

```text
review_account_noclobber_collision_preserves_the_other_writers_files ... FAILED
assertion `left == right` failed: noclobber loser deleted the winner's users.json
  left: None
 right: Some([sentinel bytes])
```

The next tenant-preservation assertion was not reached; the unconditional tenant deletion is established by the cited source, not claimed as a separately observed assertion.

**Attribution control:** retaining the identical hook and test, move account import back before the cleanup result, as before `987ffaf9`. Ran:

```text
cargo test --locked --features server --lib review_account_noclobber_collision_preserves_the_other_writers_files
test result: ok. 1 passed; 0 failed
```

Thus the new failure is caused by the expanded cleanup boundary, not by changed serialization, password processing or the no-clobber primitive.

**Suggested fix:** retain cleanup after a file was persisted, but make ownership explicit. A helper/guard should clean up only files it actually created and still owns, including its post-persistence sync-failure path; an `AlreadyExists` loser must never unlink the winner. Alternatively enforce exclusive ownership of the entire import directory for all callers. Preserve both the existing post-sync-failure test and this collision test; simply reverting N-05 would reopen the original defect.

**Reachability limitation:** the current offline CLI normally calls the helper inside a unique, private staging directory, so two ordinary restores with the same final output do not share this intermediate admin directory. This is a demonstrated destructive helper-level TOCTOU regression requiring a colliding local writer, not a demonstrated remote exploit or routine concurrent-CLI failure.

### Cross-platform and adversarial analysis without additional findings

- **Windows:** the exclusive helper calls `MoveFileExW` with flags `0`, omitting replacement and copy fallback. Actual free-name, empty-directory and file-destination checks passed. The ordinary-rename negative control destructively replaced the injected empty directory on this host, so substituting the standard library call is demonstrably unsafe here.
- **Linux/macOS, static only:** the branches call `renameat2(..., RENAME_NOREPLACE)` and `renamex_np(..., RENAME_EXCL)` respectively. Paths reject embedded NUL via `CString`; `EINVAL`, `ENOSYS` and `ENOTSUP` map to unsupported publication rather than a replacing fallback. Other platforms explicitly refuse. These branches were not compiled or executed on this Windows worker. A persistent Linux/macOS CI run of the existing two publication tests should be required before asserting cross-platform qualification.
- **Paths and secrets:** the new racing-destination and unsupported-publication errors use fixed text, not the output path or password. The exercised race test checks the output-name exclusion. Existing CLI precondition and post-publication/cleanup diagnostics intentionally identify the operator's destination; that is distinct from leaking a path through the new race branch. No new secret leak was established in the changed paths; this is not a blanket claim about excluded parser findings.
- **Cleanup/TOCTOU:** N-02 excludes symlinks and unexpected direct-child types at inspection time, but is not a hostile shared-parent protocol and still relies on the documented private parent. N-05's ownership regression is separately reproduced above. No attack requiring an untrusted parent is claimed as a new remotely reachable defect.
- **Locks/panics:** the exercised pin-registration race was killed and both shutdown waiters behaved correctly. Static lock tracing found no new inverse acquisition order between the live-set and state locks. Holding the live-set mutex over remote pin/unpin calls can delay unrelated operation-pin admission during a slow store; this is a bounded-transport/concurrency trade-off, not evidence of a lock-cycle deadlock. Saturation and panic/close tests passed, with the arithmetic and close-wait mutants killed.
