## Scope

After `failover execute` the authority is Recovering at epoch N+1 with no
writer and `base` = the former owner's last verified head. Today startup
refuses that record (`writer_authority_base_unverified`), so promotion
cannot complete. Make an authority-enabled writer restore exactly that base
before it opens its database, then claim:

1. `WriterAuthority` keeps the connected `Sets` (and the target) for
   startup. Add a blocking `WriterAuthority::prepare_database(&self,
   database: &Path) -> Result<Option<Value>, String>` (name it as you like)
   that the server binary calls **before** `open(&config)`:
   - read the authority once and keep its `Observed` (record + etag);
   - no `base`, or a writer is present → return `Ok(None)` and change
     nothing (the existing `claim` refusals still apply later);
   - otherwise validate the record (Recovering, `base.epoch < epoch`), pin
     `base.set_id` with an operation pin, `fetch` into a private `Staging`
     directory beside the database, `check_scope` against the record,
     check `fetched.record.set_id == base.set_id`, the manifest sha equals
     `base.manifest_sha256`, and the manifest lineage equals the record
     lineage; restore with `restore_ha_head(&fetched, dir, base)`, so the
     result is exactly `base.sequence` with the base chain and index
     (`seal` already verifies commits and lineage); check the restored
     sequence equals `base.sequence` and the lineage equals the record;
   - durably replace the database: sync the staged file, move the existing
     database (if any) aside with a no-replace rename to
     `<database>.superseded-epoch<base.epoch>` (refuse if that name exists),
     rename the staged file into place, `sync_directory` the parent. Handle
     the engine's sidecar files if `Database::open` keeps any (check), so a
     stale sidecar never applies to the restored file;
   - always release the pin and remove staging (success or failure);
   - return a JSON summary (`set_id`, `epoch`, `sequence`, `lineage`,
     `superseded` path or null) that the binary logs as
     `writer_authority_base_restored` on stderr.
2. `claim` keeps the `Observed` it is given (or re-reads and checks that the
   etag/revision is unchanged since the restore); if anything changed it
   refuses `writer_authority_conflict` with no retry. A CAS conflict on the
   claim is `writer_authority_conflict` with no retry (unchanged). Remove the
   unconditional `base.is_some()` refusal: with a base, claim succeeds only
   after the restore in step 1 produced a database whose lineage and
   sequence equal the base (pass that evidence into `claim`, for example the
   restored `(sequence, lineage)`), otherwise refuse.
3. New refusal `writer_authority_base_mismatch` (409) for any verification
   mismatch: set id, manifest sha, scope/installation, lineage, epoch order,
   index/chain digest, or the restored sequence. The local database must be
   left byte-for-byte unchanged on every refusal (nothing renamed). Keep
   `writer_authority_base_unverified` only for configurations that cannot
   restore safely, and refuse them before any download: `--durability none`,
   a managed-compaction selected candidate (`selected_database` returns
   `Some`), database encryption (`encryption_key` set) unless the restore
   primitives already verify encrypted sets end to end, and recovery mode.
   Add both codes where the other `writer_authority_*` codes are mapped and
   documented.
4. Binary: call the restore after `ReaderApply::enroll` / `Managed::prepare`
   and before `open(&config)`, via `spawn_blocking`. On error call
   `stop_apply` and `stop_trust` and exit non-zero with the `code: message`
   string, as the other startup refusals do. Without
   `--authority-target-file` nothing changes: no authority access, no
   restore, same startup order and output.
5. Loss semantics: commits the old epoch made after its last verified head
   are not restored (they were never archived). `failover report` already
   reports that loss from `head.or(base)`; do not change the report. The
   superseded file keeps those commits for forensics only; document that
   operators may delete it after review and that it is never served.
6. After the claim the next publish is a fresh `publish_ha` at the new epoch
   (ITEM-038 behaviour). Do not change `backup_policy.rs` unless a test
   proves the restored writer cannot publish; if so record a `FINDING:`.
