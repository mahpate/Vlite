Builds and measurement details

Release baseline: the 0.4 release tag, commit 38d5704. Source variants: commit 059650e, with default features and with graph enabled (vector-path overhead only, not graph traversal). Fixed builds, measured on October 25, 2026 UTC with Rust release builds on a shared WSL2 x86_64 host (Xeon Platinum 8370C), not dedicated hardware. A contended first attempt was excluded.

Thirty fresh child processes, one seed and metric, sequential queries and a warm filesystem. Static values are medians of trial-level statistics. Mixed trials rebuild at queries 17, 34, 51, 68 and 85. Whole-child peak RSS was about 11.84 MiB in each variant, including dataset and oracle.

Latency depends on dimensions

At 128d, VLite embedded HNSW is close to zvec (0.454 vs 0.438 ms). At 768d, VLite is about 4× slower than zvec embedded and 2–2.5× slower than Qdrant over REST in the server tier. Recall is comparable, not identical; LanceDB's quantized configuration has lower recall.

Build and reopen remain the gap

At 100k × 768, VLite embedded builds in 524.57 s and reopens plus first query in 518.75 s without an ANN snapshot. HNSW construction was single-threaded in these builds, and these runs rebuild the graph; opt-in snapshots were not measured here. Chroma and FAISS include graph construction in ingest, so compare ingest + build.

Footprint with caveats

VLite has the smallest measured ANN database footprint: 10.2 MiB at 20k × 128 embedded and 295.3 MiB at 100k × 768. It is not smallest in every exact-mode row (LanceDB exact uses 9.8 MiB at 20k). FAISS is an in-memory index library, with no durability or persisted footprint here.

Defaults are not durability-equivalent: VLite was measured with full durability (an fsync per acknowledged batch); pgvector uses synchronous WAL commits; zvec/LanceDB per-write fsync was not verified; Chroma/Qdrant persistence is asynchronous. Ingest is not a fair durability ranking. LanceDB uses one-partition IVF_HNSW_SQ, not plain HNSW; Chroma has no exact mode. Synthetic data, wrapper overhead, shared-host contention and just 2 large-data trials limit generalization. Embedded and server tiers must not be ranked together. Complete methodology, durability contracts, memory/tail-latency data and reproduction commands: benchmark README · harness.

Setup and limitations

vlite-server REST, 20k × 128 clustered dataset, k=10, keep-alive client threads, zero errors. Before is the previous release build. Native Windows 11, Xeon Platinum 8370C (8 cores / 16 threads), CPU gated to ≤50% before each trial. Latency still rises under contention at 16 readers.

Raw data

HNSW traversal

A visited-node bitmap replaced per-node hashing in graph construction and search, for graphs up to 8,388,608 nodes. On 5,000 synthetic 128-dimensional vectors, median rebuild time fell from 5.552 s to 5.080 s (8.5%), and the mean duration of two 100-query batches fell from 76.392 ms to 60.795 ms (20.4%).

Setup and limitations

Each traversal owns one bit per node (the bitmap is at most 1 MiB); larger graphs keep a sparse hash set. Native Windows release build; squared L2, M=16, ef_construction=100, ef_search=100, k=10. One before/after campaign (three rebuilds and two query batches per version) on a shared host with warm caches. Timings are whole rebuilds and query batches, not per-query latency percentiles or a universal gain; no 100k × 768, other-OS or sparse-fallback runs were made. Distance precision, graph-selection rules, filtering and durability are unchanged.

Methodology

Reproduce these results

Build the exact measured commits with the same Rust release toolchain in separate directories, following the campaign instructions. Then run the revision campaign runner; it keeps five repetitions and raw samples per workload. See also the development measurements.

Archived comparisons: pinned packages and commands are in the archived methodology; use them only to reproduce historical data. Raw zvec results: 20k × 128 · benchmark source.
