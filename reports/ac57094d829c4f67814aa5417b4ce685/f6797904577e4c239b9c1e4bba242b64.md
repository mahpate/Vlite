### R1 - PyPI's qualified SHA is not bound to wheel provenance

**Evidence:** `.github\workflows\pypi.yml:44-45` sets `CI_TAG` and the triggering release run's `head_sha`; the latter is empty for manual dispatch. `scripts\ci_policy.py:206-218` therefore qualifies the tag's current commit on manual dispatch. The upload job downloads only wheels and `SHA256SUMS` (`pypi.yml:72-77`), checks hashes and version strings (`:84-106`), and uploads them (`:107-110`). It never reads their recorded source identity.

This is not merely hypothetical unsupported metadata: `docs\INSTALL.md:28-31` expressly supports corrective packaging builds with a per-asset `source_commit`. Baseline `bindings\release_assets.py:18-21,30-36` records those overrides and the manifest's default source commit in `release-manifest.json`.

**Counterexamples/consequence:**

1. A previously published release has wheels built at A. Its tag is subsequently moved to B, which has qualifying CI. A manual PyPI dispatch qualifies B, while `gh release download <tag>` still obtains the release's original A assets. Their hashes/version remain valid. No qualifying run at A is required.
2. Even without moving a tag, a supported corrective packaging asset can record source B while the tag/default source is A. Qualifying A does not establish that the wheel built at B passed CI.

**Executed fixture evidence:** With `CI_TAG=v0.7.4`, `CI_SHA=""`, a fake tag/qualified run at `0123456789abcdef0123456789abcdef01234567`, and wheel bytes identified in the fixture as built at `1111111111111111111111111111111111111111`, the real guard returned `verified=True`. The unmodified, extracted PyPI checksum/selection step also accepted that fixture and selected `pypi-dist/vlite_client-0.7.4-py3-none-any.whl`. All filesystem operations for this probe were in-memory fakes; no real wheel was built or uploaded. The recorded manifest's old source was ignored.

**Smallest fix:** Download and checksum-validate `release-manifest.json`; bind each selected wheel's manifest hash and effective source commit (`asset.source_commit` or the manifest default) to qualified CI evidence before upload. For a minimal restrictive policy, expose the guard's verified SHA and reject wheels whose effective source differs. To preserve documented corrective packaging behavior, qualify every distinct effective wheel-source SHA rather than silently accepting a different commit.

**PRD acceptance issue:** PRD G4 (`:79`) promises CI for the exact published commit, but its prescribed PyPI wiring (`:402-411`) only binds `CI_SHA` on `workflow_run`. FM-B10 (`:454`) catches tag movement before a release-triggered guard, not manual dispatch provenance or per-asset overrides. The implementation follows that wiring; resolving this needs a narrow Part B clarification, not a claim that the current wiring satisfies the stronger guarantee.

### R2 - Truncated job responses can qualify

**Evidence:** `scripts\ci_policy.py:188-196` only validates `total_count` when `counted=True`. Run listings use that option (`:244-248`), but attempt-job listings do not (`:250-252`). Qualification subsequently trusts the collected subset (`:234-241`).

**Executed reproduction:** Return a successful trusted run and one job page with the 18 required successful jobs but `total_count=19`. The guard returns `verified=True`, despite the advertised count mismatch. As a sensitivity check, adding the omitted successful `native (extra, stable)` entry to the full list makes `full_ci_jobs` return `False`: the truncated view can hide information that changes qualification. An omitted otherwise-unchecked job also demonstrates acceptance of a known-incomplete API response, though that alone does not establish untested source.

**Consequence:** The API-evidence fail-closed promise is violated. No live GitHub truncation was induced; this is a bounded fake response demonstrating behavior under an error condition explicitly included in the requested review. PRD `:349` requires count mismatches to be errors; TEST-B07 (`:613`) requires collected-count shortfalls to fail closed. Existing tests only inject this fault in run listings (`tests\ci_workflows.py:971-986`).

**Smallest fix:** Use `slurped(api(endpoint), "jobs", counted=True)` inside the existing retry wrapper. Add enforce/report regressions for missing/mismatched job counts, including a truncated response that still contains every currently required job. Keep a positive test with mandatory jobs split over nonempty pages.

### R3 - Retry sleeps are not deadline-bounded

**Evidence:** `scripts\ci_policy.py:176-185` sleeps the full 5/15-second retry backoff without a clock or deadline. `guard` passes this unbounded sleep into target/workflow lookup and evaluation (`:296-299`); only the polling sleep is clamped (`:308-316`).

**Executed reproduction:** Use a fake clock starting at 1000, one-minute pending/grace bounds, and zero API duration. A pending evaluation sleeps 60 seconds to deadline 1060. The next listing call fails once; `retried` sleeps five more seconds before another pending response. Failure is reported at 1065, with sleeps `[(1000, 60), (1060, 5)]`. Thus the excess is retry sleep, not API execution time.

**Consequence:** The job still has a finite outer timeout (150 minutes for release; 15 for PyPI), and this does not authorize an unqualified run. It does contradict PRD `:348-349` and the v1.2 clarification at `:819`: total waiting excludes only API time, and no sleep may cross the active deadline. The existing deadline tests use API cost but do not inject retry failures at the boundary (`tests\ci_workflows.py:866-881`).

**Smallest fix/design choice:** Thread the applicable absolute deadline/clock through retry backoff and stop or clamp retries once the deadline is exhausted. Define initial evaluation behavior explicitly: PyPI deliberately has zero wait, while the PRD also prescribes retry backoff. Those prescriptions cannot both forbid every post-start sleep and require the complete backoff sequence. Either preserve a strict wait deadline with retries limited by remaining time, or explicitly budget retry overhead separately and amend the PRD, maintainer bounds, and tests. Do not retain the current unconditional "no sleep past deadline" claim.

### Rerun freshness limit in the approved design

The implemented re-fetch closes the requested jobs-fetch-to-verdict race. It does **not** make a successful guard output revocable. The guard runs beside long builds (`release.yml:39-56`); publication later consumes its cached output (`:336-338,445-447,560-562`). A rerun started after qualification, including one that fails before the first digest push, does not re-execute that already successful guard. An in-memory state-change probe confirmed that the returned result remains true after changing the fake run to a failed attempt 2; no scheduler/live-publication claim is inferred from that fixture.

This follows the one-shot architecture and parallel-build decision RD-013 (PRD `:694`), rather than being a deviation from the prescribed implementation. It limits the broader "latest attempt" guarantee in G4/RD-011 (`:79,692`) to the instant of guard evaluation. Before acceptance, state that scope explicitly, or, if freshness at each publication boundary is actually required, add short no-wait rechecks immediately before publication. Such rechecks reduce the window but cannot make GitHub CI reruns and external registry operations atomic. This is an acceptance/design trade-off, not an additional independently asserted implementation blocker.
