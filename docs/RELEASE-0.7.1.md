# VLite 0.7.1 upgrade and rollback

VLite 0.7.1 makes the protection of reserved agent-memory resources structural, stops the gRPC disk-ANN calls from letting a client choose a file path, finishes the follow-ups of the first agent-memory slice, bounds key-value listing and tool input, records a stable actor in audit events and adds Key-value and MemoryAI workspaces to the dashboard.

<!-- source: docs/SECURITY.md, docs/GRPC.md, docs/API.md#agent-memory-rest, docs/projects/roadmap/m71-memory-followups.md, docs/STORAGE-FEATURES.md#key-value-store, docs/CONSOLE.md -->

It follows [0.7.0](RELEASE-0.7.0.md). The store opens unchanged: there is no new file format, setting or migration, and files written by 0.7.0 open as before. A few answers change (see [Compatibility](#compatibility)): recall distances, some requests that now answer 422, backups on servers with memory bindings and the gRPC disk-ANN path rule. Two new guides cover [agent memory](MEMORY.md) and the [key-value store](KEY-VALUE.md). No new benchmarks were run; the [0.7.0 numbers](RELEASE-0.7.0.md#benchmarks) stand.

## What is new

### Security

Which of these apply depends on what you run. The request guard matters on servers with memory bindings or tenants, and the disk-ANN rule on servers with gRPC and scoped credentials.

- **One request guard for every path that names a resource.** A request that names a collection, graph, import job or tenant resource now goes through one per-request guard before any handler looks the name up. The guard qualifies the name for a tenant, checks the credential's name grant, hides a reserved resource from a caller without raw access, looks the name up and then checks the credential's binding to that collection, in that order. It covers REST, gRPC and webhook handlers, including collections named in a request body, credential grants, import jobs, lists, metrics, the slow-query log and change feeds. A reserved agent-memory resource answers like a missing one (like an occupied one on a create) for every caller that does not hold `raw_access` on the owning binding; the administrator token, the read-only token and dashboard sessions never hold it. 0.7.0 made these decisions handler by handler, and its two tenant-isolation fixes came from handlers that looked a name up twice. A source-scanning test now fails when server code looks a collection or graph up by name outside the guard, and a differential test generated from the served OpenAPI document sends every route that names a resource, with reserved, missing and ordinary names, through every kind of caller, with and without bindings. Answers for ordinary names do not change. See [Memory-bound resources](SECURITY.md#memory-bound-resources).
  <!-- source: src/server/guard.rs, tests/server_name_lookup_scan.rs, tests/server_guard_differential.rs, tests/server_memory_reserved_as_missing.rs, tests/server_memory_guards.rs, docs/SECURITY.md#memory-bound-resources -->
- **gRPC disk-ANN paths are the server's for everyone but the administrator.** Before 0.7.1, `BuildDiskAnn` and `SearchDiskAnn` took the sidecar path from the client, so a credential scoped to one collection could make the server write or read a file at a path the client chose, anywhere the server process can reach. Now only the administrator token may name a path (and must send one). Every other caller, a scoped credential or the read-only token, must leave `path` empty: the server then uses `disk-ann-<collection id>.dann` in the administrator directory (`VLITE_ADMIN_DIR`), the file the REST routes use, and a non-empty `path` from such a caller is refused with 422 `invalid_input` (gRPC `INVALID_ARGUMENT`). Without an administrator directory these calls answer 409 `admin_directory_disabled`. Clients that sent a path with a scoped credential must drop it. Only servers that enable gRPC (`--grpc-bind`) were exposed, and the RPCs do not run on encrypted databases. **Rolling back to 0.7.0 reopens the hole**: 0.7.0 lets a credential that holds `index` or `search` name the path. See [gRPC](GRPC.md) and [Security](SECURITY.md#native-rest-tls-and-grpc-mutual-tls).
  <!-- source: src/server/grpc.rs (Sidecar::choose), src/server/features.rs, docs/GRPC.md, docs/SECURITY.md, docs/projects/roadmap/handover-0.7.0.md -->
- **Backups are the administrator's while anything is reserved.** While a memory binding is configured, or the database holds reserved memory resources, the backup routes (list, create, verify, drill and schedule status) answer 403 `forbidden_scope` to every scoped credential, even one that holds the `backup` operation, because a backup holds the reserved data and its database-wide counts. The administrator token still reaches them. **An external backup job that uses a backup credential gets 403 once memory bindings exist: run it with the administrator token, or take the backups before you enable memory.**
  <!-- source: src/server.rs (authorize_need), docs/SECURITY.md#memory-bound-resources -->
- **Hidden attempts are audited without the name.** A credential's request for a reserved resource it may not reach answers like a request for a missing one, so the caller cannot tell. The operator can: the server writes a `reserved_hidden_attempt` entry to the persistent audit log, at most once a minute for each credential and route, with the credential ID, method, route template and request ID, never the name.
  <!-- source: src/server.rs (record_request), tests/server_memory_guards.rs (a_credentials_attempt_on_a_reserved_name_is_audited_without_the_name) -->
- **The administrator's tenant list and usage report count reserved collections.** They now list and count them, so the headroom they show is the headroom a quota enforces (0.7.0 left them out). No credential can read these reports.
  <!-- source: docs/SECURITY.md#memory-bound-resources -->
- **One change-feed rule on every transport.** REST `GET /v1/changes`, gRPC `Changes` and the `WatchChanges` poll, and webhook delivery decide with the same rule, which checks the credential's names and grants, drops events of reserved collections and graphs and drops the attach and detach operations of reserved collections. The gRPC calls stay administrator-only; the change is that a route-level refusal is no longer the only barrier, and behavior is unchanged for every caller that can reach those routes.
  <!-- source: src/server/guard.rs (retain_feed_change), src/server/grpc.rs (changes, poll_changes), tests/server_memory_reserved_as_missing.rs -->
- **A reserved graph takes only its own evidence collection.** Attaching a record of any other collection to a node of a reserved graph answers 409 `graph_record_not_attachable`, raw holders included, so an ordinary record cannot be pinned by a reserved graph. Records attached by an earlier version stay attached until the holder detaches them. Under 0.7.0 a raw credential could attach an ordinary record to a node of its reserved graph, and nobody without raw access could then delete or detach it.
  <!-- source: src/server/guard.rs (attachable), tests/server_memory_guards.rs, docs/SECURITY.md#memory-bound-resources -->
- **Audit events name a stable actor.** Events that record who acted carry an `actor` that holds no secret: `admin_token`, `user:<account id>`, `read_only_token` or the credential ID of a scoped API key. The events are `kv_put`, `kv_delete`, `memory_request`, `collection_created`, `collection_dropped`, `collection_settings_changed`, `credential_denied` and the account events. Two super admins can now be told apart (the `principal` of a `kv_put` or `memory_request` event reads `admin` for every super admin), and an account has the same actor in all its sessions. See [Audit actors](SECURITY.md#audit-actors).

### Agent memory

Agent memory stays opt-in and off without a bindings file. These follow-ups finish the first slice; the [agent memory guide](MEMORY.md) describes the whole feature.
<!-- source: docs/projects/roadmap/m71-memory-followups.md, docs/API.md#agent-memory-rest, docs/SECURITY.md#memory-bound-resources -->

- **`exact` and `mmr` recall measure cosine distance.** `ranking.selection` `exact` orders its vector candidates by `1 - cos` (0 for the same direction, 1 for orthogonal and 2 for opposite vectors), and both `exact` and `mmr` report it as `scores.distance`. The default `weighted` selection is unchanged and still measures squared Euclidean distance. A query vector of zero length has no direction: `exact` and `mmr` answer 422 `invalid_input` (0.7.0 accepted one under `exact`). A stored zero vector is never a vector candidate of `exact` or `mmr`.
- **`exact` accepts `text` together with a vector** (0.7.0 refused it with 422 `memory_unsupported_ranking`). The vector candidates are ordered by cosine distance and fused with the BM25 text candidates by reciprocal rank; a candidate found only by text is kept without a `scores.distance`. `mmr` with `text` still answers 422 `memory_unsupported_ranking`, and `mode: approximate` still answers 422 `memory_bounded_plan_unsupported`.
- **Evidence references on `remember` items.** An item may carry `evidence: [{"collection": "<binding name>", "record": <u64>}]` that names a record that already exists in the binding's evidence collection (at most one per item). It needs a grant with `raw_access`: without it the answer is one 403 before any record is looked at. A record that is missing, hidden or already held by a memory is one 409 `memory_attachment_conflict`. The request-level `evidence` list and the `evidence` of a consolidate output stay refused. Attaching transfers the record to the memory: forgetting the memory deletes the record too, so do not attach a record you still need. It is a one-way change for the file; see [Rollback](#rollback).
- **The raw graph batch route refuses memory's reserved names.** `POST /v1/graphs/{graph}/batch`, on every graph and for every caller, answers 422 `invalid_input` ("a node key or label is reserved for agent memory") and writes nothing when an operation creates or replaces a node (`create_node`, `upsert_node`) with a reserved key or with a label that starts with `VliteMemory`, patches (`patch_node`) a node with a reserved key, or adds such a label to a node. Reserved keys start with `scope:v1:`, `mem:v1:`, `receipt:v1:`, `receipt-outcome:v1:` or `content:v1:`, or are exactly `binding:v1`. Deleting such a node and removing such a label from a node with an ordinary key stay allowed. A raw caller that wrote those names under 0.7.0 now gets 422.
- **A binding's identity is stored in the database.** Each bound graph holds one record node, `binding:v1`, with the binding's name, tenant, generation, state, receipt window, graph and evidence names and a digest of its grants. Each start checks the bindings file against the records. A binding's receipt window, graph and evidence collection never change; changing grants or state needs a higher `generation`; a retired binding never becomes active again and keeps its `retired_at_ms`; an entry leaves the file only after it is retired and its receipt window has ended. A start that breaks a rule is refused with a fixed message that names nothing. Before every `remember`, `consolidate` and `forget`, the server rereads the record under the write lock; a missing or different record answers 409 `memory_capability_unavailable` with `details.feature` `binding_generation` and writes nothing. A graph is adopted when it is empty, holds the binding's record or (once, for a graph that a 0.7.0 server adopted) holds nothing but memory nodes; one node labelled `VliteMemoryScope` no longer makes a graph adoptable. Without a bindings file, a graph that holds a record and its evidence collection stay reserved from the raw routes, with no grants.
- **Two limits are documented, with no change in behavior.** Idempotency keys are scoped to the binding and the memory scope, not to the credential, so credentials that may write one scope are peers. The receipt `sequence` is the database's commit sequence and has no per-binding form: use separate database files for tenants that must not observe each other's write volume.

### Key-value store and tools

- **Bounded listing memory.** A list used to collect and sort every matching key before it applied `limit`. It now keeps only the `limit + 1` smallest candidate keys while it scans, so its working memory no longer grows with the number of matching entries. The scan still reads the whole collection, so its cost still grows with the number of entries. The Rust `KvView::visit_at` lends each entry (`KvRef`, with `has_next`) to a callback instead of copying it; `list` still copies every value it returns, so use a smaller `limit` or `visit_at` when values are large.
- **Slot exhaustion is counted.** The JSON and Prometheus metrics carry `kv_slots_exhausted_total`: the number of REST or gRPC requests answered `kv_slots_exhausted` (409, gRPC `FAILED_PRECONDITION`), for all credentials together. Anyone who can write a collection can fill the 16 record IDs of a key, and a rise that nobody expects points at records planted over a key's IDs. Behavior and format are unchanged. See [Key-value permissions](SECURITY.md#key-value-permissions).
- **Input lines are capped.** `vlite-mcp` reads request lines of at most 128 MiB (134,217,728 bytes) and answers a longer one with JSON-RPC error -32600 (`id` null), then goes on with the next line. `vlite-shell` reads command lines of at most 16 MiB; a longer line fails with `invalid_input: line exceeds 16777216 bytes`. `vlite-import` reads JSONL and COPY lines of at most 16 MiB; a longer line is rejected like any bad row (`rejected row N: line exceeds 16777216 bytes`) and nothing is published. CSV, pgvector, FAISS, Parquet and Arrow have no line limit. 0.7.0 read lines of any length. Each cap is above the largest input the engine accepts.

### Dashboard

The dashboard has two new workspaces, **Key-value** and **MemoryAI**, so it now has nine. Key-value browses an existing one-dimension collection by namespace and prefix and writes with exact version conditions; MemoryAI remembers, recalls, consolidates and forgets through an operator-provided binding with a scoped API token, because administrator sign-in alone grants no memory access. Search gains controls for embedding and ranking providers (an alias that the operator configured offline; models and secrets are never entered in the dashboard) and management of named and sparse vectors. Graphs are interactive in 2D and in force-directed 3D: drag nodes, pan (2D) or rotate (3D) the view and zoom. See the [dashboard guide](CONSOLE.md).

## Fixed

- **A record put with a due expiry answered 500 after writing.** `PUT /v1/collections/{collection}/vectors/{id}` and `PUT /v1/vectors/{id}` answered 500 `internal_error` to an `expires_at_ms` that was already due, or to `ttl_ms` 0, after the new record had been written: the old record was replaced by one that read as absent. They now answer 422 `invalid_input` before anything is written. gRPC `PutVector` stored such a record without an error; it now answers `INVALID_ARGUMENT` for a due `expires_at_ms`. An expiry must be later than the server clock when the write is applied, and `ttl_ms` is a lifetime of at least 1 ms counted from that moment. Errors that the engine raises first, such as a file older than format 5, a failed `If-Match` or an invalid vector, keep their answers. The key-value routes still accept an already due deadline by contract. See [Record expiry and metadata](API.md#record-expiry-and-metadata).

## Upgrade

Back up and verify checksums first. Replace the binary or image with 0.7.1 and restart. The store opens unchanged: there is no format change, no setting and no data migration, and existing files are never converted in place. Follow the single-writer rule in this order: stop the old process (or scale the old revision to zero replicas), then start the new one. A hosted app whose platform normally starts the new revision before it stops the old one (a rolling update) must be set to stop the old one first, so that only one process opens the file. The [Container Apps deployment](../deploy/azure-container-apps/README.md) works this way: it deactivates every old revision, waits for zero replicas and accepts the downtime.
<!-- source: docs/RELEASE-0.7.0.md#upgrade, docs/DOCKER-OPERATIONS.md#upgrade, deploy/azure-container-apps/README.md -->

Check these before you upgrade:

- **Agent memory.** If you use memory, read [First start under 0.7.1](#first-start-under-071) below and check two things. First, reserved names in graphs: a graph you bind must hold only memory nodes (a `raw_access` holder may have written ordinary nodes into a bound graph under 0.7.0, and the first start refuses it), and no raw writer may send a label that starts with `VliteMemory` or a key with a reserved prefix (it now gets 422). Second, the bindings file: the receipt window, graph and evidence names of each binding must still be the ones 0.7.0 used, and a change to grants or state needs a higher `generation`.
- **Backups.** An external job that backs up with a backup credential gets 403 once memory bindings exist. Switch it to the administrator token, or take the backups before you enable memory.
- **gRPC with scoped credentials.** A client that sends a disk-ANN `path` with a scoped credential or the read-only token must stop sending it.
- **Recall thresholds.** For vectors of unit length the order of `exact` and `mmr` hits is unchanged and the reported distance is half the 0.7.0 value (0.7.0 reported squared Euclidean distance). For vectors that are not unit length the order of `exact` hits can change, and every `scores.distance` of `exact` and `mmr` changes: recalibrate any threshold on it. `weighted` recall is unchanged.
<!-- source: docs/API.md#start-the-server-with-memory, docs/projects/roadmap/m71-memory-followups.md (sections 1.6 and 3.2), docs/SECURITY.md, docs/GRPC.md -->

### First start under 0.7.1

These apply to a server that has a memory bindings file.
<!-- source: docs/API.md#start-the-server-with-memory, docs/projects/roadmap/m71-memory-followups.md (section 1) -->

- On a writable primary, the first start writes one record per bound graph (one node and one commit each), then provisions the granted scopes as before. An unchanged record is not rewritten, so a restart with the same file adds no commit. A read-only node or a replica runs every check, writes nothing and keeps using the file where a record is still missing.
- A graph that a 0.7.0 server adopted gains its record at that first start. A bound graph that holds anything but memory nodes (for example ordinary nodes that a `raw_access` holder wrote into it under 0.7.0) is refused as holding ordinary data: start once without the bindings file, delete those nodes with the raw routes, and start again with the file.
- An entry that is already `retired` and has no record yet counts as retired by this start, so a `retired_at_ms` in the past is refused (the message is "a memory binding retirement time precedes this start"): set it to the current time or later.
- A file whose active entry changed its receipt window or its graph or evidence names (these never change), or its grants or state without a higher `generation`, since its record was written is refused; so is an active entry that was removed before it was retired and its receipt window had ended.
- The raw-name guard and the record ship together: adoption relies on the guard. Nodes planted before 0.7.1 are not found by the guard, and a forgery that consists only of well-formed memory nodes cannot be told from memory, so bind only resources that were created for memory.

These changes apply automatically and need no action: the request guard, the hidden-attempt audit, the tenant usage report, the change-feed rule, the bounded key-value scan and page, the line caps, the 422 for a due record expiry and the dashboard. Evidence references need explicit use: an item that carries one and a grant with `raw_access`.

## Rollback

Restart with the 0.7.0 binary or image. 0.7.1 writes nothing that 0.7.0 cannot read, with the exceptions below. 0.7.1 adds no route, but 0.7.0 refuses an item `evidence` field with 409 `memory_capability_unavailable` (feature `evidence`) and `exact` recall with `text` with 422 `memory_unsupported_ranking`, so stop clients from sending them.
<!-- source: docs/API.md#start-the-server-with-memory, docs/projects/roadmap/m71-memory-followups.md (sections 1.6 and 5.4) -->

- **Item evidence references (one-way).** An evidence reference is stored in the memory node as the literal token `record:<number>`, which a 0.7.0 server cannot read. After the first reference, do not roll back to 0.7.0. Measured with the real binaries (a 0.7.1 build wrote one memory with a reference; a 0.7.0 server then opened the same files):

  | On 0.7.0, in the scope that holds such a memory | Answer |
  |---|---|
  | recall by seed, recall by vector, a new `remember`, `forget`, `consolidate` | 500 `internal_error` |
  | an exact replay of a `remember` that carried no reference | 200 |
  | a replay of the request that carried the reference | 409 `memory_capability_unavailable` (feature `evidence`) |
  | any operation in another scope or another binding | 200 |
  | a raw read of the evidence record | 200, intact |

  The server stays up and writes nothing wrong; the failure is explicit, but it covers every memory operation of that one scope. **Recovery:** run 0.7.1 or later and `forget` the memory. That deletes the node and the referenced record and leaves no token behind, and 0.7.0 then answers 200 again for recall and a new `remember` in the scope. `scripts/memory_evidence_downgrade_check.py --new-bin PATH --old-bin PATH` repeats the measurement with two server binaries.
  <!-- source: docs/projects/roadmap/m71-memory-followups.md (section 5.4), docs/API.md#start-the-server-with-memory, docs/SECURITY.md#memory-bound-resources, scripts/memory_evidence_downgrade_check.py -->
- **A bound graph that never received a scope.** 0.7.0 ignores the record node: it finds memory nodes by label and scope nodes by key, and only its adoption check looks at the whole graph. That check accepts any graph with a scope node, so every graph that holds one rolls back safely. A bound graph that never received a scope (a binding without grants, or one that was retired before it had any) holds only the record, and 0.7.0 refuses it as holding ordinary data: empty that graph or delete the record node first.
  <!-- source: docs/projects/roadmap/m71-memory-followups.md (section 1.6), docs/API.md#start-the-server-with-memory -->
- **gRPC disk ANN.** 0.7.0 lets a credential that holds `index` or `search` name the sidecar path again. If you run 0.7.0 with gRPC, do not give those operations to credentials you do not trust.
  <!-- source: docs/projects/roadmap/handover-0.7.0.md, docs/GRPC.md -->

0.7.0 reads the bindings file itself and does not know the binding record, so it reserves what the file names and nothing else. The 0.7.0 dashboard has no Key-value or MemoryAI workspace.

## Compatibility

- **Files and defaults.** No file format, flag, setting or dependency changes, and the minimum Rust version (1.89) is unchanged. A file written by 0.7.1 opens in 0.7.0, with the two memory exceptions under [Rollback](#rollback). Defaults are unchanged.
  <!-- source: Cargo.toml, docs/RELEASE-0.7.0.md#compatibility, docs/API.md#start-the-server-with-memory -->
- **Wire.** There are no new routes or RPCs. Answers change in these places: recall distances and `exact` with `text`; the item `evidence` field; 422 from the raw graph batch route for reserved names; 422 from the record put routes for a due expiry or `ttl_ms` 0; 409 `graph_record_not_attachable` for an attach to a reserved graph; 403 from the backup routes while anything is reserved; 422 or the server-derived path for a gRPC disk-ANN call by a caller that is not the administrator; and the `binding_generation` value of `details.feature`. The metrics gain `kv_slots_exhausted_total`, and the OpenAPI document says that the put `expires_at_ms` must be later than the server clock and that `ttl_ms` is at least 1.
  <!-- source: src/openapi.json, src/openapi_graph.json, docs/API.md, docs/GRPC.md, docs/SECURITY.md -->
- **Audit log.** The events listed under [Security](#security) gain an `actor` field. `kv_put`, `kv_delete` and `memory_request` keep their `principal`. The collection events already had an `actor`, which read `admin` for the bootstrap token and for every super-admin session; it now reads `admin_token` or `user:<account id>`, and the credential ID is as before. `credential_denied` keeps `credential_id` and adds an `actor` that equals it. Check any reader that matches on `admin`.
  <!-- source: docs/SECURITY.md#audit-actors, tests/server_audit_actor.rs -->
- **Tools.** The line caps above apply to `vlite-mcp`, `vlite-shell` and `vlite-import`; input that fits the engine's limits is unaffected. The tool list of `vlite-mcp` is unchanged.
- **Rust.** `KvView::visit_at` and `KvRef` are new public items in `vlite::kv`. `KvView::list` and `list_at` return the same entries as before.
  <!-- source: src/kv.rs, site/api.html -->
- **Memory limits.** The first-slice refusals and error codes are unchanged except for the ones listed above; every refusal and its `details.feature` is in [Agent memory (REST)](API.md#first-slice-limits).

## Not included in this release

These are not available, and you should not rely on them.
<!-- source: docs/projects/roadmap/next-major.md, docs/API.md#first-slice-limits, docs/RELEASE-0.7.0.md#not-included-in-this-release -->

- **Compact and float16 vector storage and compact graph storage.** Internal work that nothing activates: Float32 stays the only storage precision and production graph storage is unchanged. It moved to 0.7.2.
  <!-- source: docs/projects/roadmap/next-major.md, docs/projects/performance/storage-goals.md -->
- **Agent-memory facts and erasure jobs.** `facts/query`, `facts/correct`, `erasures/get` and `erasures/resume` answer 409 `memory_capability_unavailable` with `details.feature`, and `forget` by series, entity, session or scope is refused the same way. `forget` by ID is logical deletion, not secure erasure.
- **Approximate recall.** `mode: approximate` answers 422 `memory_bounded_plan_unsupported`: no approximate index is built for a binding, and none is built lazily.
- **Leases and a fencing-token ledger.** This is a design only and is not implemented. Key-value versions are not such a ledger (see [Key-value store](KEY-VALUE.md#revisions-are-not-fencing-tokens)).
  <!-- source: docs/projects/roadmap/gap2-lease-ledger.md, docs/STORAGE-FEATURES.md#key-value-store -->
- **A key-value batch.** Each call reads, writes or deletes one key, and a list returns one page. There is no multi-key atomic operation.
  <!-- source: docs/API.md#key-value-entries, docs/GRPC.md#key-value-entries -->
- **Unchanged from 0.7.0:** temporal graph, a Cypher-style query subset and document-to-graph ingestion are not available (see [0.7.0](RELEASE-0.7.0.md#not-included-in-this-release)).
