Storage and records

Persistence, record operations and collections
FeatureSupport and requirements
Single-file databaseA portable, versioned binary log in one authoritative .vlite file. Optional indexes and administration state can use sidecar files.
Durable commitsChecksummed frames, written before a write is acknowledged. Corruption and an incomplete trailing write fail with different errors.
Durability modesPeriodic (default): commits reach the OS at once and a background flusher syncs them every 60 s (1 ms to 60 s per handle). A process crash loses nothing acknowledged; an OS crash or power loss can lose up to the last interval. Full syncs every commit before acknowledging it. None keeps the database in memory only and loses all data on restart. Server: --durability periodic|full|none.
Vector CRUD and browsePut, get, delete, numeric-ID pagination, payload bytes and typed metadata. IDs keep all 64 bits.
Atomic batchesUp to 4,096 operations and 16 MiB per batch, within one collection. Only graph batches span collections.
Conditional writesRecord revisions, put-if-absent and revision-checked puts and deletes. A conflict writes nothing.
Named collectionsIndependent dimensions, IDs, settings and derived indexes in one file. Requires format 4 or 5.
Record expiry (TTL)Absolute expiry timestamps, expiry-aware reads and compaction. Requires format 5.
Metadata-only updatesChange metadata without rewriting the vector or payload; expiry is kept. Requires format 5.
Resumable ingestionAtomic chunks with durable checkpoints, replay detection, row validation and reject or skip-invalid policies. Requires format 4 or 5.
In-memory databaseCreate in memory, open from bytes and export bytes; the host handles persistence.

Search and retrieval

Query modes and result shaping
FeatureSupport and requirements
Exact vector searchSquared L2, cosine and negative inner product, with f64 accumulation, distance-then-ID ordering and bounded top-k memory.
Approximate vector searchHNSW for squared L2 and cosine. Lazy mode may build the index synchronously; ready-only mode never builds.
Typed metadata filtersEquality, ranges, membership, existence and geographic radius predicates. Numeric types stay distinct.
Filtered ANNApproximate retrieval with metadata eligibility checks; recall depends on the workload and search budget.
Automatic query planningExact scan, indexed exact, ready ANN and filtered ANN, with plan and stats reporting. Auto mode never builds an ANN index.
Text searchBM25 on declared string metadata fields, with lowercase alphanumeric tokenization.
Hybrid retrievalDense plus BM25, or dense plus sparse, fused with weighted reciprocal rank fusion.
Grouped resultsGroup nearest matches by a metadata field, with a per-group hit cap.
RecommendationsPositive and negative examples; example IDs are left out of the results.
Facets and statisticsMetadata facet counts and numeric statistics.
Geographic searchGeoPoint metadata, Haversine-radius filtering and ranking by vector or geographic distance.
Read-only query languageParameterized vector and text search, predicates, groups, facets, ordering and limits. Not SQL or a scripting runtime.

Indexes and concurrency

Search acceleration and concurrent access
FeatureSupport and requirements
Rebuildable HNSWDeterministic parallel construction that does not depend on thread count, vectorized distances, configurable graph and search budgets, and bounded mutation buffering.
Scalar-u8 quantizationCompressed traversal codes with full-precision reranking of candidates. Original vectors stay in memory.
Metadata indexesEquality and range indexes with full-filter rechecks; rebuilt on reopen and on settings changes.
ANN restart snapshotsAn optional validated graph cache tied to the database state, from the server (--ann-snapshot), Rust, the C ABI and Python. Not available for encrypted databases.
Disk ANNAn optional graph and vector sidecar with a bounded node cache. Builds still need in-memory HNSW capacity; no metadata or expiry filtering.
Index quality and memorySampled recall against exact results, index identity and readiness, and component-level memory diagnostics.
Parallel exact scansNative Rayon scans above workload thresholds; not on WebAssembly.
Concurrent server readsShared reads and exclusive writes; bounded committed snapshots for eligible exact queries.
Shared embedded readersSeveral read-only processes under shared file locks, excluding a writer. Reopen to see later commits.
Committed read snapshotsRust handles for bounded exact search, get and browse outside the owner lock.
Background rebuildsExplicit start, poll, cancel and maintenance controls; optional server scheduling with retry backoff.
Durable group commitAn optional shared sync for bounded concurrent record writes; each write keeps its own atomic frame.
Read-lock policy--lock-held-reads trades snapshot copying for holding the owner read lock during exact scans.

Vectors and AI integration

Embedding management and reranking
FeatureSupport and requirements
Named dense vectorsIndependent dimensions and metrics per vector name, with exact and ready-only named HNSW search. Requires format 5.
Sparse vectorsSorted sparse values, derived inverted postings and negative-dot-product retrieval. Requires format 5.
Model version historyActive and retained vector versions, explicit retention and pruning, and version-targeted search. Requires format 5.
Resumable re-embeddingDurable job checkpoints, source-revision checks and atomic activation on completion. Your application schedules provider work.
Embedding providersAn application-owned Embedder registry; an optional OpenAI-compatible HTTP provider with http-embedder.
RerankingPluggable providers, exact metric rescoring and MMR diversity selection.
Typed float32 inputsPython buffer methods (search_f32, batch_put_f32) and Node.js Float32Array methods (searchF32, searchManyF32, batchPutF32). Inputs are copied, not zero-copy.
GPU exact searchAn optional gpu build using wgpu: default-collection squared L2 with CPU reranking and fallback. No filtered or cosine GPU search.

Property graphs

Opt-in graphs stored in the same file and commit log as vectors
FeatureSupport and requirements
Opt-in per fileCreate a graph file with create_with_graph or vlite-graph-cli init, or copy one with vlite-maintain enable-graph. Other files stay vector-only. Older releases refuse graph files.
AvailabilityCompiled into every build: release binaries, the C library, Python wheels, Node.js release tarballs and the Docker API server. vlite-graph-cli ships in the release archives, not the Docker image.
Data modelUp to 64 named graphs per file. Nodes have a unique key, labels and typed properties; edges have a type, endpoints, an optional key and properties. Attachments link nodes to live vector records.
Atomic graph batchesUp to 4,096 node, edge, attachment and vector operations, in any collection, commit atomically or not at all. expected makes an operation conditional.
Bounded readsNode and edge gets, paged find and neighbors, traversal and shortest path, each on one committed view. Hop, work, output and deadline limits apply; results report completeness and truncation.
Schemas and property indexesLabel and relationship rules for required and unique properties, endpoints and multiplicity. Property indexes serve node lookups and are rebuilt on open.
Hybrid retrievalA vector, text or fused pivot search, mapped to nodes through attachments and expanded, returns nodes with their evidence records.
Query textA small read-only language that maps to one typed read.
SurfacesRust, vlite-graph-cli, MCP vlite_graph_* tools, REST /v1/graphs, the C ABI, Python, Node.js and the dashboard Graph workspace. Schemas, retrieval and query text are not in the C ABI, Python or Node.js yet.
Access controlGraphs are tenant-owned. API keys need graph_read or graph_write and a graphs binding; accounts get role-based access, narrowed by graphs and graph_access. Collection scope never implies graph scope.
Maintenance and rollbackBackup, restore, verify, compaction, re-encryption and read replicas keep graph state. vlite-maintain strip-graph --confirm-graph-data-loss copies the vectors to a plain format 5 file.
Not supportedChange feeds and webhooks refuse graph files, gRPC has no graph service, format upgrade rejects graph files, and vlite-graph-cli cannot open encrypted files.

Encryption at restChaCha20-Poly1305 frame bodies and Argon2id passphrase derivation. Frame prefixes stay visible.
Key rotationValidated copy-out re-encryption; encrypted backups keep encrypted bytes.
Token authenticationAdmin and optional read-only HTTP bearer tokens, plus scoped API keys.
Dashboard accountsSuper admin, editor and viewer roles, Argon2id password hashes and HttpOnly, SameSite=Strict cookie sessions (by default 30 minutes idle, 8 hours total). Sign-in needs HTTPS or a loopback-only server.

HTTPS and gRPC TLSNative TLS or a trusted reverse proxy; optional gRPC client certificates.
Certificate reloadAdmin-triggered, validated identity and CA reload; existing sessions are unchanged.
Audit and redactionAdministrative audit history, redacted request logs and allowlisted trace attributes.

Operations, recovery and integration

Maintenance and operational visibility
FeatureSupport and requirements
Inspect and verifyOffline file, header and frame validation, detailed reports and keyed operations on encrypted files.
Backup and restoreValidated byte-preserving copies, backup drills, optional schedules and retention, and restart-selected server restore.
Compaction and format upgradeValidated copy-out maintenance; original files are never replaced in place.
Interrupted-write recoveryExplicit repair of an incomplete tail; complete but corrupt data fails closed.
Point-in-time restoreSequence-targeted restore; timestamp targets need commit timestamps. Restores publish a new lineage.
Change feedLineage and sequence cursors, whole-commit batches and explicit cursor invalidation after history changes. Requires format 4 or 5; not available for graph files.
Read replicasValidated log-segment export and apply, lag status and explicit promotion. File shipping, not automatic network replication.
WebhooksAt-least-once change-feed delivery with HMAC signatures, retry backoff and persisted subscriptions and cursor. Consumers deduplicate events.
Health and metricsHealth endpoints, JSON and Prometheus metrics, latency and route counters, and queue, sync, snapshot and rebuild diagnostics.
Live logsA bounded in-memory ring, sequence cursors, filters and JSONL export; not a durable log archive.
OpenTelemetryOptional OTLP tracing through otel, with an operator-configured collector.

  • Seven workspaces: Overview; Collections, Search and Graph under Data; Observability and Administration under Server; and the Developer Console under Tools.

  • Paginated records with selectable metadata columns and a Payload, Metadata, Vector and Raw JSON inspector.
  • One-record and bulk JSON writes with validation, revision checks and confirmation before every change.
  • Quick JSON and CSV import and export, and resumable large-file import for JSON, NDJSON and CSV.
  • Collection creation and settings, index builds and background rebuilds, readiness and sampled recall.
  • Exact, approximate, ready-only, automatic and hybrid search with a filter builder, explain, exact-versus-approximate comparison, copy as code and saved queries.

  • Observability: live request metrics and log tail, slow-query diagnostics and the change feed.
  • Administration: health and token files; users, API keys, tenants, admin tokens and the audit log; backups, drills, schedules, point-in-time restore and replication-log export; automatic index maintenance, webhooks and TLS certificate reload.

Command-line tools and agents

  • Interactive or scripted shell: query records and collections; --read-only disables writes, but the shell still takes an exclusive file lock.
  • Offline maintenance: inspect, verify, back up, restore, compact, upgrade and re-encrypt, plus enable-graph and strip-graph for graph files.
  • Import: CSV, JSONL, pgvector text and supported FAISS input; optional Parquet and Arrow IPC with import-formats.
  • Search quality: exact-oracle recall, configuration and database comparison, and bounded index evaluation.
  • Index tuning: a workload-based configuration advisor with memory and recall trade-offs.
  • Benchmark harnesses: seeded or external vectors, mixed writes and deletes, and raw timing and memory reports.
  • Graph CLI: vlite-graph-cli creates graph files and runs graph reads and write batches as JSON.
  • MCP server: stdio tools with shared-lock read-only access by default and an explicit --writable mode. Graph tools work on a file or through a server with --server URL.
  • Agent skills: four skills for RAG, MCP, operations and index tuning.

Requirements and boundaries

  • The live dataset must fit in RAM. Disk ANN bounds its node cache, not the database's overall memory footprint.
  • One exclusive writer or several shared read-only owners per file; no embedded writer and readers across processes at the same time.
  • File creation defaults to format 3. Collections and checkpoints need format 4 or 5; expiry and extended vectors need format 5. Upgrades are explicit.
  • Vector batches stay within one collection; only graph batches span collections. No distributed consensus, automatic network replication or inner-product ANN.
  • Plaintext ANN sidecars are unavailable with encrypted databases. TLS and access controls are separate from file encryption.
  • Tenants share one file. Their isolation is logical, not cryptographic.
  • Embeddings come from your application or provider. VLite does not bundle a model runtime.
  • Recovery checks do not certify physical power-loss behavior; filesystem and hardware guarantees still apply.
  • Property graphs are opt-in per file. Graph files do not support change feeds, webhooks or format upgrade.
