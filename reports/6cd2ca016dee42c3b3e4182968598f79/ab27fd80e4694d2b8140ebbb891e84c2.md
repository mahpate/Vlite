# EPIC-005 independent review

**Verdict: CHANGES REQUIRED. Validation status: INCOMPLETE for the requested cross-platform, crash-durable isolation guarantees.** The permitted Windows test suites pass, but publication is not atomic across the database and admin state, and downloaded database staging is not private by construction. Additional isolation, resource-limit, redaction and exit-status changes are needed.

Reviewed commit `dbdf36f23d9e6d34aa88e33c92e786d9f9eeb04f`. Actual checkout HEAD is `6e406dc5911cc8b4859db8c733bba4618e295c39`, not the stated target HEAD; its only difference from the reviewed commit is the supplied PRD. `src`, tests and Cargo manifests/lockfile are identical. No source was changed in the checkout.

## Scope and requirements

Read the PRD first: requirements at `docs/projects/feature-backup-ha/feature-backup-ha.prd.md:222-243`, AC-003/004/006 at `:304-307`, security at `:341-347`, ITEM-007 at `:462-468`. Reviewed the complete new `cloud_recovery.rs`, the target commit's specified diffs, and the invoked fetch, import, restore and drill implementations.

## Findings

### HIGH

#### CR-01 — Final database becomes visible before admin recovery is complete

- **Location / symbols:** `src/server/cloud_recovery.rs:350-386`, `restore_pinned`, `cleanup_admin`, `undo`; `src/maintenance.rs:733-784`, `publish_held`; `src/server/recovery_bundle.rs:248-253`, `import`.
- **Impact:** An interrupted restore leaves a final-named, openable restored database with no fresh admin, or partially published admin stores. The operator cannot safely interpret destination existence as restore completion, and retry refuses the existing database. Ordinary rollback also ignores removal errors. This is not a claim that the command automatically serves or selects the copy.
- **Evidence:** `maintenance::restore` publishes and releases its held file lock before `inspect_detail` and account/tenant import. Those stores are persisted independently. There is no durable restore transaction, completion marker, crash reconciliation or single publication boundary for both outputs. A post-publication Unix directory-sync failure is explicitly `PublicationIndeterminate` in `publish_held`, but the caller's restore-error branch only removes an empty admin directory; it does not resolve the visible database.
- **Executed fixture reproducer:** In a throwaway source copy only, insert a test-only `std::process::exit(97)` immediately after successful database restore and before inspection/import. Run the existing fake-store setup in a subprocess. Observed exit 97, final `restored.vlite` present, final `restored-admin` present, both `users.json` and `tenants.json` absent, and the download directory left behind. This is deterministic stage fault injection, not a Linux power-loss test.
- **Fix:** Build, load and verify the database and admin stores inside one private recovery root, including actual fresh-admin authentication, then publish that root with no replacement and appropriate directory durability. If two arbitrary destination roots must remain supported, use a durable typed transaction and recovery protocol that prevents either from being considered complete until both are committed. Preserve/report publication-indeterminate outcomes and rollback failures rather than silently presenting ordinary failure. Reconcile or quarantine interrupted transactions on retry.

#### CR-02 — Download staging can expose the whole database to other local users

- **Location / symbols:** `src/server/cloud_recovery.rs:334-341`, `restore_pinned`; `src/server/cloud_backup.rs:1228-1242`, `Sets::fetch`; locked `tempfile` version at `Cargo.lock:2784-2785`.
- **Impact:** On Unix with a searchable destination parent and ordinary umask 022, the staging directory is normally 0755 and downloaded `database.vlite` is normally 0644. Another local user can read the sensitive database during download, verification and the drill; a crash extends exposure. A randomized name is not access control.
- **Evidence:** The `tempfile::Builder` sets a prefix but no permissions. Fetch uses ordinary `OpenOptions::create_new` without a restrictive creation mode. The downloaded `tempfile` 3.27.0 source explicitly documents default tempdir permissions as 0777 before umask (`src/lib.rs:389-407`); `src/dir/imp/unix.rs:11-21` only sets a mode when the caller supplied permissions. The final database's restrictive `NamedTempFile` permissions do not protect the earlier downloaded copy.
- **Reproducer / qualification:** Static Unix permission analysis; not executed on Linux. On Linux, run a restore beneath a 0755 fixture directory with umask 022, pause after `fetch`, and inspect/read `.vlite-cloud-restore-*/database.vlite` from a second test identity. Windows inherited ACL exposure was not qualified.
- **Fix:** Create staging owner-only from the outset (0700 directory and 0600 files on Unix), enforce a restrictive Windows ACL or a verified private parent, and verify ownership/access before writing. Do not rely on ambient umask or late chmod. Include interrupted-staging cleanup without touching unrelated directories.

### MEDIUM

#### CR-03 — Destination validation does not establish a stable, link-free isolated directory

- **Location / symbols:** `src/server/cloud_recovery.rs:214-271`, `prepare`, and `:350-384`, `restore_pinned`; `src/server/recovery_bundle.rs:229-248`, `import`.
- **Impact:** Ancestor symlinks/junctions can redirect writes into an aliased directory. An existing empty admin directory is checked before network work, then reused without preserving its identity or checking that it is still empty. Consequently the checked destination is not necessarily the directory eventually written. There is no comparison against a known live admin location.
- **Executed fixture evidence:** Two throwaway unit reproducers using the existing fake-store setup passed assertions demonstrating the undesirable behavior:
  1. Create a synthetic root with empty `admin`, make an NTFS ancestor junction to that root, request `<junction>\admin`, and restore. The command succeeds and creates `users.json` in the aliased root. No junction privilege elevation was needed.
  2. Create an empty admin directory, call `prepare`, write `unexpected-live-state` into it, then call `restore_with`. Restore succeeds and writes users/tenants beside the unexpected file.
- **Boundary:** Stable existing database files, including the source file, are refused. Stable nonempty admin directories are refused. These fixtures do not demonstrate overwriting a populated, unchanged live account store; they demonstrate the missing traversal and time-of-check boundary.
- **Fix:** Require an explicitly isolated private restore root, reject reparse/symlink traversal, resolve and compare identities against known live/source paths, and retain directory handles/ownership through publication. Do not trust an early pathname-only emptiness check. Recheck under the publication boundary or stage a new directory and use no-replace semantics.

#### CR-04 — Database resource consumption is not bounded or preflighted

- **Location / symbols:** `src/server/cloud_backup.rs:491-516`, `Manifest::check`, and `:1224-1265`, `Sets::fetch`; `src/server/cloud_backup/azure.rs:529-572`, `Container::download`; `src/server/cloud_recovery.rs:337-363`, `restore_pinned`; `src/maintenance.rs:633-709`, `drill` / `probe`.
- **Impact:** A huge published manifest can authorize arbitrarily large database download and repeated full replay. Disk exhaustion can affect other applications sharing the destination filesystem. A valid large database can exhaust RAM during verification/open/index preparation. The proposed <=1 GiB workload envelope is not enforced by this command.
- **Evidence:** Manifest/coordination reads are bounded to 1 MiB and the bundle to 8 MiB, but the database's declared `u64` length is its only download ceiling. There is no maximum database size, free-space preflight or restore disk quota. At least the downloaded copy and one drill/final copy coexist. Network transfer uses bounded 8 MiB ranges, but verification and drill call full-replay loaders, not a bounded-memory validation-only path.
- **Reproducer:** Static inspection; no disk-filling or OOM workload was executed on the shared machine. A fake published manifest with an enormous database entry is not rejected by `Manifest::check` for its size; fetch proceeds to object download rather than a capacity refusal.
- **Fix:** Enforce a supported size/resource envelope before download, use checked peak-space accounting for all copies and admin outputs, preflight available space on each relevant volume, and enforce a runtime staging quota. Qualify or bound replay/index memory separately; chunked transport alone does not establish bounded restore memory.

#### CR-05 — Invalid input values can be echoed into structured error output

- **Location / symbols:** `src/bin/vlite-server.rs:1035-1039`, `cloud_command`; `src/server/cloud_recovery.rs:131-146`, `read_target`.
- **Impact:** Accidental secret-bearing arguments or malformed target content can enter stderr/log collectors despite the stated no-input/secret-echo contract.
- **Executed reproducers against the unmodified binary:** `vlite-server cloud-sets sig=REDACTION_SENTINEL` exits 1 and includes the complete sentinel argument in the JSON error. A target containing `"auth":"REDACTION_SENTINEL"` exits 1 and includes that supplied value in the serde `unknown variant` diagnostic. Only synthetic strings were used.
- **Fix:** Use fixed unknown-argument diagnostics without argument values. Map target and downloaded-object parse errors to bounded, value-free diagnostics, retaining safe field/position information where possible. Add sentinel tests for unknown flags, unexpected positional values, enum values and unknown field names, not just valid key-file contents on connection failure.

#### CR-06 — Unpin failure returns successful command status

- **Location / symbols:** `src/server/cloud_recovery.rs:306-331`, `restore_with`; `src/bin/vlite-server.rs:998-1005`, `cloud`; `src/server/cloud_recovery.rs:751-767`, `an_unreleased_pin_is_reported_with_its_removal_route`.
- **Impact:** Automation sees exit 0 even though cleanup failed and an indefinitely retained pin remains. This violates the requested nonzero-on-every-failure contract and can cause unbounded retention.
- **Evidence:** The passing fake-store test explicitly injects record-write refusal after pin creation, then expects `Ok` with `pin_released:false`. Every `Ok` report maps to `ExitCode::SUCCESS`. On ordinary restore failure, release failure is included in the error; on otherwise successful restore it is only a warning.
- **Fix:** Return a distinct nonzero partial-success/cleanup-failed result that explicitly states outputs were created and identifies the pin-removal route. Do not delete valid output just because unpin failed. Add retry/reconciliation guidance for interrupted operations; a process crash also cannot execute the current post-call unpin.

## Confirmed-good behavior

- **Verify before final output:** `Sets::fetch` checks the manifest SHA-256 against the published record, manifest schema/profile/roles, both payload lengths and SHA-256, full DB verification/CRC/counts/structure/lineage, and bundle/capture agreement before returning (`src/server/cloud_backup.rs:1179-1292`). `restore_pinned` then drills the fetched database before creating the final admin directory or final database (`src/server/cloud_recovery.rs:341-363`). Verification writes only staging at this stage.
- **Publication and pin gate:** `restore_with` pins before fetch; pinning only accepts `Published`, using the record CAS shared with deletion. Fetch rereads the published record and requires the pin (`src/server/cloud_backup.rs:1116-1158,1179-1219`). Missing/orphan data without a coordination record, staging records, delete-pending and tombstoned records cannot enter normal restore. Pin release is attempted on both ordinary success and ordinary error; CR-06 and crashes are exceptions to a complete cleanup guarantee.
- **Set IDs:** The fixed ASCII timestamp/hex grammar excludes traversal, separators, uppercase suffixes and malformed lengths (`src/server/cloud_backup.rs:282-291`); local preparation rejects it before connecting (`src/server/cloud_recovery.rs:206-211`). This is syntax validation, not calendar validation.
- **Rekey and RB-05:** The CLI requires both fresh-admin arguments and always supplies `Some((&username, &password))` to import (`src/bin/vlite-server.rs:1070-1081`; `src/server/cloud_recovery.rs:273-278,378-382`). Import creates an enabled unscoped super admin, while imported accounts receive fresh IDs, unusable password hashes and disabled/must-change flags (`src/server/users.rs:1179-1267`). Username collision fails rather than silently omitting the fresh admin. Thus the CLI closes the known RB-05 omission on the normal successful import path; it does not change the underlying optional library API or `Accounts::seed`'s existing super-admin shortcut (`:705-718`). CR-01 limits the crash guarantee.
- **No credential restoration:** Import writes users/tenants only; credentials, sessions, tokens and webhook configuration are not installed (`src/server/recovery_bundle.rs:221-279`). V4/V5 restore draws a new lineage, including graph-enabled V5 (`src/maintenance.rs:411-448`). Legacy V1-V3 have no lineage and are byte-copied; do not describe them as acquiring a lineage.
- **Password source/checks:** The restore password is read only through the required `--admin-password-file`, not argv password values or bootstrap environment settings. The helper requires a regular-file target <=4 KiB, bounded UTF-8 read, strips one line ending and applies password policy without echoing the password (`src/server/users.rs:1135-1175`). It follows symlinks and does not check owner/mode; restrictive password-file custody remains unqualified.
- **Atomicity at the individual-file level:** `maintenance::publish_held` stages on the destination volume, validates, syncs and persists with no-clobber semantics while holding a file lock where supported (`src/maintenance.rs:733-784`). It never intentionally replaces an existing DB. Account/tenant files also use synced no-clobber temporary-file publication. These are not a multi-file restore transaction.
- **CLI contract, except findings:** Strict per-command flag allowlists, duplicate refusal and `OsString` path handling are present. Text values reject invalid Unicode instead of panicking. Executed an unpaired UTF-16 surrogate for `--mode` on Windows: valid JSON error and exit 1. Also directly confirmed duplicate target refusal. `seed` is explicitly refused before target access, not silently mapped to rekey (`src/server/cloud_recovery.rs:199-205`). Usage documents the reserved `cloud-sets`/`cloud-restore` database basenames and prefix escape (`src/bin/vlite-server.rs:966-986`).

## Unverified items and recommendations

- No real Azure identity/account/credentials were used, and no Azure operations were attempted. Remote RBAC, actual service behavior, retention-policy qualification and credential-denial canaries are **not verified** here.
- Linux runtime permissions, rename/no-clobber behavior, directory-sync failures, real process/power-loss durability and multi-user access were not executed. The staging permission finding is static, supported by the locked dependency implementation. Windows junction behavior was executed; Windows restrictive ACLs and host crash durability remain unqualified.
- No disk-filling, OOM, <=1 GiB performance/index-readiness qualification, or actual interrupted pin reconciliation was run. Existing passing suites do not satisfy these acceptance obligations.
- Prefer one newly published private recovery root over two independent output paths: it simplifies cross-platform atomicity and secret custody. If compatibility requires arbitrary database/admin destinations, retain that interface only with a real recoverable transaction and explicit partial/indeterminate statuses.
- Keep HA, fencing and seed deferred. Do not use this review or the passing unit/CLI suites as evidence that EPIC-005's full acceptance criteria, deployment readiness or HA safety passed.
