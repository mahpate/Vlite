## Verified closed

These are bounded conclusions, not a blanket approval of M5 or M4.

### VC-M5-01 - Admission precedes remote work

**Severity:** informational/closed. **Symbols:** `Runtime::cycle`, `Runtime::update`, `Runtime::publish`. **Evidence:** `src\server\backup_policy.rs:684-697,887-923,1005-1021`.

The job and attempt timestamp are encoded into the same policy/status document and saved before entering `run_job`, including before connecting or settling a pending publication. A pre- or post-rename admission error returns without calling `run_job`. The busy guard then releases admission. This ordering is correct by inspection; dedicated failure-injection results are recorded below.

**Recommendation:** retain this ordering. Distinguish an uncertain post-rename admission from a definitely absent job: after a post-rename error, memory clears the job but the durable file can still contain it. A later startup can therefore count an interruption even though no cloud request occurred. That is conservative attempted-job accounting, not proof that a remote request was made.

### VC-M5-02 - Ordinary panic and sequential startup accounting

**Severity:** informational/closed for ordinary successful state writes and one runtime owner. **Symbols:** `interrupt`, `Unwinding::drop`, `Runtime::open_with`, `Runtime::run_job`. **Evidence:** `src\server\backup_policy.rs:176-192,232-249,584-597,970-981,1758-1800,1803-1879`.

The normal connector-panic case clears the job, records one interruption/failure and releases `busy`. Startup consumes a saved job and atomically persists the increment and cleared job before returning. A second sequential startup does not increment it again. Publication counters and `phase = after_publish` are changed in one status update, so a later drill/collection panic should not also count a publication failure. The original startup and panic tests pass. Their limitations, including mutation survivors, are below.

**Recommendation:** preserve the ID-conditional consume operation and atomic update; extend coverage to post-publication panic and lifecycle ownership failures.

### VC-M3-01 - Versioned atomic document compatibility is preserved

**Severity:** informational/closed within the tested filesystem semantics. **Symbols:** `Status`, `Document`, `encode`, `read_document`, `write_atomic`. **Evidence:** `src\server\backup_policy.rs:31-32,129-157,195-202,393-417,434-449,1706-1747,1924-1977`; `src\server\admin.rs:1322-1329`.

`FORMAT` stays 1; `Status` has struct-level serde defaults, making old format-1 files without `job`, `interrupted` or `clock_reset_unix_ms` readable. Future format numbers are refused. Policy and the entire status, including `job`, are serialized under one state mutex and replaced together, not through separate document renames. The old-format/future-format and M3 atomic-document tests pass.

**Uncertainty/trade-off:** file sync and atomic replacement were exercised on Windows, where `sync_directory` is explicitly a no-op. No Windows power-loss durability claim or Unix directory-fsync qualification follows from these tests. A post-rename error remains an uncertain outcome. Existing size-limit rollback also means a status update need not become durable; `note` logs a failed write rather than making it transactional with remote publication.

### VC-M4-01 - A single corrected clock no longer defers work by the original error

**Severity:** informational/closed for a clock that stabilizes after correction. **Symbols:** `reconcile_clock`, `next_run`, `Runtime::open_with`, `Runtime::claim_due_at`. **Evidence:** `src\server\backup_policy.rs:524-560,610-621,794-815,1883-1920`.

Future `last_attempt_unix_ms` and `policy_updated_unix_ms` are pulled back to the sampled wall clock, and an excessively future busy retry is capped at `now.saturating_add(30_000)`. Reconciliation runs on startup and before scheduling decisions. A normal due time uses the later of the two stamps plus the policy interval. The named M4 test passes.

`clock_reset_unix_ms` means the wall-clock sample of the most recent reconciliation that changed a stamp or retry. It is not a monotonic timestamp, failure counter, cancellation marker or guarantee of immediate disk persistence. Startup saves it immediately; the schedule-check path only saves it with a later status write. A subsequent correction can move its value backward, and normal successful checks do not clear it.

Intervals are validated at 300-604800 seconds on both configuration and file load; zero and huge policy intervals cannot enter through those supported paths. Normal next-run multiplication/addition and the reconciliation retry cap saturate. Remaining unchecked additions and elapsed-time limitations are covered under Still open.

### VC-AUDIT-01 - New M5 audit fields do not contain credential values

**Severity:** informational/static inspection only. **Symbols:** `Unwinding::drop`, `Handle::audit`, `Runtime::open_with`. **Evidence:** `src\server\backup_policy.rs:239-248,317-327,584-596,887-899`; `src\server\cloud_backup\azure.rs:335-380`.

The new unwind audit event contains a generated random hexadecimal job ID and an internally assigned phase, not the panic payload, target credentials, tokens or response bodies. Startup emits the corresponding event to stderr/structured logs, not to the durable audit log. Azure's production transport diagnostics avoid request URLs/body values and sanitize the response error-code header. This is a static trace of the changed audit paths, not a comprehensive secret-exfiltration test or assurance about manually corrupted local state.

**Recommendation:** retain structured IDs/codes and do not add panic payloads or raw transport errors to the audit event. If durable audit coverage of restart-detected interruption is required, append it after the audit log becomes available; currently only status and ordinary logging record that detection.

## Still open

### SO-M4-01 - An interval is still a wall-clock, not elapsed-time, bound

**Severity:** low/design limitation. **Symbols:** `Runtime::claim_due_at`, `reconcile_clock`, `next_run`. **Location:** `src\server\backup_policy.rs:524-560,794-815`; `docs\DOCKER-OPERATIONS.md:408-411`.

There is no monotonic scheduling deadline or elapsed-time minimum between claims. A forward jump of one policy interval can immediately make another backup due, even with almost no real time between runs. Repeated forward jumps can produce repeated extra runs. Conversely, repeated corrections below the last reconciled attempt keep rebasing the next deadline, potentially preventing a run indefinitely while that behavior continues. Once the clock stabilizes, the single-correction fix does bound the remaining wall-clock delay.

**Evidence:** static arithmetic; the dedicated synthetic-clock fixture exercises back-to-back due claims and repeated backward rebasing without real-time sleeps. These are scheduling-only calls, not actual remote backups or changes to the host clock.

**Suggested fix/trade-off:** explicitly choose and document wall-clock/catch-up semantics, or use `Instant` for in-process interval/retry deadlines while using persisted wall-clock stamps only to initialize/reconcile them on startup. A restart cannot reconstruct elapsed time perfectly from wall-clock state alone. Qualify the documentation's "at most one interval" as applying after a correction that subsequently stabilizes, not as a universal elapsed-time guarantee.

### SO-M4-02 - Not all retry additions are overflow-safe

**Severity:** low/theoretical input boundary; predates M4. **Symbols:** `Runtime::claim_due_at`, `Runtime::run_job`. **Location:** `src\server\backup_policy.rs:806-809,942-946`.

The new reconciliation cap saturates, but busy paths still calculate `now + RETRY_MS` and `started + RETRY_MS` without checked/saturating arithmetic. A synthetic near-`u64::MAX` time panics in a debug build; a release build can wrap the retry deadline. Valid policy interval bounds do not protect this addition.

**Suggested fix:** use `saturating_add(RETRY_MS)` in both paths and add a focused boundary assertion. This is not a plausible present-day Unix timestamp failure and is not evidence that an ordinary forward clock step overflows.

## New

### NEW-M5-01 - Timed-out work retains write authority after close and can erase recovery accounting

**Severity:** medium. **Symbols:** `Runtime::wait_for_operation`, `Service::close`, `Runtime::open_with`, `Runtime::note`. **Location:** `src\server\backup_policy.rs:849-875,570-597,684-707`; `src\server.rs:710-739`; `docs\DOCKER-OPERATIONS.md:405-408`.

At the deadline, the join handle is put back and `false` is returned. `Service::close` ignores that result, closes the database and reports success. Nothing cancels the thread, revokes its state-file writes, or transfers exclusive ownership of the cloud runtime directory. A later runtime can load the same file, count the old job as interrupted and clear it; the old thread can then finish and overwrite that recovery state with its stale in-memory status.

**Evidence:** the original timeout test itself permits a timed-out run to finish normally with no extra interruption (`src\server\backup_policy.rs:1856-1878`). The added isolated reproduction uses a blocked connector, the actual ten-second `Service::close`, a new `Runtime::open_with` over the same directory, and then releases the old thread. Exact executed results are recorded below.

Manual `run_now` and `collect` use `busy` but do not have a thread registered in `operation`; drill/restore have neither that exclusive guard nor a scheduled join handle. Graceful HTTP draining normally protects completed requests, but the join helper is not a drain mechanism for detached/disconnected manual work. These paths can retain an old runtime too.

**Suggested fix:** establish explicit runtime shutdown/ownership state before draining operations, include all writing operations in ownership accounting, and prevent an older generation from persisting after ownership is handed over. A timeout may leave computation alive, but it must not permit two independent state-file writers. Options include retaining exclusive directory ownership until the last worker exits, or returning a close outcome that forbids reopening until drained. Cancellation must be cooperative; do not pretend Rust's join handle terminates a thread.

**Documentation correction:** the ten-second limit does not cut short a run or itself increment `interrupted`. It logs `cloud_backup_shutdown_timeout` and leaves work running. Interruption is recorded only if a later panic or startup actually consumes the job. The Docker text currently conflates these outcomes.

### NEW-M5-02 - Concurrent close callers can bypass the wait

**Severity:** medium. **Symbol:** `Runtime::wait_for_operation`. **Location:** `src\server\backup_policy.rs:850-860`; caller `src\server.rs:710-739`.

The first waiter takes the handle out of the mutex and releases the lock while polling. A second waiter sees `None` and returns `true` although the worker is still running. Concurrent calls through cloned `Service` values therefore do not share a shutdown barrier; the second close can proceed to close the database before the first wait finishes.

**Evidence:** a gated-worker fixture starts one waiter, observes the now-empty handle slot, then calls the helper again with a zero duration. The second call reports completion while `busy` remains true and the first worker remains gated.

**Suggested fix:** represent running/joining/joined state explicitly and let all waiters observe the same completion condition, or serialize the complete `Service::close` lifecycle. Sequential repeated close after a completed join is harmless; it is the concurrent in-flight case that is not represented.

**Self-call analysis:** a worker waiting on its own registered handle cannot become finished while executing the wait; it times out rather than self-joining. The monotonic deadline prevents an infinite loop in that helper, but consumes the entire timeout unnecessarily. No normal production path from the scheduling loop or cloud callback to `Service::close` was found. Do not infer general reentrant-close safety: `Ops::shutdown` performs an ordinary scheduler join (`src\server\ops.rs:285-297`).

### NEW-M5-03 - The unwind destructor is not guaranteed non-panicking

**Severity:** medium/defensive reliability; boundary-dependent reproduction. **Symbols:** `Unwinding::drop`, `interrupt`, `Runtime::run_job`, `logs::stderr`. **Location:** `src\server\backup_policy.rs:176-186,232-249,684-707,951-967`; `src\server\logs.rs:117-128`.

The destructor calls ordinary fallible/error-reporting machinery during an existing panic. `interrupt` uses unchecked counter increments. The final logging path calls `eprintln!`, which can panic on stderr write failure; even `internal` used by `note` logs through the same path. There is no non-panicking boundary around this cleanup. A second panic during unwinding aborts the process instead of safely recording the interrupted job.

There is also a static double-count window on the ordinary publication-error branch: `run_job` increments `runs` and `failures` while the job remains in `publish`, then audits/logs before returning to `cycle` to clear it. A panic in that audit/log interval makes `interrupt` increment the same run/failure counters again. The job-ID check prevents consuming the same job twice; it does not prevent counting an already recorded outcome twice.

**Evidence:** the isolated subprocess fixture persists an accepted `runs = u64::MAX` status, then injects a connector panic. In a debug build the new increment in `interrupt` overflows inside `Drop`, exercising the double-panic path. This depends on boundary/corrupt counter state, not naturally reaching that count. In an unchecked release build that particular counter path wraps instead; the stderr failure path is independently present in production code.

**Suggested fix:** use saturating counters and a cleanup-specific fallible logger that ignores/report-counts I/O errors without panicking. Do not call generic helpers that themselves log by panicking-capable macros from `Drop`. Atomically mark a publication outcome as counted before executing subsequent audit/log calls, so panic cleanup cannot count it again. Keep interruption mutation idempotent and preserve the durable startup fallback if cleanup cannot finish.

### NEW-TEST-01 - The named tests do not establish several central claims

**Severity:** medium/test adequacy. **Symbols:** the three named regression tests. **Location:** `src\server\backup_policy.rs:1758-1920`.

The startup test writes a job into JSON by hand. The combined panic/join test does additionally observe a real admitted job on disk while remote work is gated: removing durable admission is killed by that assertion. However, its panic injection occurs before publication and it calls `wait_for_operation` directly; it does not exercise post-publication panic or `Service::close`. The M4 test exercises future policy-update and retry values but does not create a future last-attempt timestamp.

Retain the existing disk-job/gate assertion; add pre/post-rename admission failures, a panic in the collection/drill phase, actual service close, and a separate future-last-attempt case.

## Lock-order review and limits

Static inspection of `src\server\ops.rs:285-350`, `src\server\backup_policy.rs:684-697,794-835,1005-1044`, and `src\server.rs:710-739` found no normal-path lock-order cycle introduced by M5: the scheduler checks cloud state under its own mutex, drops that mutex before launching work, and shutdown drops it before joining. Cloud publication releases its state lock before acquiring the database write lock; close joins/waits before acquiring that database lock. Restores/drills serialize short status writes through the same state mutex and use remote pins rather than monopolizing the cycle's `busy` flag. These observations do not fix the multiple-owner/close races above.

The ten-second value bounds only polling of the scheduled cloud thread, using `Instant`; it is not a total `Service::close` deadline. Earlier webhook/scheduler shutdown, filesystem operations, later database-lock acquisition and `Database::close` can take longer. The polling interval can also overshoot the nominal deadline by scheduling latency.

`docs\API.md:780-815` correctly exposes the new fields, keeps manual runs available when the policy is disabled, and states versioned atomic policy/status persistence. `docs\DOCKER-OPERATIONS.md:405-411` needs the timeout and stable-clock qualifications described above. Neither document should be read as a cross-generation ownership guarantee.

No real Azure, Azurite, full suite, deployment, abrupt process/power-loss test, Linux/macOS directory-sync test, stderr-failure injection or host-clock modification was run. Those were not substituted by the in-memory-store, injected-panic and synthetic-clock fixtures. Release-mode counter overflow behavior is inferred from Rust's unchecked release arithmetic; the subprocess experiment uses the debug test profile.
