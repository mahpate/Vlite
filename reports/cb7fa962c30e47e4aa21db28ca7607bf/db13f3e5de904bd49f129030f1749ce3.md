# EPIC-002 prerequisite inventory: backend serving modes

## Result and scope

**Analyzed commit:** `b23c57fb5da181b804504fca3def3e5e675c9947` (the pinned checkout).

**Inventory complete; reader-mode behavioral validation INCOMPLETE.** This is a bounded static implementation-readiness report, not a claim that reader mode exists, that HA works, or that any deployment gate passed. The two executed checks below validate existing static route inventories only. No mode implementation or runtime HA validation was requested or performed.

The existing read-only engine opener is a useful storage boundary, but changing the binary to call it is insufficient. Startup currently initializes writable control-plane runtimes; queries and refusals can append persistent audit; a webhook worker can write a cursor even with no subscriptions; index maintenance can mutate a read-only handle's derived in-memory index; shutdown can write an ANN sidecar. These paths need explicit mode boundaries, not a read-only bearer token or an HTTP-method filter.

The approved future context is an opt-in ACA topology with a stateless authenticated routing gateway and private writer/reader apps per tenant, using the same engine. Standalone remains default. Private network placement is not authentication. This report does not implement that topology, investigate the separately assigned reader-apply harness, optimize `ReplicaFollower`, or infer anything about unpublished Blob log archive/PITR code. It does not clear GATE-001 or authorize reader fleet deployment or promotion.

All file/line citations refer to the analyzed SHA. "Observed" below means observed in source, not experimentally demonstrated.

## 2. Minimal safe serving-mode boundaries

### Standalone

Keep the current default, CLI semantics, auth options, local control-plane stores, timers and shutdown behavior. New mode parsing should not silently alter durability, source selection, role permissions, memory reservation behavior or existing request error precedence. Standalone is not evidence of HA exclusivity.

### Writer

Treat writer as an explicit serving responsibility for the future opt-in topology: mutation/admin/history-producing paths belong here, subject to all existing tenant/memory/auth and durability checks. **A fresh standalone alias called `writer` would misleadingly imply fencing unless it explicitly states it provides none.** The current single-process/local OS locks and compaction owner lock do not establish tenant-wide distributed single-writer authority across independent replicas.

Do not add an unfenced promotion route, mode reload, environment hot-toggle or implicit promotion on reader restart/failure. If writer startup is exposed before lease/fencing ownership exists, it must be clearly non-HA/manual-only or refuse the HA configuration. The actual distributed fencing design is outside this inventory; writer naming must not be used to pass that unresolved prerequisite.

### Reader

1. Select an immutable mode at startup and validate the complete effective configuration (CLI, environment, copied/persisted policy and source type) before any writable preparation. Store mode in the shared service state used by REST and gRPC; do not infer it from caller role.
2. Open only an existing, validated local generation using `open_read_only` or `open_read_only_encrypted`. No create, repair, writable reopen or fallback to `Durability::None`. Core read-only open is a second defense, not the sole refusal policy.
3. Use a reader-specific initialization boundary: validate bindings/reservations and load approved immutable auth/tenant inputs, but do not invoke writable `Managed::prepare`, `load_control`, cloud runtime open, webhook configure, ops schedules, group commit, bootstrap account creation or ANN-save setup. Avoid abusing `admin_directory=None` if doing so drops required credentials, tenant suspension or reservations.
4. Apply an explicit semantic operation allowlist and uniform reader refusal to all authenticated callers, including admin/session/scoped identities. Preserve authentication, live authorization/tenant checks, reserved-as-missing behavior, memory exact scope checks, admission, request limits and content-safe telemetry. Unknown operations default to refusal; HEAD/method fallbacks must not bypass policy. Do not blanket-deny POST queries.
5. Allow no query-triggered lazy index build/publish, cleanup commit, import mutation, archive/history publication or writer-only admin change. Prefer ready/exact paths with existing documented errors or nonbuilding planner behavior. ANN loading can be a separately approved read-only initialization operation, but the current `--ann-snapshot` combines load with shutdown save and cannot be accepted unchanged.
6. Make `/ready` and authenticated status/capabilities report mode and local generation usability without consulting metrics. Current `/ready` probes `db.get(0)` (`src\server.rs:2304-2312`); it is not freshness, catch-up, lease or fencing evidence. Readiness should be false while starting/draining/unusable and must not claim replication freshness before a separate applied-generation contract exists. Existing `/health` is just constant liveness (`:884`).

## 3. Blockers to resolve before mode implementation

These are design/input prerequisites, not authorization to start implementation.

1. **Agree on the mode contract and refusal precedence.** Separate immutable serving mode, credential role, storage read-only, durability and HA authority. Specify a stable reader refusal status/code and when auth/tenant/reservation errors take precedence. Existing engine APIs sometimes validate malformed vectors/preconditions before reaching `ReadOnly` (`tests\server_record_expiry.rs:470-493,587-602,887`); a central mode refusal intentionally changes reader behavior, but standalone precedence must remain unchanged.
2. **Choose the reader auth/tenant control-state contract.** Existing read-only bearer role is not process mode, and `load_control` is writable. Decide how credential lineage, expiration/revocation, tenant suspension, memory grants/reservations and raw-access restrictions reach a reader without local administration. Gateway/backend authenticated identity and trust boundaries must be explicit; internal placement alone is not acceptable. Do not implement an "admin bearer only" shortcut that loses tenant isolation.
3. **Choose reader observability versus persistent audit behavior.** Existing memory success/refusal and scoped-denial paths persist audit. Decide an explicit nonpersistent/content-safe sink and report its capabilities honestly, rather than silently attempting forbidden writes or deleting existing authorization/audit semantics.
4. **Freeze initial operation/source/transport scope.** Resolve whether initial reader supports directory generations, read-only disk-ANN/ANN initialization, custom embeddings/reranking and gRPC. Each excluded combination must have a startup/request refusal and tests. The explicit route/RPC table must default closed and account for future registrations; a URL prefix or GET-only policy is inadequate.
5. **Define status and fixed-generation readiness.** Specify the usable-generation identity/status fields, drain behavior and authenticated status contract independent of metrics. Applied-generation freshness/lag is not supplied by the current binary; coordinate the contract with the separately owned work without investigating or implementing its harness here.
6. **Re-run this bounded inventory after archival delivery.** The analyzed SHA includes cloud backup/recovery policy, not the other session's unpublished Blob log archive/PITR work. Its startup hooks, timers, request paths, configuration and shutdown publication must be mode-gated too. No inference about its retention, history continuity, restore windows or PITR guarantees is justified from this base.

Distributed writer fencing/promotion remains unresolved external HA work, not something a `writer` alias or this report can clear. EPIC-002 should state this limitation plainly and not enable promotion.
