### 2. MEDIUM - Proposed fencing uses independent CAS objects without a shared serialization point

**Confidence: 9/10. Evidence:** changed `docs/projects/feature-aca-ha/feature-aca-ha.prd.md:251,256`.

F1 specifies a per-tenant authority object and a separate per-epoch head, then claims a former owner's head CAS fails once the authority epoch moves. Updating the authority object's ETag does not invalidate the old head object's ETag. A paused publisher can resume with its still-valid old-head condition; `If-None-Match:*` on a fresh segment name does not fence its upload either. Epoch checks before an operation do not atomically bind that later operation to authority.

**Impact:** the proposed protocol has not established its stated stale-publication proof obligation. This is a design gap, not an implemented-runtime regression; infrastructure fencing and the existing deployment gates must remain mandatory. The older HA design explicitly uses the *same authority-record CAS serialization point* for appends and epoch closure (`docs/projects/feature-backup-ha/feature-backup-ha.prd.md:187-188` at the pinned base). The reusable object-store API conditions each individual named object (`src/server/cloud_backup.rs:162-168`), not multiple objects transactionally.

**Remediation:** put epoch and authoritative head advancement behind one CAS serialization point, or specify an equivalent atomic fencing protocol. Add a paused-old-publisher test: bump authority, resume its old conditional publication, and prove no authoritative history advances. If old immutable uploads are intentionally allowed but unreachable, distinguish that from preventing authoritative publication. Keep GATE-004/005 open.

### 3. LOW - Foreign-lineage smoke rejection is masked by duplicate position

**Confidence: 10/10. Evidence:** changed `benchmarks/ha_reader_apply.rs:76-88`; associated assertion in `benchmarks/ha_reader_apply_tests.rs:23-32`.

`check_rejections` runs after applying `segment`, but constructs `foreign` by changing only that already-applied segment's lineage. Its base sequence is therefore also stale. Even if the lineage guard were missing, the continuity guard would reject it and the smoke would still report `"foreign_lineage"` as verified. This is visible from `ReplicaFollower::apply`'s successive lineage/base checks (`src/replica.rs:144-156` at the pinned base).

**Impact:** this harness's reported foreign-lineage coverage is weaker than it appears. Existing `tests/replica.rs::followers_refuse_writes_and_bad_segments_leave_state_unchanged` independently tests a foreign lineage at a valid next position, so this is not evidence that the engine currently accepts it.

**Remediation:** derive the foreign case from an otherwise admissible segment at the current applied position, then alter only lineage; retain the unchanged-position/file assertions. Keep duplicate testing separate.
