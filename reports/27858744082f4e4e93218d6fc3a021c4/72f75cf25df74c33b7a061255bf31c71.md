# Attribution of the selection-effect compaction flake

## Result

**Pre-existing, not introduced by the backup work.** The unchanged test failed naturally at **c61aae91**, before backup, and at **987ffaf9**, the pinned backup base. Both failures were the same assertion at `tests\server_compaction.rs:651:5`: expected `"outcome_unknown"`, observed `"not_published"` in a response already reporting `"fence":"recovery"`.

The cause is a **mixed-time status response**, not a failed recovery transition: `status()` copies the job journal before filesystem work, but reads the fence and recovery code later. Selection can advance between those reads. An isolated timing experiment on the pre-backup commit increased this exact failure to **3/3**; capturing the journal, fence, and recovery code together reduced it to **0/40 with the same timing perturbation**, without changing the test or any assertion.

All requested builds, 160 filtered repetitions, and 20 whole-binary repetitions were executed. This is **not an all-green suite result**: there were two target-test failures and one separate scheduling-test failure. Host exclusivity was not established: “idle” below means no deliberately injected CPU load, not a reserved machine with every background service stopped.

## Root cause and attribution: static inspection

All line references in this section are to the unmodified A/B files; relevant lines have the same numbering in both revisions.

1. **The test trusts one status response.** `wait_fence()` returns the first response whose `fence` field equals `"recovery"` (`tests\server_compaction.rs:219-229`). The test then asserts that response's recovery code and `job.selection` (`:646-651`). It does not independently reload the job after establishing the fence. [E1]
2. **The writer orders the transition correctly.** The injected selection-effect error occurs *after* successfully writing `selection.json` (`src\server\compaction.rs:782-787`). The error branch updates the job to `selection="outcome_unknown"`, `phase="selection_outcome_unknown"`, then subsequently publishes the recovery fence (`:1780-1813`). `Coordinator::update()` holds the state mutex through its update and durable-store attempt (`:466-486`); `fence_recovery()` stores the code, then performs a sequentially consistent fence store (`:550-555`). [E3, E4]
3. **The reader does not take one corresponding snapshot.** `status()` calls `c.snapshot()` at `src\server\compaction.rs:1980`, releasing the journal mutex when the clone is made. It then does reasons/metadata/retained-file/selection-file work (`:1982-1995`). Only while forming JSON does it load the live fence (`:2025`) and call `c.recovery()` twice (`:2026`). Sequential consistency of one atomic does not refresh an already copied `Persisted`. [E2, E4]
4. **Failing interleaving:** status copies a `selecting/not_published` job; the compaction worker records `outcome_unknown` and publishes `RECOVERY`; status serializes the old job together with the new fence/code. `wait_fence()` accepts this torn observation, and line 651 fails. Both natural failure payloads show exactly this combination. The first natural failure even says `"available":true` with a recovery fence, another consequence of sampling different fields at different times.
5. **Restart explains the intended recovery semantics.** Startup sees durable selection authority matching the interrupted job, repairs it to committed/reopening (`src\server\compaction.rs:836-878`), and successful serving completes the job (`:958-975`). The original test checks the reopened fence, succeeded job, selected filename, and churned data (`tests\server_compaction.rs:680-685`). Successful original and experimental-fix runs exercised those assertions; no assertion was removed or relaxed. [E1, E4]

**Historical attribution:** `git blame` attributes the relevant status snapshot/fence reads and the target assertion to **`99872782f1c97dd34e9eaa0e24c7668472c87857`**, “EPIC-002..005: managed compaction runtime, journal/recovery and admin API”, before A. `git diff c61aae91 987ffaf9 -- tests/server_compaction.rs` was empty. The entire compaction-module diff between A and B only makes `free_bytes` (both platform variants) and `civil` `pub(super)`; it does not change this status/error/restart path. [E6]

This is best classified as a **pre-existing observable status-consistency race exposed by a timing-sensitive test**, not evidence that selection recovery itself lost state. It is not a shared-static fault-hook race: the hook reads a child-process environment variable, and each server receives its own value. The state mutex and selection mutex serialize individual operations, not the separate reads used to assemble status. [E3, E5]

## Causal experiment actually executed

The experimental clone was based on A. The **test file and its assertions remained byte-identical**.

### Experiment 1: widen the suspected interleaving

Added only these two fault-specific delays to production code in the temporary clone:

```rust
// In write_selection(), after selection.json is written, inside the existing fault branch:
std::thread::sleep(Duration::from_millis(150));

// In status(), immediately after copying state, outside its state lock:
if fault("selection_effect_error")
    && state.job.as_ref().is_some_and(|job| job.phase == "selecting")
{
    std::thread::sleep(Duration::from_millis(300));
}
```

The first delay gives status a chance to copy `selecting`; the longer second delay allows the writer to publish recovery before that response reads the live fence. These sleeps deliberately perturb server worker timing and are **diagnostic instrumentation, not a recommended fix or a fixture-only substitute for running the server**.

Rebuilt with the same Cargo command and ran the real filtered test sequentially three times: **0 passed, 3 failed (100%)**, all at the original line 651 with the same stale-selection/new-fence contradiction.

### Experiment 2: preserve instrumentation, capture related fields together

Kept both delays and changed only status sampling/serialization in the experimental clone:

```rust
let (state, fence, recovery) = {
    let state = c
        .state
        .lock()
        .unwrap_or_else(std::sync::PoisonError::into_inner);
    let fence = c.fence.load(Ordering::SeqCst);
    let recovery = if fence == RECOVERY { c.recovery() } else { None };
    (state.clone(), fence, recovery)
};
```

JSON used this captured `fence` and `recovery`, rather than loading them later. The state guard was released **before** the existing injected 300 ms delay and filesystem work. For the selection-error transition, the writer cannot update the journal and publish recovery behind an old journal copy while these related fields are being captured.

Rebuilt again using the same Cargo command and ran the unchanged real test sequentially 40 times with no injected CPU load: **40 passed, 0 failed (0%)**. Every passing invocation continued through authentication/control-plane fencing assertions, restart, successful recovery, and data verification.

| Pre-backup configuration | Pass | Fail | Failure rate |
|---|---:|---:|---:|
| Original A, filtered, both load conditions combined | 79 | 1 | 1.25% |
| A + fault-specific timing delays | 0 | 3 | 100% |
| A + identical delays + captured status tuple | 40 | 0 | 0% |

The controlled comparison is **3/3 versus 0/40 under the same delay scheme**. It is strong evidence for the proposed interleaving, not a statistical guarantee that every status field or every coordinator transition is now coherent.

## Recommendations and trade-offs

**Preferred code-side fix:** give status a coherent in-memory snapshot of journal, fence, and recovery code, then serialize those captured values. The tuple experiment demonstrates a narrowly scoped implementation for this transition. Capture once, release locks before filesystem access, and review lock ordering and *all* fence-changing transitions before adopting it. A more comprehensive snapshot/version protocol may be preferable if the API promises consistency across generation, filesystem-derived fields, and all fence transitions. The experiment intentionally does not claim that broader guarantee: `reasons()`, current generation, retained files, and selection metadata still have independently timed reads.

Add a deterministic regression test that pauses after the journal snapshot and releases the selection-error transition before response serialization. Keep the existing `"outcome_unknown"` assertion. A test-only barrier is preferable to committing sleeps, because sleeps are scheduler-dependent and slow down the suite.

**Test-side alternative if status is explicitly eventually consistent:** first establish the terminal recovery fence, then issue a fresh status request and run the unchanged assertions against that request:

```rust
server.wait_fence("recovery");
let status = server.status();
// Keep all existing equality assertions and restart/data checks.
```

For this specific fault, the job update precedes recovery publication and no further transition occurs until restart, so a request initiated after observing recovery avoids the old snapshot. This alternative was **not run**; it is a proposed workaround, not a fix for externally inconsistent API responses. Do not remove the assertion, accept `"not_published"`, or add an arbitrary test sleep.

**Separate scheduling flake:** A whole-binary run 8 failed in `churn()` at `tests\server_compaction.rs:280:13`, with a write receiving maintenance 503 instead of 204. Static inspection shows the schedule test enables compaction before generating growth (`:980-1017`), so the scheduler can start maintenance during the write loop that crosses its trigger threshold. This is a separate timing hypothesis, not a proven neighbouring-test collision or backup regression; no causal experiment was performed for it.
