Architecture

How VLite works

VLite is an embedded Rust storage engine. One process owns one database file, every write is an append-only, checksummed frame that is fsynced before it is acknowledged, and every index is derived state that can be rebuilt from that file. REST, gRPC and the language bindings are thin adapters over the same Database core.

Storage

Append-only log

32-byte header, then CRC32-framed records. No pages and no WAL sidecar.

Durability

fsync per commit

Append, sync_all, then publish. Torn tails are reported, never silently dropped.

Indexes

Derived & rebuildable

HNSW, ScalarU8, metadata, BM25 and ANN snapshots are caches over the log.

Layered architecture

The core is a library (src/lib.rs). Transports and bindings sit on top, and they all call the same Database API. Storage and format code sit underneath, and derived indexes are maintained after each successful commit.

The single-file contract

The primary file, for example data.vlite, is the only source of committed records. It is an append-only sequence of variable-length frames after a fixed header. There is no page allocator, no superblock and no separate WAL or journal: the file itself is the log.

File header

The file starts with a fixed 32-byte little-endian header. Its CRC32 covers bytes 0–27 and is checked on every open.

Unknown flag bits are rejected rather than ignored, so an older binary never misreads a newer file.

Frames

Every mutation is written as one frame: a 36-byte prefix, a body, optional AEAD overhead and a 16-byte footer. The footer is the commit marker. A frame without a valid footer is never treated as committed.

Prefix detail (36 bytes):

There are three independent CRC32 checks: header, frame prefix (bytes 0–31) and footer (all preceding frame bytes). The footer also repeats the frame sequence, so a frame spliced from elsewhere fails validation.

Record encoding

Vectors are stored as little-endian f32, always at full precision, even when an index uses ScalarU8. A record body is laid out as:

dims × 4 Bvectorf32 LE 4 Bpayload len ≤ 1 MiBpayload variablemetadatatyped

Metadata-only updates write a frame with just the new metadata, so the vector is not rewritten.

Format versions

Features that need new on-disk structures bump the format version. Older files are never silently re-encoded; using such a feature on an old file returns BatchRequiresUpgrade, MetadataRequiresUpgrade or ExpiryRequiresUpgrade, and the caller upgrades explicitly through compaction.

Write path

Commits are synchronous: a call returns only after the frame is on stable storage. In-memory state and indexes change only after the fsync succeeds, so readers never observe uncommitted data.

Open & recovery

Opening a file replays the log. VLite separates two cases that many engines merge: a corrupt file, and an incomplete tail from a crash during an append. Neither is repaired silently. repair is an explicit operation that may discard only the unacknowledged trailing frame.

Locking & concurrency

A file permits either one exclusive writer (Database::open) or multiple shared-lock readers (open_read_only / open_read_only_encrypted), across threads and processes. Conflicting opens fail immediately with Error::Locked; readers do not coexist with a writer. Each reader sees the committed state at open time; close and reopen to observe later commits. Mutations return Error::ReadOnly without poisoning the handle; in-memory ANN builds remain allowed and never write the datafile.

The server retains the exclusive file lock, but its Arc<RwLock<Option<Database>>> lets read routes execute concurrently on bounded blocking workers. Writes take the exclusive guard. An approximate search that needs a rebuild retries under a write guard, so that rebuild can block readers. Explicit background HNSW rebuilds construct from a snapshot, then catch up and publish under exclusive access.

Native exact scans use Rayon when there are at least 4,096 candidate rows and rows × dimensions ≥ 524,288, with more than one Rayon worker. Chunk-local bounded top-k results merge deterministically by distance then ID; wasm32 retains serial scans. Python calls within one process are serialized by the C ABI: use separate processes with read-only handles for parallel embedded requests.

In-memory model

On open, the replayed log becomes an ordered map from u64 IDs to records, per collection. Indexes are built from those maps.

Query planner

Each search is planned. The planner uses an ANN index only if one is ready and its configuration, metric and quantization match the query; otherwise it falls back to an exact scan. Exact distances accumulate in f64, and lower is always nearer.

HNSW & quantization

The HNSW index uses a seeded, deterministic level assignment. Changing m, ef_construction or the seed requires a rebuild. With ScalarU8, each dimension is trained into a codebook, traversal uses asymmetric u8 distances, and the candidate set is reranked against the original f32 vectors.

Unreleased source uses a traversal-local visited bitmap during construction and search for graphs up to 8,388,608 nodes: one bit per graph node, rounded up to 64-bit words, at most 1 MiB per traversal. Larger graphs use a sparse hash set. Concurrent traversals do not share mutable visited state; the bitmap cap is not a total search-memory bound. This changes membership bookkeeping, not distance precision, graph-selection rules, filtering or durability. See the small Windows before/after experiment and its limitations.

Text & hybrid search

Text fields are tokenized into BM25 postings (k1 = 1.2, b = 0.75). Hybrid search runs the dense and text legs independently and fuses ranks with weighted reciprocal-rank fusion.

Advanced retrieval

  • Grouped search groups hits by a metadata field with per-group limits.
  • Geo search filters by spherical radius in meters over a geo field (format 5).
  • Recommend builds a query from positive and negative examples (at least one positive).
  • Rerank / MMR reorders candidates for relevance and diversity.
  • Query language supports predicates, IN (≤ 64 values), geo radius and grouping, with at most 64 predicates.
  • GPU exact search (feature gpu) runs WGSL compute in 16M-float chunks and falls back to the CPU.

Encryption & tenancy

With encryption on, each frame body is sealed with ChaCha20-Poly1305 (12-byte nonce + 16-byte tag). The key is derived from a passphrase with Argon2id (19,456 KiB, 2 iterations, parallelism 1), with parameters stored in a 64-byte descriptor after the header. Frame prefixes stay plaintext so recovery can walk the log, which means operation types, IDs, sizes and sequence numbers are visible. ANN snapshots and Disk ANN would hold plaintext vectors, so both sidecars are refused for encrypted databases.

Tenants are policy namespaces in the same file, not separate files or cryptographic domains. Physical collection names are t<32-hex-id>__<name>, with up to 1,024 lifetime tenant IDs.

CDC, point-in-time restore & replicas

Because the file is a sequenced log, change data capture, restore and replication all read the same frames.

A restore is selected through the admin API and applied on restart; it never swaps the live owner in place.

Server

vlite-server wraps one owned database. REST (Axum) and gRPC (tonic, vlite.v1.VLite, opt-in with --grpc-bind) share authentication, authorization, metrics and the core adapters.

  • Remote listeners require --allow-remote plus bearer auth. TLS does not replace auth.
  • Credentials are admin, read-only or scoped (read, search, write, import, index, collections, diagnostics, backup, …).
  • gRPC ExportVectors streams to the client and StreamImport streams from it; each import chunk commits independently.
  • A disconnect after a write is commit-indeterminate: check before retrying.

MCP and agent skills

vlite-mcp (Cargo feature mcp) is a stdio JSON-RPC client of the embedded engine, not a REST proxy. It opens a shared-lock read-only handle by default; --writable opts into exclusive ownership and upsert/delete tools. Encryption key-file and environment options are supported. See installation, tools and host configuration and RAG, MCP, operations and index-tuning skills.

Bindings

All embedded bindings drive the same engine through a handle-based C ABI: char *vlite_execute(uint64_t handle, const uint8_t *input, size_t length) takes a request envelope and returns a response string. Python (vlite_embedded) and Node.js (@vlite/embedded) wrap it; WASM builds the core separately with an injected clock (set_wasm_clock_ms).

Honest limitations

  • Single writer. One process owns a file; it is not a multi-writer or multi-process database.
  • Per-operation fsync. No group commit or async durability mode, so small-write throughput is bounded by the device's fsync latency. Batch writes to amortize it.
  • Startup replays the log. Open time and memory grow with data size; compaction reclaims deleted and overwritten bytes.
  • No automatic tail repair. A crash mid-append surfaces as IncompleteTail until you call repair.
  • ANN is approximate. HNSW and ScalarU8 trade recall for speed; inner product always uses exact search.
  • Exact search is scalar CPU code unless the optional GPU path is enabled.
  • Logical tenancy only; streaming exports are not point-in-time snapshots; webhooks are at-least-once.
