VLite benchmarks

Reproducible performance numbers for VLite's embedded engine, measured in-process against zvec, Chroma, LanceDB and FAISS, plus a separate server tier with Qdrant and pgvector.

Results Reproduce VLite features
Summary

What the measurements show

Where VLite leads

  • Smallest measured ANN database footprint in these runs, in one portable file.
  • Every ingest batch is a checksummed, fsync-before-ack atomic commit with fail-closed recovery.
  • Recall@10 is 1.0 at 20k × 128 and about 0.968 at 100k × 768; latency depends on dimensionality.

Where VLite is improving

  • HNSW build time: VLite builds single-threaded today.
  • Reopen with ANN: the HNSW index is rebuilt in memory unless an index snapshot is enabled.
  • Bulk ingest throughput and Python binding overhead (JSON over the C ABI).
Multi-engine benchmark

Embedded and server tiers, measured separately

WSL2, 16 vCPU Intel Xeon Platinum 8370C. Medians of 3 trials at 20k × 128 and 2 at 100k × 768. These are VLite 0.3.0 baseline runs, not measurements of the new concurrent-reader implementation.

Seeded float32 Gaussian clusters (64 clusters, σ = 0.35, seed 42), squared L2, 200 top-10 queries; recall against a tie-aware float64 oracle. HNSW M=16, ef_construction=100, ef_search=100 where exposed; 10 warmups, one sequential client, one query in flight. QPS is sequential queries/second, not maximum service throughput. Each engine/mode/trial uses a fresh process; server containers each have 4 CPUs and 4 GiB, with direct bridge-IP connections.

Latency depends on dimensions

At 128d, VLite embedded HNSW is close to zvec (0.454 vs 0.438 ms). At 768d, VLite is about 4× slower than zvec embedded and 2–2.5× slower than Qdrant over REST in the server tier. Recall is comparable, not identical; LanceDB's quantized configuration has lower recall.

Build and reopen remain the gap

At 100k × 768, VLite embedded builds in 524.57 s and reopens plus first query in 518.75 s without an ANN snapshot. These runs rebuild the graph; opt-in snapshots were not measured here. Chroma and FAISS include graph construction in ingest, so compare ingest + build.

Footprint with caveats

VLite has the smallest measured ANN database footprint: 10.2 MiB at 20k × 128 embedded and 295.3 MiB at 100k × 768. It is not smallest in every exact-mode row (LanceDB exact uses 9.8 MiB at 20k). FAISS is an in-memory index library, with no durability or persisted footprint here.

Defaults are not durability-equivalent: VLite fsyncs every acknowledged batch; pgvector uses synchronous WAL commits; zvec/LanceDB per-write fsync was not verified; Chroma/Qdrant persistence is asynchronous. Ingest is not a fair durability ranking. LanceDB uses one-partition IVF_HNSW_SQ, not plain HNSW; Chroma has no exact mode. Synthetic data, wrapper overhead, shared-host contention and just 2 large-data trials limit generalization. Embedded and server tiers must not be ranked together. Complete methodology, durability contracts, memory/tail-latency data and reproduction commands: benchmark README · harness.

HNSW traversal optimization (unreleased source)

A bounded visited-node bitmap replaces per-node hashing during graph construction and search on graphs up to 8,388,608 nodes. Each traversal owns one bit per node, rounded up to 64-bit words (at most 1 MiB); larger graphs retain a sparse hash set. This is not a bound on total traversal memory. On 5,000 synthetic 128-dimensional vectors, median rebuild time fell from 5.552 s to 5.080 s (8.5%), and the mean duration of two 100-query batches fell from 76.392 ms to 60.795 ms (20.4%).

Native Windows release build; squared L2, M=16, ef_construction=100, ef_search=100, k=10. One before/after campaign (three rebuilds and two query batches per version) on a shared host with warm caches, not per-query p50 or other latency percentiles, a universal gain or a new zvec comparison. No 100k × 768, other-OS or sparse-fallback measurements were collected. Existing cross-engine results above have not been revised. Distance precision, graph-selection rules, filtering and durability are unchanged. Methodology and reproduction · Raw timings and limitations.

Methodology

Reproduction and earlier zvec-only runs

Setup

  • One seeded dataset (64 Gaussian clusters, σ = 0.35), SHA-256 recorded in the results.
  • Same ingest batches for both engines; VLite commits each batch durably.
  • HNSW m = 16, ef_construction = 100, ef = 100 for both (zvec defaults overridden).
  • Every (trial, mode, engine) runs in a fresh process; engine order alternates by trial.
  • Recall is ID-based and tie-aware against a float64 brute-force oracle.

Caveats

  • Synthetic clustered data; real embeddings and larger collections can rank differently.
  • Shared WSL2 host; these baseline runs use a single sequential client, no concurrent load.
  • Python wrappers differ: VLite uses JSON over a C ABI, zvec uses native bindings.
  • Memory growth is resident memory after build minus before opening.
  • Durability contracts differ, so ingest times are not like-for-like.

Reproduce

# Linux x86_64, Python 3.11+
python -m venv .venv && . .venv/bin/activate
python -m pip install zvec numpy vlite-embedded==0.3.0
git clone https://github.com/mahpate/Vlite && cd Vlite
python benchmarks/compare_zvec.py --records 20000 --dimensions 128 --trials 3 --output zvec-20k.json
