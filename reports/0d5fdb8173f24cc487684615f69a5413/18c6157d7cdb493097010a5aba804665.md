### Why F-003 is more than a missed retry

The catalog is read with an ETag, but no lease or equivalent durable owner/fencing mechanism spans the destructive work. At `:1433-1445`, any collector observing an active decision can execute it and clear it. At `:1532-1545`, an original collector can still execute its local copy. Its next destructive operation has no dependency on the current catalog ETag or decision. `delete_reason` merely records the old decision's text. Detecting a conflicting catalog revision during final cleanup cannot undo deleted bytes.

The executed repro also exposes an independent stale-eligibility weakness: a completed drill changes the per-set ETag, so the first deletion CAS loses, but `update` retries against the new record and `delete_set` checks only `pins.is_empty()`. A newly verified candidate is still deleted using the old eligibility decision. Per-set CAS by itself therefore does not establish cross-set safety.

## Missing tests, unexecuted checks and uncertainties

**Not run / not permitted:** real Azure or managed-identity endpoints, an isolated Azure Blob drill, production RBAC deny tests, immutable-container/legal-hold tests, real proxy/private-endpoint behavior, and live log/audit inspection. Recommended qualification, after fixing the three reproduced defects:

1. Cover every crash/unknown-result point, including an applied create followed by unreadable reconciliation, pin CAS applied but unreadable, catalog intent/clear applied but unreadable, and final set CAS racing staging tombstoning. Assert exact identity and no duplicate logical job after process restart, not merely in-process retry.
2. Add genuine multi-janitor pause/resume tests spanning catalog handoff, changed verification status, changing policies, failed deletion, and survivor reservation release. Exercise partial survivor loss and all candidates losing CAS. Prove minimum **verified** count and last verified protection rather than merely counting newest published records.
3. Add HTTP-level large-object tests for 4 MiB, 4 MiB+1, 8 MiB boundaries, multiple block IDs, 201 without ETag for stage blocks, commit timeout, range truncation, changed ETag, bounded oversized/chunked responses, and source mutation. The existing fake store does not model Azure block response semantics.
4. Validate listing pagination end-to-end, numeric entities, malformed XML, CDATA/encoded-name cases appropriate to the API version, empty pages with continuation, and repeated markers. Prefer a bounded XML parser that rejects ambiguity; add a page/marker progress bound.
5. Test identity cache near the expiry margin, malformed expiry, refresh failure, missing platform variables, IMDS request shape using injection, 401 handling, redirects, configured proxies and secret-free error/Debug behavior. The current platform-cache fixture is useful but narrow.
6. Require least-privilege deployment evidence: upload principal cannot delete; read principal cannot mutate coordination except authorized pins; janitor cannot bypass survivor decisions; no access outside the chosen prefixes; no unrelated secret/VM permissions. Different containers facilitate permission separation but are optional and share one process credential in `connect_with`; separate identities/RBAC are an operational prerequisite, not proven enforcement.

**Questions, not additional confirmed exploit claims:**

- Where will three-set/30-day defaults and a nonzero last-survivor floor be enforced? `Retention` accepts arbitrary values and the runtime caller is deferred. Do not expose unchecked `keep_sets = 0` as an approved retention policy.
- How are service-enforced legal holds/immutability surfaced before condemning a set? A refusal after DELETE_PENDING preserves protected bytes at the service but leaves the set unavailable to `pin`/`fetch`; no undo path is present. Durable operator pins cover only holds known to this protocol.
- Who exclusively owns each consumer pin? Explicit unpin during fetch defeats its protection; automatic expiry is correctly absent, but crashed-job reconciliation needs an ownership/runbook contract.
- Which future job layer durably persists the set ID and every uncertain phase before retry? `Pending` covers final publication only; this commit does not demonstrate write-new/sync/rename/directory-sync of the whole job.
- Will incomplete/malformed listing responses be treated as ambiguity before enabling destructive GC? The present parser returns partial success, but no malformed real Azure response was observed in this review.

## Design trade-offs and recommendations

ETag-only publication is a reasonable simplification for one never-recreated record: a stale publisher cannot beat the tombstoning CAS, and permanent records prevent ABA through deletion/recreation. Do not generalize that proof to a catalog spanning multiple records. The PRD's leased/fenced decision lifecycle and protected survivor identities still require a cross-object safety argument; merely adding retry loops or a pre-delete catalog read will not solve F-003.

Read-back certification costs a complete remote read and Azure traffic, but the PRD explicitly requires it. Bounded range reads already provide the basic mechanism. Perform it before the immutable manifest and PUBLISHED CAS, and carry the exact service identities forward so verification, restore and deletion refer to the same committed objects.

Keep the good fail-closed behavior: orphan manifests are not authority, tombstoned IDs remain terminal, pins never silently expire, encryption/continuity profiles unsupported by this version are rejected, and recovery remains explicitly rekey-only. Scope/deployment documentation should distinguish those implemented safety mechanisms from the incomplete manifest schema, deferred runtime job persistence and unqualified Azure RBAC/immutability environment.

### B. Stale janitor deletes the last verified set after another janitor clears its decision

```rust
#[test]
fn review_stale_janitor_deletes_last_verified_after_decision_cleared() {
    let env = setup();
    let ids: Vec<String> = (0..3).map(|i| publish(&env, BASE + i * 1000)).collect();
    let verified = DrillResult { ok: true, unix_ms: BASE, detail: "ok".into() };
    let pin = env.sets.pin(&ids[1], "initial drill", BASE).unwrap();
    env.sets.record_drill(&ids[1], &pin.id, &verified, BASE).unwrap();
    env.sets.collect(INSTALL, &retention(false), BASE).unwrap();
    let sets = env.sets.clone();
    let victim = ids[0].clone();
    let previous_verified = ids[1].clone();
    let meta = env.meta.clone();
    let target = format!("{victim}/record.json");
    env.meta.hook(Op::Put, &target, move || {
        let pin = sets.pin(&victim, "concurrent drill", BASE).unwrap();
        let resumed = sets.collect(INSTALL, &retention(false), BASE + 86_400_000).unwrap();
        assert_eq!(resumed.skipped, vec![victim.clone()]);
        let catalog: Catalog = serde_json::from_slice(
            &meta.raw(&sets.catalog_key()).unwrap()
        ).unwrap();
        assert!(catalog.decision.is_none());
        sets.record_drill(&victim, &pin.id, &verified, BASE).unwrap();
        let pin = sets.pin(&previous_verified, "failed recheck", BASE).unwrap();
        let failed = DrillResult { ok: false, unix_ms: BASE, detail: "failed".into() };
        sets.record_drill(&previous_verified, &pin.id, &failed, BASE).unwrap();
    });
    let out = env.sets.collect(INSTALL, &retention(true), BASE + 86_400_000).unwrap();
    assert_eq!(record(&env, &ids[0]).state, SetState::Tombstoned);
    assert_eq!(out.deleted, vec![ids[0].clone()]);
    assert!(out.failures.iter().any(|f| f.code == "cloud_collection_conflict"));
    assert!(ids.iter().all(|id| {
        let r = record(&env, id);
        r.state != SetState::Published || !r.last_drill.is_some_and(|d| d.ok)
    }));
}
```

            b"HTTP/1.1 201 Created\r\ncontent-length: 0\r\nx-ms-version: 2021-08-06\r\nconnection: close\r\n\r\n"
        ).unwrap();

    let container = Container {
        http: client(true).unwrap(),
        base: format!("{address}/data"),
