### Q-1: epoch and writer identity

> Accepted 2026-11-16: require writer ID and epoch on archive metadata, with epoch-bound `If-Match` CAS for authoritative head advancement.

**NOT SATISFIED.** `Checkpoint` and `Index` have sequence, lineage, installation and hashes, but no writer ID or epoch (`src\server\cloud_backup\archive.rs:44-71`). Serve-status explicitly reports `"epoch": null` (`src\server\serve_mode.rs:176`). The missing work is separately listed as ITEM-023/024, Not Started (HA PRD `:837-838`).

### Q-2: fail-closed archive consumption

> Accepted 2026-11-16: require contiguous verification and fail closed on gaps, compaction-floor changes, or divergence; require a new baseline to recover.

**PARTIAL.** Publisher refuses missing history, source divergence and policy changes, resuming after a new snapshot (`src\server\backup_policy.rs:1391-1429`). Index validation enforces ordered contiguous base/sequence chains (`src\server\cloud_backup\archive.rs:164-203`); offline replay verifies objects, lineage/header, continuity and result (`:400-542`). This is strong reusable validation, but not a live reader consumer, tail-polling protocol or automatic verified re-seed path. HA PRD ITEM-019 is Not Started (`:827`). See API inventory below.

### Q-3: reader retention pins

> Accepted 2026-11-16: require retention pins to protect each reader's baseline and needed segments until its position advances or it is safely replaced.

**PARTIAL.** Existing non-expiring **whole-set** pins protect the baseline and all archive objects beneath it; pinned sets cannot be retention-deleted (`src\server\cloud_backup.rs:1362-1399,1660-1666`; `docs\DOCKER-OPERATIONS.md:577-579`). `Pin` contains ID, reason, creation time and kind, not consumer/applied-position state; kinds are Operator and Operation (`src\server\cloud_backup.rs:473-493`). No reader enrollment, pin handoff, applied-position advancement or safe replacement lifecycle exists. Whole-set pins are a viable conservative protection primitive, not a finished reader retention protocol.

### Q-4: actual progress

> Accepted 2026-11-16: require actual durable/source positions and explicit failures for status and failover-loss reporting; never infer progress from the configured interval.

**PARTIAL for the entire answer; EXISTS for honest archival checkpoint/error reporting.** Persisted `ArchiveStatus` reports baseline, checkpoint sequence/time, counters, attempts and last error (`src\server\backup_policy.rs:195-218`); success advances it only after checkpoint publication, errors preserve the checkpoint and increment failures (`:1310-1355`). Baseline changes clear stale checkpoint stamps (`:1317-1320`).

`Runtime::view` exposes policy/status (`:966-977`); `Runtime::archive_progress` exposes an in-memory copy (`:980-984`). HEAD's `/v1/admin/serve-status` combines a live feed sequence and archive checkpoint position/age, withholding sequences when memory requires it (`src\server\serve_mode.rs:139-177`). That compact view exposes a failure count but **not `last_error`**; detailed errors remain in cloud-backup status. It is not an atomic source/archive snapshot, not an epoch-qualified head, and there is no failover-loss-report consumer (HA PRD `:839`, Not Started).

The checkpoint time is a capture/attempt timestamp, **not commit time or a measured durable-upload-completion time**: the runtime initializes `started = now()` before archival (`backup_policy.rs:1294`) and passes it into the checkpoint (`:1310,1455`; `archive.rs:338-347`). `docs\DOCKER-OPERATIONS.md:573-574` also warns that the timestamp is not each commit's time. A configured interval alone cannot establish the loss window.

### Q-5: memory-bound tenants

> Accepted 2026-11-16: use the protected in-process archiver for memory-bound tenants; never expose reserved frames to readers or public endpoints.

**PARTIAL overall; protected publisher path EXISTS.** In-process archival reads the current bindings and exports the log while holding the database read lock; configuration is captured before/after and must remain stable (`src\server\backup_policy.rs:1398-1433`). The checkpoint bundle carries the captured binding set (`backup_policy.rs:1443-1454`), and recovery validates it (`cloud_recovery.rs:648-680`).

There is no reader-facing archive endpoint or reader consumer to validate for reserved-frame exposure. Archive segments contain raw database frames, so successful protected storage capture must **not** be equated with safe exposure to an arbitrary reader/client. End-to-end reader authorization, matching binding generation and TEST-011 remain undelivered (HA PRD `:243,828-830`). The memory checkpoint restore case is tested at `src\server\cloud_recovery.rs:2525-2564`; this is not reader-serving qualification.

### Q-6: replacement and cadence

### Baseline-first guarantees supported by the implementation

1. A scheduler checkpoint requires the latest recorded published snapshot and current matching capture policy, otherwise fails explicitly (`backup_policy.rs:1380-1396`). `open_archive` revalidates the Published record and manifest identity (`archive.rs:211-249`).
2. The segment must continue the baseline/checkpoint lineage and position, include the complete current cut, fit the bounds, and preserve the header (`archive.rs:289-331`). Bounds are 256 checkpoints, 1 GiB cumulative segments, 64 MiB one segment (`:31-39`). Empty cuts append nothing (`backup_policy.rs:1434-1440`).
3. Segment and recovery-bundle objects are created and verified by read-back before authoritative index publication. Index CAS and unknown-outcome reconciliation prevent reporting an unconfirmed different head as success (`archive.rs:364-393`; `cloud_backup.rs:1118-1155`).
4. Replay verifies the full baseline-to-target chain and refuses unavailable/corrupt content; final database and bundle must match (`archive.rs:400-542`). Existing pins protect the whole set's archive from retention (`cloud_backup.rs:1362-1399,1660-1666`).

These are source and mock-store-test guarantees, **not** live Azure, writer-failover or concurrent reader-fleet qualification.

**GATE-001 archive condition: MET, narrowly as written for code implementation.** The condition at HA PRD `:462` asks for baseline-first archival with honest progress and Q-1..Q-6 answered or explicitly deferred; it does not say all six HA requirements must already be implemented. **EPIC-005 readiness: NOT MET. Minimal concrete gaps, without authorizing gated implementation:**

1. **Reader archive contract:** an internal supported path for verified same-lineage baseline download, segment enumeration/fetch after an applied position, head/tail polling and explicit re-baseline on floor/gap/divergence or baseline rollover. Existing offline `cloud_restore` deliberately changes lineage; its final output cannot be used as if it were the same-lineage follower (`cloud_recovery.rs:660`; `docs\STORAGE-FEATURES.md:69-73`).
2. **Reader pin/cursor lifecycle:** protect the active baseline and tail through apply, crash/restart and replacement; hand off whole-set pins safely. Existing pins provide retention protection but have no reader identity/applied-position protocol (`cloud_backup.rs:479-493,1364-1399`).
3. **Progress and freshness integration:** reader durable applied position/age, status failures sufficient for consumers, staleness readiness/refusal and response reporting. Existing archival progress is useful but not an epoch-qualified source/archive/applied-position contract (`serve_mode.rs:139-179`; HA PRD ITEM-020, `:828`).
4. **Protected serving/routing:** binding-generation eligibility, memory reservation guarantees on reader paths, opt-in gateway reader selection and TEST-006/011 evidence (HA PRD `:243,829-830`). Raw archived frames are not a public reader API.
5. **Capacity/cadence qualification:** archive-backed apply/replacement measurements, enrollment ceiling/refusal and selected refresh cadence. GATE-002 explicitly requires a capacity ceiling; ITEM-003 remains Blocked (HA PRD `:463,621,698`).

**Adjacent Q-1 gap, not permission to start EPIC-006:** no epoch/writer-ID-bound archive head exists. That is a recorded requirement and separate Not Started authority/fencing work (HA PRD `:833-840`). A reader contract must not promise epoch-qualified positions until that dependency is resolved; plain ETag CAS and lineage must not be relabeled fencing.

Trade-offs already inherent in the available foundation: exact checkpoint targets rather than arbitrary time/sequence (`archive.rs:75-92`); coarse whole-set retention pins rather than fine-grained reader positions (`cloud_backup.rs:1362-1399`); and O(database-size) follower replay rather than qualified steady-state incremental cost (`replica.rs:28-31`). Reuse of these primitives is supported by evidence; publication success, unseen PITR item completion and production/HA suitability remain **UNVERIFIED**.
