## Findings and recommended regression tests

### F-001 - Medium, coverage: record-to-manifest SHA guard is independently unprotected

**Files/symbols:** `src\server\cloud_backup.rs:1494`, `Sets::fetch`; `src\server\cloud_recovery.rs:1237`, T2's corruption matrix.

**Exact edit/repro:** apply RB01-1 and run `L(T2)`. It passes, as do the 39/19/29-test broader suites above. The existing "manifest changed" case uses `b[0] ^= 0xff`, making the JSON invalid. Consequently parsing can still reject it after manifest hash verification is removed.

**Executed distinguishing fixture:** using `setup()` and `edit()`, parse the stored manifest, increase `created_unix_ms` by one, serialize with `serde_json::to_vec_pretty`, assert unchanged byte length, and overwrite **only the manifest**, leaving the coordination record hash unchanged. The unmutated restore rejects it as `cloud_set_corrupt`, releases the pin and leaves no output. With RB01-1, the restore succeeds and the negative test panics:

> `called Result::unwrap_err() on an Ok value`

This is a non-equivalent survivor: a syntactically valid, same-length manifest alteration is no longer detected.

**Suggested fix/test:** add that valid-JSON corruption case to T2, without calling `rewrite_manifest` because that helper also rebinds the record. No production change is needed; retain the current SHA comparison. The supplemental test name was `adversarial_review_valid_manifest_rewrite_without_record_rebind_is_refused`.

### F-002 - Medium, coverage: the wrong-database-digest case is masked by bundle binding

**Files/symbols:** `src\server\cloud_backup.rs:1519,1559-1565`, `Sets::fetch`; `src\server\cloud_recovery.rs:1311-1332`, T2's "database under a wrong digest" case.

**Exact edit/repro:** replace:

```rust
if bytes != db.bytes || sha != db.sha256 {
```

with:

```rust
if bytes != db.bytes {
```

`L(T2)` still passes, as do all three broader cloud-related suites. Static inspection shows the existing wrong-digest fixture changes the manifest's database digest but not the bundle's `database_sha256`. The later cross-capture binding guard can therefore reject it even without the intended database hash guard. The other damaged-database cases also have structural/CRC checks available to reject them.

**Executed distinguishing fixture:** preserve the original valid database bytes, size, CRC and structural summary; store those bytes under a different valid digest; change both the manifest's database digest and the bundle's `database_sha256` to that wrong digest; recompute the bundle's actual digest/length, and rebind the manifest and record normally. The only broken invariant is now the database content's claimed SHA-256. In outline, using the existing test helpers:

```rust
let database = env.data.raw(&object(&env, ROLE_DATABASE)).unwrap();
let wrong = "ab".repeat(32);
env.data.set_raw(
    &format!("vlite/prod/sets/{}/objects/{wrong}", env.set_id),
    &database,
);
let mut bundle: Value =
    serde_json::from_slice(&env.data.raw(&object(&env, ROLE_BUNDLE)).unwrap()).unwrap();
bundle["database_sha256"] = json!(wrong);
let bundle = serde_json::to_vec(&bundle).unwrap();
let bundle_hash = cloud::sha_hex(&bundle);
env.data.set_raw(
    &format!("vlite/prod/sets/{}/objects/{bundle_hash}", env.set_id),
    &bundle,
);
rewrite_manifest(&env, |manifest| {
    for entry in manifest["objects"].as_array_mut().unwrap() {
        if entry["role"] == ROLE_DATABASE {
            entry["sha256"] = json!(wrong);
        } else if entry["role"] == ROLE_BUNDLE {
            entry["sha256"] = json!(bundle_hash);
            entry["bytes"] = json!(bundle.len());
        }
    }
});
```

The unmutated negative test passes with `cloud_set_corrupt`, zero pins and no leftovers. Under AUDIT-1 it fails because restore returns `Ok`, with `"pin_released": true` and a published output.

**Suggested fix/test:** strengthen the existing wrong-digest case to remove the unrelated bundle-binding failure, or add this focused case beside it. Preserve all output/pin cleanup assertions. The executed supplemental name was `adversarial_review_wrong_database_digest_without_a_binding_mismatch_is_refused`. No current production fix is indicated.

### F-005 - Informational, qualified survivor: revision rejection masks the independent pin guard

**Files/symbols:** `src\server\cloud_backup.rs:1640-1645`, `delete_set`; `Sets::update` at lines 1287-1335; T10 near line 2910.

**Exact edit/repro:** remove only `record.pins.is_empty() &&` from retention condemnation. T10 and the broader 39/19/29-test suites still pass.

**Explanation, from static inspection:** the test saves the victim's revision, then calls `pin`. `Sets::update` assigns `record.revision = random_hex()?` for the pin write. Resumed deletion thus fails the remaining revision comparison even when the explicit pin predicate is absent. Removing **both** predicates is killed by T10, and clearing all pins during restore release is killed by T11.

**Executed isolation fixture:** create a held record, then synthesize a persisted decision naming that held record's **current** revision. HEAD skips it and preserves its objects and pin. AC002-1 instead resumes deletion; the negative fixture fails with:

> `Collection { ... resumed: ["..."], skipped: [], ... }`

**Recommendation/trade-off:** if the explicit pin predicate is intended as an independently protected defense, add a small direct/synthetic guard test like `adversarial_review_pin_guard_independently_refuses_a_held_victim`. Otherwise document the redundancy when interpreting mutation scores. The synthetic held-and-current-revision decision is not evidence that the normal collector generates such a decision. **No normal-API legal-hold loss was reproduced**, and this survivor alone is not a production safety finding.

### F-006 - Low, documentation qualification: source comment overstates capture binding

**File/symbol:** module documentation, `src\server\recovery_bundle.rs:12-15`:

> "the bundle names the database object and the admitted policy it was  
> captured with, so a restore cannot pair it with another set's copy."

The actual comparisons in `Sets::fetch:1559-1565` bind installation, lineage, database digest and policy, not an authenticated capture identity. `docs\SECURITY.md:350-355` correctly qualifies the trust boundary and explicitly permits exchange between captures with identical database bytes/policy by a writer to both containers.

**Executed evidence:** in unmutated code, a supplemental fixture changed the bundle's webhook-subscription inventory to `123456`, wrote the new content-addressed bundle, updated its manifest entry, and rebound the record to the manifest. Restore succeeded; the import report contained `"webhook_subscriptions_to_recreate": 123456` and `"pin_released": true`. This confirms the documented unsigned model, not an unanticipated vulnerability.

**Suggested fix/test:** qualify the source comment to say that mismatched database/policy/installation/lineage are refused, while a self-consistent rewrite by trusted-container writers is outside the hash chain's authenticity guarantees. The supplemental `adversarial_review_self_consistent_unsigned_rewrite_is_accepted` was an executed trust-boundary characterization, not a proposed failure expectation.
