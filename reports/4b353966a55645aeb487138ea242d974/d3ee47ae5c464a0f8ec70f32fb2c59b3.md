# Storage assessment: checkpoint conversion followed by packed backup

**Base:** public `mahpate/Vlite`, commit `25003dd9dace64f5829a4cf2afad23ab8d78edcc`, package v0.7.5. All source links below are immutable and refer to this base.

## Executive verdict

**Conditional candidate, not an exact-state-preserving or exact-graph-revision-preserving compactor.** For an ordinary supported v5 source, `maintenance::convert_to_directory(source, staging)` builds a same-lineage checkpoint at the source's global sequence; `maintenance::backup(staging, new_file)` copies its logical stream into a genuine v5 single file. Production need not adopt directory storage. The second hop does not repair or undo first-hop normalization. Implementation evidence supports preserving retained record revisions, collection state, graph contents and per-live-graph ID high-waters, but **ordinary graph node and edge revisions are rebased UP to the checkpoint**, expired state is physically removed, closed import-job history is discarded, and earlier change history is unavailable. [E1][E2][E3][E4][E5]

The user's local observations (lineage/global sequence/credentials retained, older graph revisions raised to the source checkpoint, stale CAS rejected) are **observations supplied with the assignment, not experiments reproduced here**. Lineage, sequence, upward rebasing and stale-token rejection have independent code support below. Credential retention is supported only conditionally as opaque retained engine payload; no credential-specific storage mapping or authentication behavior was inspected. Existing tests provide useful pieces, including an actual graph-TTL two-hop test, but do not establish the whole proposed production contract. **Do not approve this as lossless maintenance without explicitly accepting import/history losses and graph CAS false conflicts, and completing the bounded prerequisite tests below.**

Ordinary `maintenance::compact` is **forbidden for this objective and is not recommended**: it creates a fresh lineage and invokes the zero-floor writer, which allocates new frame sequences instead of preserving the checkpoint sequence/revisions. Its similar graph-body serializer must not be confused with the same-lineage, nonzero-floor checkpoint path. [E6][E4]

## Both hops and reopen

1. **Load and validate source:** maintenance takes an exclusive read-only source lock, replays with the supplied key if applicable, rejects an incomplete tail, requires v5, and explicitly rejects commit timestamps. This is not online maintenance against an independently writable source. [E1][E7]
2. **Convert at checkpoint `S`:** `create_converted` uses `loaded.sequence`, the original lineage and loaded cipher. For `S > 0`, it writes a validated checkpoint image plus an empty WAL and publishes the manifest. For `S = 0`, it writes only a v5 WAL header. Ordinary conversion supplies a wall clock; this is a filtering rewrite, not a byte copy. [E2][E3]
3. **Write image/header:** the writer emits a v5 header with original lineage and collection high-water; a nonzero floor adds `FLAG_HISTORY` and an advance frame at `S`. Collection declarations restate at sequence 1, record-block entries carry record revisions, vector/import frames restate at `S`, and graph snapshots restate at `S`. The build reload checks completeness, sequence and lineage before syncing. [E3][E4]
4. **Pack:** directory segments concatenate into the single-file logical stream, retaining the first header and hiding later segment headers. `backup` validates that stream, copies all bytes, checks the byte count, then reloads/validates/syncs the staged file and publishes without overwrite. It is byte-identical to the **directory logical stream**, not to the original source or a raw concatenation of all directory files. [E5][E8][E9]
5. **Reopen:** advance-frame replay restores `loaded.sequence = loaded.history_floor = S`; image restatements do not increment the global sequence. `Database` adopts loaded lineage/sequence/collections/import registry/cipher/graph; the next commit uses checked `S + 1`. Packed files use the same loader and do not require a manifest. A conversion test explicitly reopens the packed output and asserts `!is_directory()`. [E10][E11][E12][T1]

Assumption for the invariants below: staging is not independently mutated between hops. If it is mutated, backup faithfully includes those later commits; its head is then the staging head, not necessarily the original source's `S`. The existing conversion test actually exercises such an intermediate write. [T1][E5]

## Two-hop state/invariant matrix

Here `r` is a source live entity revision; `S` is the complete source global sequence. "Retained" excludes state filtered by conversion's clocks.

|---|---|---|---|
| Format/layout | v5 image plus empty WAL, or header-only WAL at `S=0` | Validated logical stream in one normal file | **v5 single-file output**, possibly with `FLAG_HISTORY`; not source-byte identity. [E2][E3][E5][E8][T1] |
| Lineage | Original nonzero lineage supplied to image and WAL headers | Header copied unchanged | Exact lineage preservation, not a new generation. [E2][E3][E5] |
| Global sequence | Floor/head remains `S` despite many restatement frames | Loader restores `S`; next commit `S+1` | Neither lowered nor raised by the two hops themselves; sequence exhaustion remains an error. [E10][E11][E12] |
| Dense records/documents/payload/metadata | One current retained record per ID; extended body writes float32 bytes, opaque payload and metadata; entries include expiry and revision | Copied and decoded through the ordinary loader | Retained content preserved by codec; old values/tombstones are not carried. ### Why graph revision restoration does not rescue production v5

The code does contain `restore_revisions`, separate node/edge revision blocks, a full import-registry image, and a no-clock preserving relocation path. They are selected by `FLAG_PRECISION`, not by ordinary v5 conversion. At this base `precision_supported()` is false in non-test builds, and release readers refuse that capability. The ordinary writer does not emit those supplemental revision blocks. Thus citing that method as proof of exact production graph revisions would be incorrect. [E34][E35][E4]

Temporal edges are another explicit exception in the implementation: their snapshot form carries a revision and whole series, rather than ordinary edge rebasing. **Temporal capability is test-only at this base**, so it is not a supported production escape hatch either. [E25][E36][E37]

## Precise CAS and change-history contract

### CAS

CAS uses **numeric equality against the addressed current entity**, not `(lineage, revision)` comparison, an ordering comparison, or a revision from any entity. Record checks use `Expected::Revision(r) == Some(current)`; graph planner checks use the same equality and pass actual node/edge revisions. [E38][E39]

For retained records, pre-conversion current token `r` remains valid until a subsequent mutation; a genuinely stale token `t < r` stays invalid. For retained ordinary graph nodes/edges, current becomes `S`: a current source token `r < S` now fails, even though its content may be unchanged; `r == S` remains valid. A genuinely stale token for that same entity satisfies `t < r <= S`, so **cannot become valid through this upward rebasing**. This explains the user's stale-CAS observation without asserting exact token preservation. It also shows why the broad conversion doc comment about preserving compare-and-set state must be read with the ordinary graph snapshot implementation, not as a guarantee that every pre-conversion current graph token remains accepted. [E1][E4][E25][E38][E39]

Example (deduced, not executed): node current revision 7, previous token 4, source head 20 -> reopened node revision 20. Both `Revision(4)` and formerly-current `Revision(7)` fail; refetched `Revision(20)` can succeed. No evidence supports lowering a valid retained ordinary graph revision on this route. The record writer has an explicit clamp, but valid source record revisions are already within its range. [E4][E15][E25][E39]

The graph API's write-result fallback `map_or(sequence, |entity| entity.revision)` is **not restoration of an absent original revision**: it reports planner state, or the new operation sequence if the entity is no longer present. Snapshot loading independently established current graph revisions as `S`. Deletion outcomes are separate. [E40][E25]

Deleted/reclaimed entities have no current revision to match. `Expected::Absent` may create a replacement; same record ID can be reused, and graph keys may be recreated with fresh IDs above preserved high-waters. Replacements commit at a sequence greater than `S`, so old source tokens cannot match a recreated entity solely because history was compacted. This avoids a same-lineage sequence-reset/ABA problem; it does not preserve tombstones or make graph IDs globally non-reusable. Graph mutation planning reclaims expired entities before checking further operations. [E12][E14][E23][E39][E41][T4]

### Resumed readers

For an unchanged staging store, nonzero `S` is the new history floor:

- Same-lineage **commit-boundary cursor at `S`** is valid; initially it returns no new changes, and later commits after `S` can be read. Cursors below `S`, including a beginning cursor, return `CursorBeforeHistory`, not a silent partial history. [E32]
- Same-lineage cursor **above head** returns `CursorAhead`; "at or after checkpoint" is not unconditional acceptance of arbitrary future positions. Wrong nonzero lineage returns `CursorCompacted`. [E32]
- Graph event/ordinal cursor **partway through commit `S`** is rejected even though its sequence equals the floor: the image cannot reproduce the remaining events of that commit. Commit-boundary and event-position cursors are not interchangeable. [E33]
- Snapshot frames provide graph-key context for later changes, not replayable historical changes before the floor. Retained per-record revision `r < S` does not mean change readers can resume at `r`. The graph-key-after-checkpoint test demonstrates the context mechanism, not preservation of old history. [E32][T3]

An empty `S=0` conversion has no advance frame and no historic commits to discard. This is a separate header-only case, not an example of a nonempty store retaining its old feed. [E2]

## Unsupported cases, irreversible changes and failure conditions

**Unsupported production combinations:** pre-v5 sources; commit timestamps (therefore no timestamp-history fidelity on this route); unknown/unsupported header flags; test-only precision or temporal capabilities. Header validation rejects invalid feature combinations before accepting the source. Do not solve older-format rejection by quietly calling `upgrade`: it changes lineage and is outside this preservation objective. [E1][E6][E35][E36][E37]

`FLAG_COMPACT` storage images are not synonymous with the forbidden `maintenance::compact` call, and the flag alone is not categorically rejected by production readers. At this base the compact-image reader rejects critical/unassigned block kinds but can skip authenticated declared-derived blocks; ordinary conversion does not carry that envelope/derived-block cache forward. Treat capability-table/compact-image source variants as separately unqualified for this proposal, not as evidence of precision support or full block-byte fidelity. [E37][E43][E3]

**Irreversible normalizations:** previous mutation history and old values/tombstones; expired records and graph entities/incident edges/attachments; older ordinary graph revisions and old per-graph freshness markers; closed import status/provenance and high-water derived only from discarded jobs; disposable index caches/sidecars. Surviving future deadlines and current stored values are distinct from time-travel fidelity. This is a bounded-state checkpoint operation, not a full historical archival copy. [E4][E19][E20][E25][E26][E30][E31]

**Failure handling:** source locking, malformed/corrupt input, incomplete tail, missing/wrong encryption key, unsupported flags, serialization bounds/graph validation, missing destination parent/permissions/storage errors, or an already-existing destination can fail the operation. Conversion creates a new directory and removes it on pre-manifest failure; packed backup stages in the destination directory and publishes without overwrite. Once visible, failures can return `PublicationIndeterminate` rather than remove published output. Unix directory syncing and Windows' lack of a corresponding guarantee are documented. There is **no atomic all-or-nothing transaction across the two public calls**: a successful staging conversion remains if packing fails. The source is not replaced by either call. These are storage-publication facts only, not a production replacement/lifecycle design. [E1][E2][E7][E9][E21][E27][E29][E42]

Size reduction is plausible from discarding log history but **not guaranteed**: restatement overhead, current live content and fresh encrypted frames still occupy space. No benchmark or size measurement was performed, and neither API checks that packed output is smaller than source. [E4][E5]

## Bounded prerequisites before using the primitive

These are recommended future tests, **not new tests implemented or run here**:

1. **One rich plain-v5 end-to-end fixture, no intermediate writes:** older/current node and edge revisions plus an unrelated last commit; retained records/documents/metadata; named/sparse/versioned vectors and a partially staged re-embedding job; live and dropped/recreated collections with nondefault settings; graph schema/property indexes, attachments and deleted highest node/edge IDs. Compare logical state after each hop and packed reopen. Assert source bytes unchanged, output v5/non-directory, identical lineage/head, record `r -> r`, ordinary graph `r -> S`, and next-write `S+1`. Check index-query parity and next IDs, not physical index equality. Targets the serializer/loader and coverage gaps above. [E4][E16][E19][E20][E22][T1][T7]
2. **CAS and feed subcases on that fixture:** current/stale/absent node, edge and record tokens; old-current graph token below `S` must fail; token exactly `S` must work where current; delete/recreate and TTL reclaim must not revive old tokens. Exercise boundary cursor `S`, cursor `S-1`, future cursor, wrong lineage and graph split cursor at `S`; verify subsequent feed keys and unchanged sequence after rejected CAS. [E25][E32][E33][E38][E39][T2][T3]
3. **Explicit fidelity-loss fixture:** open import with cumulative counts/digest and retry; closed and aborted higher-ID jobs and dropped-collection provenance; assert preserved open resume and demonstrate closed-status/high-water loss. Require a product decision whether those losses disqualify the primitive. Include long-lived, opaque credential-shaped payloads without real secrets; prove byte fidelity only, not authentication ownership. [E13][E30][E31][T6][T11]
4. **Encrypted/TTL and negative-path variants:** repeat essential two-hop assertions with keyed conversion and backup, wrong/no key, due/future record and graph deadlines, schema uniqueness released by expiry, empty source, timestamp/old-version rejection, incomplete/corrupt source, locked source and existing destination. Use deadlines safely away from sampled wall time; do not infer exact-boundary determinism from a fixture clock unavailable to this API. Check failure leaves source unchanged and no partial published file; explicitly account for indeterminate-publication outcomes. [E1][E2][E3][E9][E20][E29][E42][T4][T8][T9]

**Decision trade-off:** accepting checkpoint rebasing is reasonable only if clients can refetch current graph revisions and tolerate maintenance-induced false conflicts, consumers have consumed full commits through `S` or can resynchronize, and discarded expiry/import/history state is intentionally out of contract. If exact graph tokens or complete persisted import history are required, this pinned production API pair is **not sufficient**; test-only preserving features are evidence of a separate path, not an available solution. No ordinary `compact` substitution is acceptable. [E4][E6][E25][E30][E32][E33][E35]
