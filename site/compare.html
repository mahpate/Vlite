VLite benchmarks

Reproducible performance numbers for VLite's embedded engine, measured in-process against another embeddable vector database (zvec) on the same data, metric and HNSW parameters.

Results Reproduce VLite features
Summary

What the measurements show

Where VLite leads

  • Lower memory growth and a smaller on-disk footprint, in one portable file.
  • Every ingest batch is a checksummed, fsync-before-ack atomic commit with fail-closed recovery.
  • Recall matches the exact oracle, with query latency in the same range.

Where VLite is improving

  • HNSW build time: VLite builds single-threaded today.
  • Reopen with ANN: the HNSW index is rebuilt in memory unless an index snapshot is enabled.
  • Bulk ingest throughput and Python binding overhead (JSON over the C ABI).

What the numbers say

Query speed: close

Exact and HNSW latency are within roughly 10–20%. zvec is slightly faster; part of VLite's gap is its Python binding, which passes JSON through a C ABI on every call.

Build and reopen: zvec

VLite builds HNSW single-threaded and keeps it in memory, so a reopen rebuilds it. zvec persists its index and reopens almost instantly. This is VLite's biggest gap.

Footprint and durability: VLite

VLite uses less memory and disk, and every ingest batch above is an fsync'd, checksummed atomic commit, which accounts for part of its slower ingest.

Methodology

How it was measured

Setup

  • One seeded dataset (64 Gaussian clusters, σ = 0.35), SHA-256 recorded in the results.
  • Same ingest batches for both engines; VLite commits each batch durably.
  • HNSW m = 16, ef_construction = 100, ef = 100 for both (zvec defaults overridden).
  • Every (trial, mode, engine) runs in a fresh process; engine order alternates by trial.
  • Recall is ID-based and tie-aware against a float64 brute-force oracle.

Caveats

  • Synthetic clustered data; real embeddings and larger collections can rank differently.
  • Shared WSL2 host; single sequential client, no concurrent load.
  • Python wrappers differ: VLite uses JSON over a C ABI, zvec uses native bindings.
  • Memory growth is resident memory after build minus before opening.
  • Durability contracts differ, so ingest times are not like-for-like.

Reproduce

# Linux x86_64, Python 3.10+
python -m venv .venv && . .venv/bin/activate
pip install zvec numpy https://github.com/mahpate/Vlite/releases/download/v0.3.0/vlite_embedded-0.3.0-py3-none-manylinux_2_28_x86_64.whl
git clone https://github.com/mahpate/Vlite && cd Vlite
python benchmarks/compare_zvec.py --records 20000 --dimensions 128 --trials 3 --output zvec-20k.json
