## Findings

### P2-1: A successful, non-mutating preflight invalidates the dashboard's data

**Evidence:** `src/dashboard/console-tools.js:1778-1781` calls `ctx.api("POST", "/v1/admin/memory/bindings/preflight", {})` without the existing `{ data: false }` transport option. `src/dashboard/app.js:550-560` classifies every non-search POST without that option as `changesData`; lines 627-628 call `mutationChanged()` on success. Its implementation at `app.js:309-317` clears browse/search/record-inspector output and labels the snapshot "Data changed", even for `outcome:"unchanged"`. Lines 582 and 597 do the same on transport/5xx failures.

**Executed reproduction:** isolated Node fixtures exercised the actual new handler and actual `app.js` transport separately, without a browser. The handler supplied no options. A 200 unchanged preflight, a 500, and a 503 each cleared an existing browse status and changed the snapshot note. Passing `{ data: false }` preserved the same state on success. This is a new call-site issue, not a change to `app.js`.

**Recommendation:** use the established non-data-mutating transport option for preflight, retaining its exact POST route and empty body, and add a focused handler/transport regression. Status is a GET and does not have this classification problem. This preserves REQ-A09's non-mutating operator experience without changing server behavior.

The middleware also logs `credential_id` on a rejected scoped request (`server.rs:1600-1609`), includes it in the generic admin request record (`1610-1616`), and can append a persistent `credential_denied` event with the principal identifier (`1520-1541`). TEST-A09 makes its requests only as the admin; TEST-A10 verifies denials without sweeping their logs/audits.

**Impact and recommendation:** there is no demonstrated resource-name or file-path disclosure in the response bodies, and these are existing generic observability paths, not a new unprivileged data read. Nevertheless, unconditional REQ-A03/SEC-002 acceptance must not be reported as passed. Explicitly reconcile the allowed generic request, authentication-denial, and internal-error events with the PRD; if strict silence/redaction is required, implement a narrowly scoped, reviewed solution without weakening general authentication auditing. Add failure/denied-caller coverage and make clear which observer events remain allowed.

## Server behavior and contract assessment

### Non-mutation and reload regression

- `reload.rs:164-200` contains the shared `check(&Database, ...)`. It preserves the sequence: gRPC restriction, grants-only restriction, changed count, graph-enabled restriction, graph/evidence existence, record plan, orphan coverage in both directions. `changed` at lines 205-210 preserves the original equality predicate and ignores binding ordering while respecting grant ordering.
- `reload.rs:117-151` still holds `published_bindings` through check and step 8. Provisioning, record writes, read-only handling, and conditional install are equivalent to the original; only extraction aliases changed (`planned.writes` to `writes`, the local `served` alias to the fully qualified cell, and the final count alias). A direct baseline comparison found all four reload message constants unchanged and `reload`/`complete` unchanged. The check extraction does not introduce a second validator.
- Preflight at `reload.rs:218-277` reads a file snapshot, then uses only `run_read`; `src/server.rs:586-622` takes the shared database lock and passes `&Database`. It does not acquire `try_reload` or `published_bindings`, provision, write records, install, drain, or prune. The database/served-view read is therefore serialized before or after a concurrent reload's exclusive-lock install. It may still wait behind a writer; "non-interfering" does not mean zero contention.
- Status at `reload.rs:296-327` has no database access or database/reload lock. It reads `current()` once for comparison, reads the source once, and calls the same `admin::reloadable` helper as capabilities (`admin.rs:501-505,571`). "No lock" here must mean no **database or reload** lock: `Served::current` uses its own short RwLock and `is_drained` its retired-list mutex (`reserved.rs:288-295,341-347`).
- `Served::is_drained` only iterates weak entries; it does not prune. Baseline comparisons confirmed `drain` and private `drained` are byte-identical after LF normalization (`reserved.rs:322-337`). The new unit test at `reserved.rs:731-748` pins retained-list length as well as pin lifetime.
- Existing lifecycle and reload behavior are exercised by the unchanged pre-existing tests in the integration and `pins_reload` suites. The existing `admin_call` helper body is unchanged; only its gRPC-only compilation restriction was removed. Name-scan entries move to `check` and justify both read/write lock contexts (`tests/server_name_lookup_scan.rs:132-154`); the complete scanner suite passes.

### Response bodies, confidentiality, and error forwarding

`reload.rs:218-289` correctly maps `reload`, `unchanged`, `restart_required`, `refused`, `unavailable`, and `invalid`. Successful evaluations return 200 even for refusal verdicts. Successful counts and `error:null` are correct; refusal/unavailable/invalid `changed` and `records` are null. Both unavailable variants suppress `bindings`, including after gRPC. Restart/refused retain parsed file counts. Records are zero for `db.is_read_only()` and otherwise use `Checked.writes.len()`.

Status correctly returns `none` only without a source, `unreadable` on read/parse failure, and `agrees` only for equal lengths and zero changes. It otherwise returns `differs`. It returns configured count and advisory drained state without a database read. TEST-A12 covers startup, file edit, reload, binding reorder, and grant reorder.

The apparent `error.to_string()` passthrough at `reload.rs:238-243` is **not** an I/O-path or parser-detail leak: `admin::read_memory_bindings` at `admin.rs:391-411` discards every underlying open, metadata, read, and parse error and constructs exactly three fixed messages: unavailable, must be a regular file, and invalid. Neither path nor parser token survives. Graph/resource errors are replaced with fixed constants at `reload.rs:178-190`; every `refusal_message`/`rotation_message` arm is fixed text (`memory.rs:21-63`). `internal` also discards its supplied error text (`server.rs:1742-1754`). These fixed, previously returned reload messages are permitted by PRD section 3.4; adding raw underlying diagnostic strings would not be permitted.

One specification nuance: the current `plan` returns `Refusal`, not raw storage errors (`src/memory/startup.rs:49-115`). `check` maps its unreadable-storage refusal to the fixed 409 conflict, hence preflight 200 `refused`. The PRD's hypothetical raw `plan` storage-5xx passthrough is not reachable with this API. This is unchanged reload behavior, not a newly introduced swallowed error.

### Authorization and admission

Both literal routes and their capabilities entries are present next to reload (`admin.rs:449-462,615-618`). Neither route is recognized as a memory data-plane read/write operation. Authorization uses the admin-path read-only rejection and deny-unmapped `Need::Admin` (`server.rs:1081-1198,1218-1295`).

The required integration authorization test passes for both methods: no token -> 401, read-only token -> 403 `read_only`, root scoped credential -> 403 `forbidden_scope` (`tests/server_memory_live_grants.rs:967-993`). Ordinary admin evaluation works; error bodies name no resource. Rate limiting is inherited and precedes authorization (`server.rs:1416-1427,3839-3871`), so a limited scoped caller can get 429 rather than 403. Tenant-scoped credentials use the same `Need::Admin` denial branch.

The handler-level status implementation has no 503 path. The whole-router claim "status has no 503" requires a qualification: the unchanged shared rate limiter can return 503 `busy` at its 512-entry capacity before authorization, even on a status request from a new rate-limited scoped principal (`server.rs:3847-3854`). Authorized admin status does not use this scoped limiter and remains independent of database availability.

## Recommendations and design trade-offs

Retain the shared `check` design and the no-database status implementation: they avoid validator drift and let status work during queue saturation and after close. Preserve the advisory file-snapshot and drain semantics; stronger atomicity between file edits, gRPC adoption, or later reload would require additional locking that this PRD intentionally rejects.

Fix the preflight transport classification, complete the integrated recapture, and reconcile the absolute no-log/confidentiality/no-503 wording with generic request/error/auth middleware rather than claiming that a direct-function text scan proves transitive silence. Keep generic authentication observability unless an explicit reviewed policy requires route-specific redaction. Scope any additional tests to these demonstrated gaps rather than broadening the implementation.
